## 만들어 놓고 안 이은 자리 여덟 (2026-09-26 발견·수정, P0058)

1-A 를 「끝냈다」고 보고한 직후 사용자가 «전체 다 구현 했다고?» 라고 물었고, 세어 보니 여덟 자리가
**만들어만 놓고 아무도 안 부르는** 상태였다. 단위 시험은 전부 초록이었다.

| 자리 | 결과 | 고친 방법 |
|---|---|---|
| `seedRegularSessions` 소비처 0 | 캘린더가 영원히 비어 크론이 매분 `no_session_row` 로 끝남 — **봉이 한 줄도 안 쌓임** | `ensureSessionWindow` 로 바꿔 크론이 그날 줄을 스스로 세움 (옛 함수는 지움) |
| `aggregateBars` 소비처 0 | 5분 봉이 저장 안 됨 (단정 15개로 검증돼 있었는데) | 구간을 닫는 분에서만 묶어 저장 |
| `KisClient.price` 소비처 0 | 미결제약정이 늘 null | 시세를 불러 `open_interest` 를 채움 |
| `ai_request_at`·`ai_response_at` 미기록 | Jev 지연을 못 잼 (§14.2 필수) | 밖으로 나가는 판단기만 시각을 남김 |
| 야간장 미구현 | §6.1 「야간장도 수집한다」가 안 지켜짐 | 야간 창을 세우고 모으되 판단은 정규장만 |
| `trading_day_config` 미사용 | §14.4 거래일 고정이 안 됨 | 거래일 시작에 굳히고, 그 덕에 마스터 재다운로드도 막음 |
| `syncContracts` 를 매분 호출 | 92KB 마스터를 하루 1,440번 받게 됨 | 굳힌 날은 표에서 읽음 |
| 크론 `job_name` 이 판마다 같음 | 운영과 로컬이 같은 분 슬롯을 다툼 — **로컬이 운영 수집을 가로챌 수 있었음** | 이름에 판을 박음(`trading-tick@development`) |

### 왜 못 봤나

시험이 **함수가 맞게 계산하는가**만 봤다. **그 함수가 불리는가**는 아무도 안 물었다.
크론을 실제로 쳐서 `no_session_row` 를 받고도 「캘린더가 비었으니 맞는 답」으로 읽었다 —
「비어 있는 것이 정상」이 아니라 「채우는 코드가 없다」는 신호였다.

### 어떻게 막았나

`apps/web/lib/policy/trading-wiring-guard.test.ts` 가 `lib/trading/**` 의 값 export 를 전부 훑어
운영 코드 어디에서도 안 불리는 것을 센다. 만들 때 세 번 깨뜨려 보며 고쳤다.

- 시험 파일을 소비처로 세면 **잡아야 할 것을 정확히 놓친다** (`aggregateBars` 가 그랬다)
- `import` 줄만 남아도 통과한다 — 들여온 것은 쓴 것이 아니다
- **주석도 통과시킨다** — 다른 파일 주석에 이름이 적혀 있어 한 번 놓쳤다

셋 다 「이름이 있나」가 아니라 「값이 가나」를 봐야 한다는 같은 이야기다.

## Release 1-B 검증 — 재는 자는 완성, 잰 값은 아직 없음 (P0059)

1-B 는 「이 전략이 비용과 지연을 뺀 뒤에도 남는가」를 **잴 수 있게** 만드는 단계다.
재는 자는 다 만들었고, **잰 값은 표본이 쌓여야 나온다.**

### 지금 관문은 전부 「아직 못 잼」이다 — 그것이 정확한 상태다

관문은 검증 합계 **500건 이상**을 요구한다. 1분 판단이라 신호는 많지만, 그 500건은
**봉이 쌓여야** 나온다. 수집이 아직 시작되지 않았으므로 지금 잰 값은 없다.

「미달」이 아니라 「아직 못 잼」으로 뜨는 이유가 이것이다 — 표본 없는 상태를 미달로
말하면 전략이 나쁜 것으로 읽히고, 멀쩡한 전략을 버리게 된다.

### 1-B 를 실제로 통과시키려면

1. 수집이 돌아 봉이 쌓인다 (배포 + KIS 키, 위 1-A 항목)
2. 과거 봉 백필로 개발 구간을 채운다
3. `POST /api/trading/cron/validate` 로 파이프라인을 돌린다
4. 관문 열 항목을 보고 미달 항목을 고친다
5. 마지막에 Lockbox 를 **한 번** 연다 (사람만, 사유를 적고)

### 이 단계에서 확인 못 한 것

- **실제 스프레드 분포**를 모른다. 슬리피지 가정이 얼마나 맞는지는 호가가 쌓여야 안다
- **수수료율이 0** 이다(§19 기본값). 1-B 를 진짜로 돌리기 전에 실제 값으로 바꿔야 한다
- 체결 재현의 **지연 2분**은 가정값이다. 1-C 에서 실제 기록으로 바꾼다

### 확인한 사실 (기억이 아니라 실측)

**KIS 계좌 조회 TR** — 공식 저장소 `koreainvestment/open-trading-api` 의
`examples_llm/domestic_futureoption/<기능>/<기능>.py` 에서 2026-09-26 에 읽었다.

| 무엇 | 경로 | 실전 | 모의 |
|---|---|---|---|
| 잔고 | `inquire-balance` | `CTFO6118R` | `VTFO6118R` |
| 체결·미체결 | `inquire-ccnl` | `TTTO5201R` | `VTTO5201R` |
| 총자산 | `inquire-deposit` | `CTRP6550R` | 없음 |
| 주문가능 | `inquire-psbl-order` | `TTTO5105R` | `VTTO5105R` |
| 야간 잔고 | `inquire-ngt-balance` | `CTFN6118R` | 없음 |
| 야간 체결 | `inquire-ngt-ccnl` | `STTN5201R` | 없음 |
| 야간 증거금 | `ngt-margin-detail` | `CTFN7107R` | 없음 |

조회와 주문은 **같은 `/uapi/domestic-futureoption/v1/trading/` 아래** 살고
앞 네 글자도 겹친다(`TTTO5201R` 은 조회, `TTTO1101U` 는 주문). **끝 글자가 가른다 — 조회 `R`, 주문 `U`.**

이걸 확인하다 주문 금지 가드의 구멍을 찾았다: 규칙이 `(TTTO|JTCE|VTTO)\d{4}U` 라
실전 야간 주문 `STTN1101U` 와 정정취소 `TTTN1103U` 를 **안 잡았다.** 끝 `U` 로 바꿨다.

### 푸시 발송 장치가 없다

이 저장소에 웹 푸시나 문자 발송 장치가 없다. 그래서 「보낸다」는 **대기 표에 넣고
`sent` 로 표시하는 것까지**고, 사람은 신호 화면에서 본다.

장치가 생기면 `lib/trading/notify/outbox.ts` 의 `flushNotifications` 한 곳만 바꾸면 된다 —
정책(`outbox-policy.ts`)과 표는 그대로 쓴다.

### 모의투자 계좌로는 야간 조회를 못 한다

공식 예제에 야간 TR 의 모의 짝이 없다. 그래서 `paperTrId: null` 로 적고,
모의 환경에서 야간 조회를 부르면 **실전 TR 로 대신 부르지 않고 거절한다** —
대신 부르면 모의를 본다고 믿으면서 실계좌를 보게 된다.

### 이 단계에서 확인 못 한 것

- **실제 계좌 연결을 안 해 봤다.** 계좌번호가 `trading_broker_credentials` 에 없으면
  감시가 `watch=no_account` 로 넘어간다. 모의투자 계좌를 먼저 붙여야 한다(§3.2 1-C)
- **보정 모델이 없어 신호가 안 나간다.** 발행은 늘 네 번째 단계(`calibrate`)에서 멈추고,
  그 사실이 화면에 「5단계 중 4단계에서 멈췄습니다」로 뜬다. 1-B 관문을 지나야 풀린다
- **우리 기록의 포지션이 비어 있다.** 체결 연결이 1-C 범위 밖이라 `expected: []` 로 넘긴다 —
  계좌에 포지션이 있으면 `unknown_in_account` 로 잡혀 대조 잠금이 걸린다. 의도한 동작이다
- **실현 손익이 늘 0 이다.** 닫힌 거래를 아직 안 쌓는다. 일일 한도와 목표는 그래서 안 걸린다

## Release 2 Gemini 지식과 설명 (2026-09-26)

### 무엇을 만들었나

| 부품 | 무엇을 하나 |
|---|---|
| as-of 규율 | 지식 표 여섯을 읽을 때 `available_at <= asOf` 를 **한 함수**가 건다 |
| 지식 카드 | 근거 0건이면 안 만든다. 덮지 않고 판을 쌓는다 |
| 소스 분석 | 원문을 보존하고, 인용이 원문에 없는 주장은 버린다 |
| 패턴 리포트 | 숫자는 코드가 세고 AI 는 말로 옮기기만 한다 |
| 스펙 후보 | AI 는 제안만. §15.3 금지 목록은 후보로도 안 올린다 |
| 신호 설명 | 알림이 **나간 뒤에** 붙는다. 알림은 AI 를 안 기다린다 |
| 청산 Jev 섀도 | 기록만. `is_shadow` 가 참이 아니면 DB 가 행을 안 세운다 |
| 설정 도우미 | 우리 설명을 덮지 않고 아래 붙는다 |
| 크론 배선 | 지식은 §10.2 **맨 뒤**, 한 분에 하나, 장중엔 급한 둘만 |

### 지어내기를 세 겹으로 막는다

말 한 겹으로는 안 된다. 카드를 예로 들면

1. **말** — 프롬프트가 「사실에 없는 것을 쓰지 않는다」 「숫자를 지어내지 않는다」
2. **코드** — `validateDraft` 가 근거 0건을 거절한다
3. **표** — `trading_knowledge_cards_sources_not_empty` 검사 제약이 행을 안 세운다

소스 분석은 여기에 한 겹 더 있다: 인용이 **원문에 정말 있는지** 대조하고 없으면 버린다.

### `available_at` 을 앱이 안 쓴다

값을 만드는 함수 자체를 안 뒀다. DB 기본값 `now()` 가 박고, 앱에는 그 값을 넘길 통로가 없다 —
통로가 있으면 언젠가 「이 카드는 그때도 알았던 것으로 해 두자」가 생기고, 그 한 줄이
백테스트 전체를 못 믿게 만든다. 가드가 `insert` 인자 덩어리를 잘라 `available_at` 0건을 센다.

### 이 단계에서 확인 못 한 것

- **실제 Gemini 응답을 안 받아 봤다.** 모델이 요구한 JSON 꼴로 답하는지, 인용을 원문에서
  그대로 옮기는지는 키가 붙고 자료가 들어와야 안다. 못 읽는 응답은 전부 거절로 떨어진다
- **패턴 리포트의 표본이 늘 0이다.** 실현 손익을 아직 안 쌓아 `netPnlR` 이 0 이고,
  표본 하한(기본 30건)에 안 걸려 리포트가 안 만들어진다. 체결 연결이 먼저다
- **청산 섀도가 안 돈다.** 우리가 쥔 포지션이 없어 `position: null` 로 넘긴다.
  체결 연결이 생기면 `tick.ts` 의 `knowledgeOrExplain` 에서 채운다
- **스펙 후보를 사람이 받아들여 본 적이 없다.** 받아들이는 길은 시험이 지키지만
  실제로 설정이 다음 거래일부터 바뀌는지는 한 번 돌려 봐야 안다

## Release 3 AI 운영자와 리포트 (2026-09-26)

### 무엇을 만들었나

| 부품 | 무엇을 하나 |
|---|---|
| 점검 여덟 | 순수 함수가 **센 숫자로만** 판정. AI 는 판정에 안 들어간다 |
| 조치 | AI 가 할 수 있는 것은 **명시 목록 셋**, 나머지는 전부 사람 몫 |
| 인계 | 사람 할 일은 `daily_logs` 로. **새 할 일 표 0개** |
| 브리핑 | 하루 한 번. 조용한 날과 죽은 날을 가른다 |
| 개입 수준 | 항목마다 자동·승인·끔. **자동이 기본인 항목 0개** |
| 기간 리포트 | 신호·지연·점검을 한 장에. 표본 0 은 0% 가 아니라 「없음」 |
| 야간장 | 신호까지 확장하되 **꺼진 채로 시작**, 야간 표본으로 관문을 지나야 켜진다 |
| 크론 배선 | 지식과 같은 **맨 뒤**. 점검은 전부, 조치는 하나만 |

### 「모른다」를 「괜찮다」로 안 센다

이 릴리스에서 가장 많이 나온 판단이 이것이다.

- 점검 상태에 `unknown` 을 따로 뒀다. 값을 못 읽으면 `ok` 가 아니다
- `unknown` 이 `warn` 보다 **앞**이다. 경고는 무엇이 문제인지 아는 것이고, 모르는 것은 그것조차 모른다
- `unknown` 에는 고치는 조치를 안 붙인다. 무엇이 문제인지 모르는데 고치면 고쳤는지도 모른다
- 브리핑이 「조용한 날」(수집은 돌았는데 신호 없음)과 「죽은 날」(봉 0개)을 다르게 말한다
- 리포트에서 표본 0 은 비율 `null` 이고 화면 글은 「잰 것 없음」이다
- `tick` 이 운영자에게 넘기는 측정값이 지금 전부 `null` 이다 — 0 으로 넘기면 점검이 「괜찮다」로 읽는다

### 기본이 사람이다

조치를 **허용 목록**으로 뒀다. 금지 목록으로 두면 새 조치가 생길 때 아무도 검토하지 않은 채로
AI 에게 열린다. 적는 것을 잊었을 때, 허용 목록은 조용히 막고 금지 목록은 조용히 연다.

겹이 셋이다: ① 금지어(이름에 `order`·`gate`·`lockbox` 등이 들어가면 막힘)
② 허용 목록(셋뿐) ③ 실행 직전 재확인(판정과 실행 사이에 목록이 줄었을 수 있다).

### 이 단계에서 확인 못 한 것

- **운영자가 실제로 돈 적이 없다.** `operator_enabled` 가 꺼져 있어 점검·브리핑이 안 돈다.
  켜기 전에 `tick` 이 넘기는 측정값을 실제 값으로 채워야 한다 — 지금은 전부 `null` 이라
  켜면 점검 여덟이 전부 `unknown` 으로 나온다(그것이 정확한 상태이긴 하다)
- **야간 관문을 잰 적이 없다.** 야간 섀도 일수를 세는 자리가 아직 0 을 넘기고,
  그래서 야간 신호는 켜려 해도 막힌다. 의도한 동작이다
- **개입 수준을 바꿔 본 적이 없다.** 셋 다 `approve` 로 시작하고, 자동으로 바꾸면
  다음 거래일부터 AI 가 스스로 한다. 한 번은 사람이 지켜보며 돌려 봐야 한다
- **사람에게 넘긴 업무를 받아 본 적이 없다.** 소유자가 설정에 없으면 `handoff=no_owner` 로 끝난다
