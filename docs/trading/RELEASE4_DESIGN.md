상시 프로세스 등 재검토(D-03)」 한 줄로만 적는다. 설계가 없다. 이 문서가 그 설계다.

## 0. 무엇이 바뀌나

| 지금까지 (Release 1~3) | Release 4 |
|---|---|
| C1 시스템은 **주문하지 않는다**. 사람이 자기 수단으로 한다 | 사람이 **무장**한 동안만 시스템이 주문한다 |
| M1 저장소에 주문 API 를 부르는 코드가 **없다** | `lib/trading/order/**` **안에서만** 있다. 밖은 그대로 0건 |
| 신호 화면 단추 셋: 주문함·건너뜀·손절 설정함 | 그대로 둔다. 무장 중에도 사람이 직접 할 수 있다 |

**C1 과 M1 을 통째로 버리지 않는다.** 경계를 옮길 뿐이다 —
주문 코드가 사는 자리를 한 폴더로 못 박고, 그 폴더 밖에서는 지금과 똑같이 0건을 센다.
그래야 「조회 하나 더」처럼 보이는 줄이 엉뚱한 곳에 생기는 일이 여전히 막힌다.

## 1. 왜 무장(arming)인가

「자동 주문을 켰다」와 「지금 주문이 나갈 수 있다」는 다른 상태여야 한다.

설정 하나로 켜고 끄면, 그 설정은 다른 설정들과 같은 무게로 보인다. 화면에서 스무 개 값 중
하나이고, 잘못 눌러도 화면은 아무 일 없어 보인다. 그런데 그 하나가 **돈을 움직인다.**

그래서 무장은 설정이 아니라 **상태**다.

- **기본이 해제**다. 배포되면 해제 상태로 나간다
- 무장은 **사람만** 한다. AI 도, 크론도, 다른 설정 변경도 못 한다
- 무장에는 **만료가 있다**. 기본 하루 — 켜 놓고 잊는 일을 구조가 막는다
- 해제는 **언제나, 누구든** 된다 (소유자). 켜는 쪽과 대칭으로 만들지 않는다
- 무장·해제는 전부 기록에 남는다. 누가 언제 왜

## 2. 무장 관문 (arming gate)

무장하려면 아래를 **전부** 지나야 한다. 하나라도 아니면 무엇이 모자란지를 말하고 거부한다.

| # | 조건 | 왜 |
|---|---|---|
| A1 | 1-B 검증 관문 통과 (`gate_progress` = ok) | 비용과 지연을 뺀 기대값이 양수임을 확인한 적이 있어야 한다 |
| A2 | 알림이 켜져 있음 | 사람이 신호를 보고 있어야 한다. 무장은 **사람을 대신하는 것이 아니라 손을 빌려주는 것** |
| A3 | 모의투자 계좌로 **20거래일** 자동 주문을 돌려 봄 | 명세 §3.2 1-C 완료 기준이 「20거래일 소액 실거래 후 순손익 > 0」이다. 그 전 단계를 모의로 한 번 더 |
| A4 | 계좌와 기록이 맞음 (`reconciled` = ok, 포지션 잠금 없음) | 어긋난 채로 주문하면 어긋남이 두 배가 된다 |
| A5 | 오늘 안전 게이트 열둘에 `fail` 이 0건 | 깨진 데이터로 자동 주문을 내지 않는다 |
| A6 | 1회 위험이 일일 손실 한도 안 (§9 리스크 산술) | 한 번에 한도를 넘을 수 있으면 한도가 아니다 |

**실계좌 무장은 A1~A6 에 더해 A7 이 필요하다.**

| A7 | 모의 20거래일 실적의 순손익 하한 > 0 (거래일 단위 부트스트랩) | 「돌려 봤다」가 아니라 「남았다」여야 한다 |

## 3. 무장 중에도 못 하는 것

무장은 **신호를 주문으로 옮기는 권한**일 뿐이다. 아래는 무장과 무관하게 계속 사람 몫이다.

- 신규 진입 방향·수량 바꾸기 — 신호가 정한 대로만
- 손절·목표·시간 청산 값 바꾸기 — 설정이 정한 대로만
- 일일 손실 한도 올리기, 안전 게이트 기준 낮추기 (§15.3 그대로)
- **2계약 이상** — Release 1 은 1계약이고 이 릴리스도 1계약이다(D-11)
- 신호 없는 임의 주문 — 주문은 늘 신호 ID 를 물고 나간다

## 4. 주문 흐름

```
신호 발행 (M2 다섯 단계 통과)
  │
  ├─ 무장 안 됨 → 알림만. 지금까지와 같다
  │
  └─ 무장됨
       ① 무장 관문 재확인 (A1~A6 을 그 순간 다시 잰다)
       ② 계좌 대조 — 우리 기록과 계좌가 지금 같은가
       ③ 주문 멱등 선점 — (신호 ID, 주문 종류) 유일 키로 행을 먼저 넣는다
       ④ 넣는 데 성공한 실행만 KIS 주문 API 를 부른다
       ⑤ 주문번호를 받아 적는다. 실패하면 사유를 적고 **재시도하지 않는다**
       ⑥ 체결은 기존 계좌 조회가 확인한다 (1-C 의 대조 경로 그대로)
```

**⑤ 에서 재시도하지 않는 이유**: 주문은 되돌릴 수 없다. 응답을 못 받았을 때
「안 나갔겠지」로 다시 부르면 두 번 나갈 수 있다. 응답이 불확실하면 **미체결 조회로
사실을 확인**하고, 확인될 때까지 그 신호는 `order_unknown` 으로 둔다.

## 5. 청산 주문

진입만 자동으로 하고 **청산은 처음부터 자동**이다 — 진입만 자동이면 들고 있는 것을
사람이 놓쳐야 하는 상황이 생기고, 그것이 가장 위험하다.

청산 계기 넷 (§8 그대로): 손절 도달 · 목표 도달 · 시간 청산 · 당일 청산.
넷 다 **가격 관측이 아니라 계기 시각·계기 가격에 닿았을 때** 주문을 낸다(D-32 는
상태 판정에 대한 규칙이고, 주문을 내는 계기와는 다르다 — 주문을 내고 체결로 상태를 바꾼다).

## 6. 멈추는 장치

| 장치 | 무엇 |
|---|---|
| 만료 | 무장은 기본 하루. 지나면 스스로 해제 |
| 일일 주문 수 상한 | 기본 12건(신호 상한 6 × 진입·청산). 넘으면 그날 해제 |
| 연속 주문 실패 | 3번 연속 실패하면 해제 |
| 대조 어긋남 | `reconciliation_required` 가 뜨는 즉시 해제 |
| 손절 이탈 | `breached` 가 뜨면 해제 (사람이 봐야 한다) |
| 사람 해제 | 언제나. 화면 단추 하나 |

해제는 **주문을 취소하지 않는다.** 이미 낸 주문은 살아 있고, 미체결이면 사람이 취소한다 —
자동 취소를 넣으면 「해제했더니 포지션이 반만 남았다」가 생긴다.

## 7. D-03 재검토 — 상시 프로세스를 안 만든다

명세는 Release 4 에서 상시 워커를 재검토하라고 적는다. **안 만든다.**

- 크론 1분 지연이 문제였다면 그것은 **사람 지연 1~3분**을 없앤 뒤에야 보인다.
  자동 주문을 켜면 사람 지연이 0이 되므로, 그때 실제 지연을 재고 다시 판단한다
- 새 서버는 C2(기존 앱 안에서, 새 서버 없이)에 어긋난다
- 지금 할 일은 **재는 것**이다: 자동 주문의 네 구간 지연(§14.2)을 그대로 기록하고,
  「서버」 구간이 진입 한계가를 자주 넘기면 그때 워커를 다시 꺼낸다

## 8. 표

| 표 | 무엇 |
|---|---|
| `trading_arming` | 무장 상태. 한 행(현재 상태) + 이력 |
| `trading_orders` | 낸 주문. 유일 키 `(신호 ID, 주문 종류)` |

체결은 기존 `trading_fills`·`trading_position_events` 를 쓴다 — 새로 안 만든다.

## 9. 가드

| 가드 | 무엇을 세나 |
|---|---|
| M1' | 주문 TR·경로가 `lib/trading/order/**` **밖**에 0건 |
| 무장 없이 주문 | 주문 함수가 무장 확인을 안 지나는 길 0개 |
| AI 무장 | AI 가 무장하는 길 0개 (§15.3 실행 방식) |
| 기본 해제 | 무장이 켜진 채로 배포되는 길 0개 |

| 재시도 없음 | 주문 호출에 재시도 루프 0개 |

## 10a. 구현하며 바뀐 것 (2026-09-26)

설계를 쓰고 만들면서 두 가지가 달라졌다. 적어 둔다 — 문서와 코드가 갈리면 문서가 거짓말이 된다.

1. **미체결 취소를 사람 창구로 만들었다.** §6 은 「미체결이면 사람이 취소한다」고만 적었는데,
   취소할 방법이 없었다. `cancelOrder` 와 화면 창구를 더했다. 취소는 무장을 안 본다 —
   위험을 줄이는 쪽이고, 무장이 풀린 뒤에도 남은 주문을 지울 수 있어야 한다.

2. **「곧 풀리나」를 묻는 자리를 파일로 갈랐다.** 화면이 그것을 알려면 해제 판정을 불러야 하는데,
   그 판정이 사는 파일은 실제로 **푼다**. 화면을 여는 것만으로 무장이 풀리면 안 되므로
   묻는 일(`order/disarm-view.ts`)과 푸는 일(`jobs/order-job.ts`)을 나눴다.

## 10. 이 설계가 스스로 인정하는 한계

- **모의 20거래일을 우리가 돌려 본 적이 없다.** A3 는 조건이지 실적이 아니다
- **KIS 주문 API 를 한 번도 안 불러 봤다.** 응답 꼴은 공식 예제에서 읽었고 실제로는 다를 수 있다
- **부분 체결**을 1계약이라 안 다룬다. 2계약 이상을 허용하는 날 다시 설계해야 한다
- **장애 중 주문**: KIS 가 응답을 늦게 주는 동안 크론이 다음 분에 다시 도는 경우,
  멱등 키가 두 번째를 막지만 첫 번째가 나갔는지는 미체결 조회로만 안다.
  그 조회도 안 되면 `order_unknown` 이고, 그동안 그 신호는 아무것도 안 한다
