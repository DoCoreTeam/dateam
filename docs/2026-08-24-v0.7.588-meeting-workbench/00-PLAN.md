# 회의 작업대 — 한 화면에서 쓰고, 녹음하고, 합쳐서 정리한다

**상태**: 기획 (구현 착수 전 · 사용자 지시 "절대구현하지마")
**기준 버전**: v0.7.588
**선행 문서**: `docs/2026-08-21-v0.7.572-crm-meeting-capture/` (00-ANALYSIS · 01-PLAN · 02-PLAN-UNIFIED)

---

## 0. 지시 원문과 내가 읽은 것

> "회의노트가져오기도 좋은데 **회의노트를 쓸 수도 있어야** 할것 같고
> **화면 전환이 일어나면 사용이 불편**할거 같으니 **같은 플랫폼을 공유해서 여기서도 바로 작성**할 수 있음 좋겠는데,
> 그리고 더불어서 **작성한 회의노트와 녹음된 회의 내용을 별도로 두고 전체적으로 정리** 하는 방법으로 기획할 수 있겠네
> 분석하고 기획해서 **내가 놓치는것까지** 기획해서 보고해 절대구현하지마"

지시를 넷으로 읽었다.

| # | 요구 | 지금 상태 |
|---|---|---|
| ① | CRM 미팅 화면에서 **회의노트를 직접 쓴다** | 진입 3개(녹음·붙여넣기·가져오기) 중 **쓰기 없음** |
| ② | **화면 전환 없이** — 같은 플랫폼 공유 | 노트 편집은 `(member)` 셸의 다른 라우트. 녹음은 **라우트가 바뀌면 죽는다** |
| ③ | 작성 노트와 녹음 전사를 **별도로 두고**, 합쳐서 **전체 정리** | 저장 구조는 이미 분리돼 있으나 **AI는 한쪽만 읽는다** |
| ④ | 내가 놓치는 것까지 | §3에 12건 |

**중요한 정정 하나.** ②를 "불편"으로 쓰셨는데 실측은 **유실**이다.
`use-recorder.ts:129`의 `useEffect(() => cleanup, [cleanup])`이 언마운트에서 마이크 트랙을 끊는데,
그때 아직 회전(10분)되지 않은 **진행 중 구간은 업로드되지 않는다.** 라우트를 바꾸면 **최대 10분이 조용히 사라진다.**
그리고 지금 CRM의 "녹음 시작"은 **반드시 `router.replace`를 한다**(`MeetingCapture.tsx:101`).

## 1. 지금 구조 — 이미 절반은 맞다

선행 기획(v0.7.572~588)이 "원본은 회의노트 하나, CRM은 스냅샷"을 세워 놓았고 그건 유지한다.

```
meeting_notes (원본 1건 · 개인 소유 · 소프트삭제)
├─ body_html / body_plain ················· 층1 · 사람이 쓴 것
├─ meeting_recording_part (10분 구간)
│    └─ meeting_transcript_segment ········ 층2 · 기계가 받아적은 것
├─ transcript (평문 캐시)
└─ summary / decisions ···················· 층3 · AI가 만든 것

crm_meeting (팀 · 워크스페이스)          ← noteId 참조(FK 없음) + noteSyncedAt
├─ summaryMd ······························ 발행 시 층3 스냅샷
├─ crm_transcript_segment ················· 발행 시 층2 스냅샷
└─ crm_meeting_suggestion (5축) ··········· CRM AI 결과
```

**층은 이미 셋으로 나뉘어 있다.** 지시 ③의 "별도로 둔다"는 **새 테이블이 아니라 화면과 AI 입력의 문제**다.

---

## 2. 원칙 셋

**P1. 한 회의 = 원본 하나 · 층 셋 · 창구 둘.**
창구는 `/meeting-notes/{id}`(개인)와 `/crm/meetings/{id}`(팀). **같은 부품이 같은 데이터를 그린다.**

**P2. 층은 서로 덮어쓰지 않는다.**
전사를 본문에 붙이지 않는다. 정리본이 메모를 지우지 않는다. 정리를 다시 돌려도 **이전 정리가 사라지지 않는다.**
(무손실 원칙 — 목록 심층분석 v0.7.367·회의록 정제 v0.7.571과 같은 계약)

**P3. 화면 전환이 일을 끊지 않는다.**
특히 녹음. 라우트가 바뀌어도 마이크는 계속 돈다.

## 3. 실측 — 지금 이런 상태다 (발견 12건)

> 전부 코드를 직접 읽어 확인했다. 파일:줄 표기.

### 심각 — 사용자가 손해를 본다

**F-1. 라우트 이동 = 녹음 유실 (최대 10분).**
`use-recorder.ts:117-129` cleanup이 `rec.stop()` 없이 트랙만 끊는다. 진행 중 구간의 `ondataavailable`가
정상 경로로 발화하지 않아 그 구간이 업로드되지 않는다. 게다가 `stoppingRef=false`라 onstop이
죽은 스트림으로 `spawnRecorder`를 다시 부른다.

**F-2. CRM의 "녹음 시작"은 녹음을 시작하지 않는다 — 죽은 배선.**
`MeetingCapture.tsx:101`이 `/crm/meetings/{id}?record=1`로 보내는데,
`(crm)/crm/meetings/[id]/page.tsx`는 `searchParams`를 **아예 받지 않고**, `MeetingDetail.tsx`에도
`record` 참조가 없다. `RecordingPanel` 사용처는 `(member)/meeting-notes/MeetingDetailClient.tsx:171` **한 곳뿐**.
→ 미팅과 노트는 만들어지고 화면은 넘어가는데 **아무것도 녹음되지 않는다.** 사용자는 녹음 중인 줄 안다.

**F-3. AI가 반쪽만 읽는다 — 지시 ③의 핵심 빈칸.**
`buildSummaryPrompt(bodyPlain)`(`summary-prompt.ts:23`)·`extractMeetingItems`는 **본문만** 받는다.
CRM 5축은 `crm_transcript_segment`(**전사만**)를 읽는다.
→ **"메모 + 녹음"을 함께 읽고 정리하는 경로가 지금 어디에도 없다.**

**F-4. 전사 결과를 볼 화면이 노트 쪽에 없다.**
`(member)/meeting-notes/` 폴더 전체에 문자열 `transcript` **0건**.
전사는 `meeting_notes.transcript`와 `meeting_transcript_segment`에 쌓이는데(`transcribe-parts.ts:106,140`)
화면은 진행률만 보여준다. **녹음이 끝나도 받아적은 내용을 볼 수 없다.**

**F-5. 붙여넣기 경로는 노트를 빈 껍데기로 남긴다.**
`savePasted`(`MeetingCapture.tsx:107`)는 `withNote:true`로 노트를 만든 뒤
전사는 **CRM API로만** 넣는다. 그 노트는 영원히 비어 있다 → "원본은 회의노트 하나" 원칙이 이 경로에서 깨진다.

### 중간 — 기능이 있는데 안 보인다

**F-6. `summaryMd`가 미팅 상세에 안 그려진다.**
`MeetingDetail.tsx:44`에서 타입으로 받기만 하고 JSX에 없다. 목록 배지·`MeetingPanel`은 쓰는데
정작 상세에서 **발행해 온 요약·결정사항이 안 보인다.**

**F-7. 공개 범위를 바꿀 UI가 0개.**
D6 원문 "미팅에서 생성하면 기본으로 공개이고 **수정 할 수 있음** 되지 나만보기라던지" 중 후반부 미구현.
컬럼(마이그 216)·RLS(마이그 220)·기본값은 있는데 화면에 스위치가 없다.
게다가 기존 private 노트를 발행해도 visibility는 그대로라, 다른 CRM 멤버에겐 **"비공개 원본"**만 보인다.

**F-8. 저장 모델이 둘이라 붙이면 충돌한다.**
`MeetingCapture`는 "저장 버튼 없음 — 누르는 순간이 저장". `MeetingEditor`는 "제목 필수 + 저장 버튼 + 저장하면 라우트 이동".
한 화면에 넣으면 이 모순이 그대로 화면에 나온다.

**F-9. 회의 중 자동저장이 없다.**
`MeetingEditor.save()`는 명시 저장이다. 회의 중에 쓰는 글인데 탭이 죽으면 통째로 날아간다.
`lib/forms/useDraftPersist.ts` + `components/ui/DraftRestoreBanner.tsx`가 **이미 있는데** 여기엔 안 붙어 있다.

**F-10. 한 화면에서 쓰면 스냅샷이 상시 낡는다.**
`isStale = note.updated_at > noteSyncedAt`. CRM 화면에서 본문을 편집하면 저장할 때마다 참이 된다
→ **"원본이 수정됐어요 · 다시 가져오기" 배지가 항상 켜져 있는** 상태가 된다. 지금 설계 그대로 임베드하면 반드시 생긴다.

### 낮음 — 설계에서 미리 정해야 하는 것

**F-11. 권한: 남의 회의는 못 쓴다 — 그런데 편집기는 보인다.**
`meeting_notes`의 UPDATE 정책은 본인만이다(216 주석: "읽기 공개이지 편집 공개가 아니다").
CRM 멤버 B가 A의 미팅 작업대를 열면 편집기가 떠 있는데 저장이 실패한다.
**읽기 전용 모드를 처음부터 정해 놓지 않으면 "왜 저장이 안 되지"가 된다.**

**F-12. 참석자가 두 벌이다.**
`meeting_notes.attendees(text[]) + attendee_user_ids` vs `crm_meeting.attendeesJson{memberIds,personIds,externalNames}`.
`match-attendees.ts`가 발행 시 매핑한다. 한 화면에서 편집하면 **어느 쪽을 고치는 것인지** 명확해야 한다.

## 4. 요구① — 같은 화면에서 쓴다

### 4-1. 무엇을 만드나 — 셸 중립 공용 부품 4개

`apps/web/components/meeting/` (신설 · INVENTORY 등재)

| 부품 | 하는 일 | 재사용 |
|---|---|---|
| `MeetingWorkbench` | 탭 3개(작성·녹음/전사·정리)를 묶는 껍데기 | `SegmentedTabs`(렌더러 SSOT) |
| `MeetingMemoEditor` | 본문 편집 + **자동저장** | `TiptapEditor` · `useDraftPersist` · `DraftRestoreBanner` |
| `MeetingTranscriptView` | 전사 세그먼트 목록(지금 없는 화면) + 붙여넣기 상자 | `EmptyState` · `SkelList` |
| `MeetingDigestPanel` | "전체 정리" 실행 + 결과 + **출처 뱃지** | `NbButton` · `NbBadge` · `RichText` |

**두 창구가 이 넷을 그대로 import한다.**
`/meeting-notes/{id}` = 작업대 + 개인용 곁가지(태그·부서·CRM 발행 카드)
`/crm/meetings/{id}` = 작업대 + 팀용 곁가지(회사·딜·5축 인박스)

> §0 시스템 참조 순서를 따랐다 — `INVENTORY.md`에 회의 전용 부품은 0건이고,
> 중복 경보 성격(로딩·탭·표·빈상태·헤더)은 전부 **기존 부품을 쓴다.** 새로 그리는 것은 전사 목록 하나뿐이다.

### 4-2. 진입 재설계 — 넷째 버튼 "직접 쓰기"

`/crm/meetings/new`의 카드를 넷으로.

```
[ 🎙 녹음 시작 ]  ← 크게. 라우트를 바꾸지 않는다(§4-3)
  ✏️ 직접 쓰기      ← 신설. 미팅+노트 생성 → 작업대 '작성' 탭
  📋 회의 내용 붙여넣기
  📓 회의노트에서 가져오기
```

넷 다 목적지가 같다 — **미팅 작업대**. 지금은 붙여넣기만 화면 안에서 처리하고 나머지는 이동한다.

### 4-3. 화면 전환을 없애는 실제 방법

**문제**: Next App Router에서 `/crm/meetings/new` → `/crm/meetings/{id}`는 **다른 라우트**라
페이지가 언마운트된다. `history.replaceState`로 URL만 바꾸면 라우터와 어긋난다.

**답 둘을 같이 쓴다.**

**(a) 녹음을 셸로 올린다 — `RecordingProvider` + `RecordingBar`**
`(crm)`·`(member)`·`(ci)`·`admin`이 **전부 `components/ui/shell/AppShell`을 쓴다**(실측).
그래서 provider를 AppShell 안에 **한 번만** 두면 네 표면 전체가 덮인다.

```
AppShell
└ RecordingProvider   { noteId, meetingId, state, elapsed, parts }
   ├ RecordingBar     ← 녹음 중이면 어느 화면에서든 상단에 상주(빨간 점·경과·정지)
   └ {children}
```
- 라우트를 바꿔도 recorder가 **언마운트되지 않는다** → F-1 유실 해소
- 회의 중에 딜을 열어 보거나 사람을 검색해도 녹음이 계속된다 (이게 "같은 플랫폼 공유"의 실체)
- **동시 녹음 1건으로 잠근다.** 두 개가 돌면 어느 노트에 붙는지 사람이 알 수 없다.
- `beforeunload` 경고 + 탭 종료 시 진행 구간 flush

**(b) `new` 화면에서 바로 시작한다**
"녹음 시작"을 누르면 ①미팅+노트 생성 ②**그 자리에서 recorder start** ③그 다음에 `router.replace`.
provider가 셸에 있으므로 ③이 녹음을 죽이지 않는다.

> **F-2(죽은 `?record=1`)는 여기서 자연히 사라진다** — 쿼리로 다른 화면에 "녹음해라"를 시킬 필요가 없어진다.

### 4-4. 저장 모델을 하나로 (F-8)

작업대의 계약은 **`MeetingCapture`의 것**을 따른다 — *"내용을 넣기 시작하는 순간이 저장이다."*

| | 규칙 |
|---|---|
| 제목 | 비워도 된다. `8/24 미팅`으로 채운다(`fallbackTitle` 재사용) |
| 본문 | 5초 debounce 자동저장 + 로컬 임시저장(`useDraftPersist`). 저장 버튼은 **없다** |
| 상태 표시 | 헤더 옆에 `저장됨 14:32` / `저장 중…` / `저장 실패 · 다시 시도` |
| 실패 | **조용히 삼키지 않는다.** 로컬 임시저장본은 남기고 배너로 알린다 |
| 라우트 | 저장이 화면을 바꾸지 않는다 (`MeetingEditor`의 `router.push`는 작업대에선 안 쓴다) |

`(member)/meeting-notes`의 기존 `MeetingEditor`는 **남긴다** — 나중에 차분히 정리할 때 쓰는 전체 편집면이다.
본문 편집만 `MeetingMemoEditor`로 뽑아 둘이 공유한다(중복 구현 금지).

### 4-5. 권한 (F-11)

| 보는 사람 | 작성 탭 | 전사 탭 | 정리 탭 |
|---|---|---|---|
| 노트 주인 | 편집 | 편집(화자 교정) | 실행 |
| 같은 워크스페이스 CRM 멤버 (visibility=crm) | **읽기 전용** + "원본 주인만 고칠 수 있어요" | 읽기 | **CRM 5축만** 실행 |
| 그 외 | 스냅샷만 (지금과 같음) | 스냅샷 | — |

읽기 전용은 **편집기를 비활성으로 보여주는 게 아니라 `RichText`로 그린다.** 못 쓰는 입력칸은 오해를 만든다.

## 5. 요구② — 작성본과 녹음본을 별도로 둔다

**새 테이블은 필요 없다.** 이미 나뉘어 있다(§1). 필요한 것은 **화면에서 섞이지 않게 하는 것**뿐이다.

### 5-1. 절대 하지 않는 것

- 전사를 `body_html`에 붙이지 **않는다** (한번 섞이면 되돌릴 수 없다)
- 정리본을 본문에 덮어쓰지 **않는다**
- 전사를 "정리했으니" 지우지 **않는다** (오디오만 보관 기간 후 삭제 — v0.7.581 `audio-purge` 유지)

### 5-2. 화면에서의 분리 — 탭 3개

```
┌ 작성 ──────────── 녹음·전사 ──────── 정리 ┐
│ 내가 쓴 메모        받아적은 것          합친 결과 │
│ (Tiptap)           (세그먼트 · 시각)     (안건·결정·제안) │
└──────────────────────────────────────────┘
```

- **작성**: 회의 중에 손으로 치는 곳. 자동저장.
- **녹음·전사**: 구간별 진행 + 전사 목록. 화자 이름 교정 가능(`speaker`). 붙여넣기도 여기.
- **정리**: 버튼을 눌러야 돈다(D7 계약 유지 — 전사는 자동, 분석은 버튼).

각 탭 제목 옆에 **분량 배지**: `작성 1,240자` / `전사 38분 · 412줄` / `정리 8/24 15:02`.
비어 있으면 비었다고 말한다 — 사용자가 "녹음이 됐나?"를 화면에서 알 수 있어야 한다(F-4 해소).

## 6. 요구③ — 전체적으로 정리한다

### 6-1. 입력 계약을 둘로 넓힌다

```ts
// lib/meeting/digest-prompt.ts (신설 · SSOT)
buildMeetingDigestPrompt({
  memo:       string,   // body_plain — 사람이 쓴 것
  transcript: string,   // 세그먼트를 "화자: 말"로 이은 것
})
```

**기존 `buildSummaryPrompt`는 지우지 않는다.** 메모만 있는 회의(녹음 없음)가 대부분이고,
그 프롬프트는 v0.7.571에서 두 번 실패한 끝에 겨우 맞춘 계약이다(수량 상한 금지 · 묶되 버리지 않기).
**`digest`는 그 계약을 상속하고 소스 구분만 더한다.** 전사가 없으면 `digest`가 `summary` 경로로 위임한다.

### 6-2. 출력에 **출처**를 박는다 — 이게 "별도로 두고 합친다"의 실체

```json
{
  "agenda": [
    { "title": "예산·사업 범위",
      "facts": [
        { "text": "기존 15억 원 → 40억 원으로 증액 요청함", "origin": "both" },
        { "text": "배수현 팀장이 구미시 협의 일정을 8/29로 제안함", "origin": "transcript",
          "segmentIds": ["..."] },
        { "text": "(중요) ISP 없이 바로 ISMP로 가는 안 검토", "origin": "memo" }
      ] }
  ],
  "decisions": [ { "text": "...", "origin": "memo" } ],
  "conflicts": [
    { "memo": "예산 3억", "transcript": "김대표: 예산은 3억 5천으로 품의했습니다", "segmentIds": ["..."] }
  ]
}
```

**충돌은 어느 쪽도 버리지 않는다.** 메모는 사람의 해석이고 전사는 발화 그대로다 —
둘이 다르면 **둘 다 보여주고 사람이 고른다.** 조용히 하나를 택하면 그게 틀렸을 때 아무도 모른다.

화면에서는 뱃지로: `메모` / `녹음` / `둘 다` / `⚠ 어긋남`.
`녹음` 뱃지는 누르면 전사 탭의 그 대목으로 간다(CRM 5축의 근거 UX와 같은 방식 — 이미 있는 패턴).

### 6-3. 긴 회의 — map-reduce (지금 없으면 60분 회의에서 반드시 깨진다)

60분 한국어 전사 = 4~6만 토큰. 출력 상한 32,768. 메모까지 얹으면 넘는다.

```
구간(10분) × N → [1차 압축: 구간별 안건·사실]  ← 파트 경계를 그대로 쓴다
                        ↓
             [2차 종합: 메모 + 구간 요약 N개 → 최종 정리]
```
`meeting_recording_part`가 **이미 10분 단위**라 경계를 새로 만들 필요가 없다.
1차 결과는 구간 행에 저장해 재실행 시 재사용한다(비용·시간 절감).

### 6-4. 정리본은 버전으로 쌓는다 (P2)

지금은 `summary`/`decisions`를 **덮어쓴다.** 정리를 두 번 돌리면 첫 결과가 사라진다.
회의록은 되돌릴 수 없는 자산이라 이건 위험하다(주간보고 `weekly_report_snapshots` 전례).

**마이그 221 (신설 · 추가 전용)**
```sql
create table meeting_note_digest (
  id           uuid primary key default gen_random_uuid(),
  note_id      uuid not null references meeting_notes(id) on delete cascade,  -- 소유
  seq          int  not null,                     -- 1부터
  agenda_json  jsonb not null,                    -- §6-2 구조
  decisions    text,
  sources      jsonb not null,                    -- { memoChars, transcriptSegments, partIds[] }
  model        text,
  created_at   timestamptz not null default now(),
  unique (note_id, seq)
);
```
- `meeting_notes.summary`/`decisions`는 **최신 정리본의 평문 사본**으로 계속 채운다(기존 소비처 6곳 무영향 — 추가 전용)
- 화면에 "이전 정리 보기" — 되돌릴 수 있으면 사람이 부담 없이 다시 돌린다

### 6-5. AI 두 개의 관계 (선행 §7 계승)

1차에서는 **입력만 통일**하고 프롬프트는 안 합친다.

| | 읽는 것(현재) | 읽는 것(변경 후) |
|---|---|---|
| 회의노트 AI (`meeting-summarize` / `meeting-extract`) | 메모만 | **메모 + 전사** |
| CRM 5축 (`five-axis-suggest`) | 전사만 | **메모 + 전사** |

같은 원본을 읽게 하는 것만으로 지시는 달성된다.
중복 방지는 CRM 인박스 카드에 한 줄 — *"이 회의는 회의노트에서도 할 일 N건을 뽑았습니다"* + 링크.
**자동 판정은 하지 않는다**(제목 대조는 틀린다).

| 발견 | 이 기획의 답 |
|---|---|
| F-1 녹음 유실 | `RecordingProvider`를 AppShell로 · cleanup에서 진행 구간 flush · `beforeunload` |
| F-2 죽은 `?record=1` | 쿼리 배선을 없앤다(§4-3) · 가드: "선언만 하고 소비 0" 검사에 등재 |
| F-3 반쪽 AI | `buildMeetingDigestPrompt` 신설(§6-1) |
| F-4 안 보이는 전사 | `MeetingTranscriptView` 신설 · 탭 배지로 분량 노출 |
| F-5 빈 노트 | 붙여넣기를 **노트 `transcript`에 먼저 쓰고** CRM은 발행으로 받는다(원본 하나 원칙 복구) |
| F-6 안 그리는 요약 | 작업대 '정리' 탭이 `summaryMd`를 그린다 · `wired.test.ts`에 등재 |
| F-7 공개범위 스위치 없음 | 작업대 사이드에 `나만 보기 / 영업팀 공개` 2택 · 발행 시 "공개로 바꿀까요" 확인 |

| F-9 자동저장 없음 | 기존 `useDraftPersist` + `DraftRestoreBanner` 재사용 |
| F-10 상시 stale | 같은 화면에서 편집 중이면 배지를 띄우지 않고 **본문 저장 시 스냅샷만 조용히 동기화**. 제안 만료는 **전사가 바뀔 때만** |
| F-11 남의 회의 | 읽기 전용 모드를 명시 설계(§4-5) |
| F-12 참석자 두 벌 | 작업대는 **노트 쪽만** 편집. CRM `attendeesJson`은 발행이 채운다(단방향) |

### 추가로 정해 둬야 하는 것 5개

**G-1. 회의 중 모바일.** 폰으로 녹음하다 화면이 잠기면 브라우저가 `MediaRecorder`를 죽인다(iOS Safari는 특히).
→ 화면 켜짐 유지(`navigator.wakeLock`) + 잠김 감지 시 **경고**. 못 막는 것은 못 막는다고 말한다.

**G-2. 네트워크 끊김.** 구간 업로드가 실패하면 지금은 다음 구간으로 넘어간다(`uploadPart` 주석).
→ 실패한 blob을 **IndexedDB에 보관**하고 복구 시 재업로드. 최소한 "구간 3 올리지 못함 · 다시 시도" 버튼.

**G-3. 오디오 보관과 전사 보존은 다른 이야기.** v0.7.581이 오디오를 기간 후 지운다.
전사·정리본은 **지우지 않는다**는 걸 계약에 명시(`relation-contract.ts`).

**G-4. 삭제 문구.** 노트를 지우면 녹음 구간·전사·정리본이 **함께** 사라지고 CRM 미팅은 **남는다**.
`previewDelete`에 그대로 적는다(R-5: 무엇이 사라지고 무엇이 남는지 둘 다).

**G-5. 비용.** 60분 회의 1건 정리 ≈ 입력 5~7만 토큰. 하루 10건이면 무료 티어를 넘는다.
→ 정리를 버튼으로 둔 이유가 여기에도 있다. `token-logger` feature를 `meeting_digest`로 분리해 **볼 수 있게** 한다.

## 10. 검증 계획 (E-1 ~ E-6) — 판정은 G3(`crm-qa`)에 요청

### 정상 경로
1. `/crm/meetings/new` → 직접 쓰기 → 본문 입력 → **5초 뒤 "저장됨"** → 새로고침해도 남아 있다
2. 녹음 시작 → **다른 화면으로 이동** → 상단 바에 녹음 계속 → 돌아와 정지 → 구간 전부 업로드
3. 전사 완료 → 전사 탭에 줄이 보인다 → **"전체 정리"** → 안건에 `메모`·`녹음`·`둘 다` 뱃지
4. `/meeting-notes/{id}`를 열면 **같은 것**이 보인다

### 예외 (전부 밟는다)
- 마이크 권한 거부 / 녹음 중 탭 종료 / 구간 업로드 실패
- 메모만 있고 녹음 없음 → 정리가 `summary` 경로로 위임되는지
- 녹음만 있고 메모 없음 → 정리가 도는지
- 메모와 전사가 **충돌** → 둘 다 표시되는지
- 60분 이상(구간 7개+) → map-reduce가 도는지, 잘리지 않는지
- 남의 미팅 열기 → **읽기 전용**으로 보이고 저장 버튼이 없는지
- 노트 삭제 → CRM에 "원본 없음", 정리본·전사 동반 삭제 확인
- 콘솔 오류 0

### E-6 (화면으로 못 밟는 것)
- 정리 토큰 상한: 구간 7개 전사를 **실측 1건**으로 재고, 그 값으로 map-reduce 임계를 잠근다
- 앵커: `digestChunkPlan(segments)` 입력·출력 한 쌍을 실측에서 떠 단정으로 박고 **어디서 잰 값인지** 주석에 적는다

G1 `crm-ui-watch` / G2 `policy-audit` / G3 `crm-qa` — **현재 전부 💤 휴면**(보드 실측).
착수 시 다시 띄울지 결정 필요. 안 띄우면 자가수행이 되고 보고에 그렇게 적어야 한다.
