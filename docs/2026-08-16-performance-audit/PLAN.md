# 퍼포먼스 전수 조사 — 무엇이 느린지 재고, 무엇을 고칠지 정한다

작성 2026-08-16 · 기준 v0.7.489 · **조사·기획 문서. 구현 없음.**

---

## 0. 한 줄

**느린 것은 화면이 아니라 셸이다.** 페이지 JS가 198 B인 사실상 빈 화면(`/ci/my-channels`)도
무거운 화면과 **똑같이 DB 왕복 20회 + 인증 서버 왕복 7회**를 쓴다.
화면을 하나씩 최적화해도 이 27회는 그대로 남는다.

그리고 첫 화면이 뜨기 전에 **2.0MB 폰트**를 외부 CDN에서 **직렬 체인**으로 받는다.

## 1. 무엇을 어떻게 쟀나

측정을 신뢰할 수 있게 만든 장치 세 가지:

1. **대조군** — 화면을 안 열고 유휴 상태의 배경 트래픽을 먼저 쟀다. 안 그러면 남의 부하를 내 화면 탓으로 돌린다.
2. **최솟값** — 같은 측정을 3회 하고 최솟값을 썼다. 배경 소음은 **더하기만** 하므로 최솟값이 진짜 비용에 가장 가깝다.
3. **결정적 지표로 전환** — dev 벽시계는 같은 화면이 3.6초와 18.8초로 나올 만큼 편차가 커서 순위를 매길 수 없었다.
   그래서 **렌더 1회당 DB 왕복 수**로 바꿨다. 이 값은 dev/프로덕션과 무관하게 같다.

DB 왕복은 `pg_stat_statements`로 셌다(PostgREST는 요청마다 `set_config`를 정확히 한 번 부른다).
인증 검증은 `SELECT users.aud…` 호출 수로 셌다.

⚠️ **한계 두 가지를 먼저 밝힌다.**
- 프로덕션 URL을 알 수 없어 **실제 배포 환경은 재지 못했다.** 아래 수치는 로컬 dev + 운영 DB 기준이다.
- 처음엔 e2e 저장 쿠키로 쟀는데 그 토큰이 만료돼 매 요청 갱신이 섞였다. **실제 브라우저 세션으로 다시 쟀고**, 본문 수치는 후자다.

## 2. 실측

### 2-1. 화면 1개를 여는 비용 (실제 로그인 세션)

| 화면 | 페이지 JS | DB 왕복 | 인증 왕복 |
|---|---|---|---|
| `/ci/my-channels` | **198 B** | **20** | **7** |
| `/ci/boards` | 3.16 kB | **20** | **7** |
| `/ci/monitoring` | 1.65 kB | **20** | **7** |

**세 화면이 완전히 같다.** 페이지가 무엇을 하든 비용이 안 변한다 = 비용은 셸에 있다.

(참고: 만료 토큰으로 잰 값은 화면별로 7~19회였다. 실세션 20회가 정확한 값이다.)

### 2-2. 어디로 가는 27회인가

| 출처 | 왕복 |
|---|---|
| 미들웨어 `getUser()` — 화면 요청마다 | 인증 1 |
| `(ci)/layout.tsx` — `getRequestUser` + `Promise.all(4)` + `getLoopCounts(5)` | DB 9~10 |
| `resolveActiveWorkspace` · 브랜딩 · 테마 · 프로필 | DB 3~4 |
| 페이지 자신 | DB 1~6 |
| `/api/ci/notifications` **×2**(마운트 시 중복 호출) | DB 4 · 인증 2 |
| `/api/ui-preferences` (목록 화면마다) | DB 1 · 인증 1 |

404 라우트(미들웨어만 도는 경로)도 인증이 발생한다 — **페이지가 없어도 인증은 낸다.**

### 2-3. 첫 화면이 뜨기 전 (프런트)

| 항목 | 실측 | 판정 |
|---|---|---|
| **Pretendard 폰트** | **2,057,688 B (2.0 MB)** · 외부 CDN | ❌ 치명 |
| 폰트 로딩 방식 | `globals.css` **1행 `@import`** ×2 (jsdelivr + Google Fonts) | ❌ 직렬 체인 |
| `preconnect`/`preload` | **없음** | ❌ |
| 빌드된 CSS | 228 KB (전 화면 공통 1장) | ⚠️ |
| 공유 JS | 88.2 KB | ✅ 양호 |
| 화면별 First Load JS | 대부분 100~200 KB | ✅ 양호 |
| 최악 화면 | `/ai-chat/analyze` 443 KB · `/ai-chat` 401 KB | ⚠️ 2곳뿐 |

`@import`는 브라우저가 **globals.css를 받아 파싱한 뒤에야** 폰트 CSS의 존재를 안다.
거기서 다시 DNS → TLS → CSS → 폰트 파일. **최소 4단계 직렬**이 첫 글자 앞에 놓인다.

### 2-4. DB 자체는 범인이 아니다

| 항목 | 실측 |
|---|---|
| 가장 큰 테이블 | `ci_jobs` **2,049행** |
| 앱 쿼리 평균 실행 시간 | **0.1 ~ 0.3 ms** |
| 로컬 → Supabase 왕복 | **11 ~ 20 ms** |

데이터량도 쿼리 자체도 문제가 아니다. **왕복 횟수 × 왕복 지연**이 전부다.
그래서 왕복이 20회면 로컬에서 300ms, 지연이 190ms인 환경이면 **3.8초**가 된다.

### 2-5. 예외적으로 느린 쿼리 (누적 기준)

| 쿼리 | 호출 | 평균 | 최악 |
|---|---|---|---|
| `get_schema_digest()` | 260 | **136 ms** | 829 ms |
| `SELECT * FROM gpu_audit_logs LIMIT/OFFSET` | 2,397 | **71 ms** | 347 ms |
| `market_prices` 조회 | 372 | 59 ms | 601 ms |
| `ci_content_metrics` 조회 | **103,042** | 0.3 ms | — |

마지막 줄이 핵심이다. 0.3ms짜리를 **10만 번** 부르면 그게 가장 비싼 쿼리가 된다.

### 2-6. 파생값 계산의 N+1

`lib/ci/analysis/derive.ts`

- `computeDerived(콘텐츠 1건)` = **DB 왕복 8회**(metrics · contents · siblings · siblings metrics · peers · peers metrics · snapshots · upsert) — 전부 순차
- `recomputeChannelDerived(채널 1곳)` = 콘텐츠 **최대 500건을 `for` 루프로 순차** 호출
  → **최대 4,000회 순차 왕복.** 왕복 10ms만 잡아도 **40초**

실측으로도 잡혔다 — 잡 하나가 15초 동안 DB 왕복 **266회**를 냈다(콘텐츠 33건 × 약 8회).
그리고 이 작업은 **사용자 요청 경로**에서 돈다(`QueueDriver` → `/api/ci/queue/drain`).
CI 화면을 열어 둔 동안 계속 돌며 그 화면의 조회와 **같은 DB를 두고 경쟁**한다.

### 2-7. 캐시가 사실상 없다

| 항목 | 실측 |
|---|---|
| `unstable_cache` 사용 | **전체 1건** |
| `export const revalidate` | **0건** |
| 렌더 전략 | 동적 **283** / 정적 2 / SSG 0 |

브랜딩·테마·조직도·사이드바 배지처럼 **분 단위로 안 변하는 값**도 매 요청 새로 조회한다.

### 2-8. 배포 리전 (⚠️ 확인 필요 — 가장 큰 잠재 위험)

`apps/web/vercel.json`에 **`regions` 지정이 없다.** Supabase는 `ap-northeast-2`(서울)다.
Vercel 함수가 기본값인 `iad1`(미 동부)에서 돌면 DB 왕복 하나가 **약 190 ms**가 된다.

> 왕복 20회 × 190 ms = **3.8초** — 쿼리를 하나도 안 고쳐도 이것만으로 느려진다.

프로젝트 대시보드 설정이 이를 덮어썼을 수 있어 **단정하지 않는다.**
확인 방법: 배포 URL 응답 헤더의 `x-vercel-id` 앞부분이 리전 코드다(`icn1`이면 서울, `iad1`이면 미 동부).

또한 `vercel.json`에 **매분 크론**(`* * * * *` → `/api/cron/analyze-drain`)이 있다.
하루 1,440회이며, 위 N+1 때문에 한 번이 수백 왕복이 될 수 있다.

## 4. 기획 — 무엇을 어떤 순서로

효과 대비 위험이 낮은 순서다. **각 단계는 독립적이고 되돌릴 수 있다.**

### 단계 1 — 폰트 (가장 싸고 가장 크게 체감)

- Pretendard를 **자체 호스팅**하고 **한글 서브셋**으로 줄인다 (2.0 MB → 약 100~200 KB 예상)
- `globals.css`의 `@import` 2줄을 **제거**하고 `app/layout.tsx`에서 `<link rel="preload">` + `font-display: swap`
- Nanum Pen Script는 `--font-tape`로 `.tape-title`(118곳)·`.tape-mini`·`.font-tape`가 쓴다 — **제거 불가**.
  다만 쓰이는 곳이 **제목 몇 글자뿐**이므로 자체 호스팅 + 서브셋 효과가 특히 크다
- 검증: 폰트 전송량 · FCP · 외부 origin 수 0

**왜 1번인가**: 서버 코드를 한 줄도 안 건드리고, 사용자가 가장 먼저 겪는 "흰 화면" 구간을 직접 줄인다.

### 단계 2 — 셸 캐시 (P0-1 · P0-5)

레이아웃이 매 요청 조회하는 것 중 **분 단위로 안 변하는 것**을 캐시한다.

| 대상 | 캐시 |
|---|---|
| 브랜딩 · 전역 테마 | `unstable_cache` + 태그, 설정 저장 시 무효화 |
| 사이드바 배지 5종 (`getLoopCounts`) | 30~60초 TTL |
| 조직 구조 | 태그 기반 |

- 사용자별 값(프로필·워크스페이스)은 **캐시하지 않는다** — 사용자가 섞이면 사고다
- 배지는 실시간일 필요가 없다. **"몇 초 늦은 숫자"와 "매번 5회 왕복" 중 전자를 고른다**
- 목표: 셸 DB 왕복 **20 → 6 이하**

### 단계 3 — 인증 왕복 (P0-3)

- 미들웨어와 페이지가 **같은 검증을 두 번** 한다. 미들웨어는 이미 화면 라우트로만 좁혀져 있으니(`/api` 제외 — 이미 반영됨) 다음 단계는 **세션 검증 결과를 요청 안에서 한 번만 쓰는 것**
- `/api/ci/notifications`가 마운트 시 **2회 호출**된다 → 1회로
- `/api/ui-preferences`는 목록 화면마다 별도 왕복 → **셸 응답에 실어 보내면 왕복 0회**
- 목표: 인증 왕복 **7 → 2**

### 단계 4 — 파생값 N+1 (P0-4)

- `computeDerived`의 8왕복을 **1~2왕복으로** — 형제·동료 콘텐츠와 지표를 **한 번에 읽어** 메모리에서 계산
- `recomputeChannelDerived`의 순차 루프를 **일괄 처리**로 (읽기 1회 → 계산 → upsert 1회)
- 무거운 재계산은 **사용자 요청 경로에서 빼낸다** — `QueueDriver`는 가벼운 잡만, 무거운 재계산은 별도
- 목표: 채널 재계산 **4,000왕복 → 10왕복 이하**

⚠️ 이 단계는 **계산 결과가 바뀌면 안 된다.** 기존 값과 새 값을 비교하는 테스트를 먼저 만들고 착수한다.

### 단계 5 — 리전 (P1-6, **확인이 먼저**)

1. 배포 URL의 `x-vercel-id` 헤더로 실제 리전을 **확인**한다
2. `iad1`이면 `vercel.json`에 `"regions": ["icn1"]` — Supabase와 같은 서울
3. 매분 크론이 정말 필요한지 재검토 (브라우저 구동 드레인이 이미 있다)

**이 단계만 사용자 확인이 필요하다** — 배포 설정 변경이고, 내가 대시보드를 볼 수 없다.

### 단계 6 — 개별 느린 쿼리 (P1)

- `gpu_audit_logs`: `select('*')` → 필요한 열만 · `OFFSET` 페이지네이션 → 커서
- `get_schema_digest()` 평균 136ms: 호출처와 캐시 가능성 확인
- 전체 `select('*')` **54곳** 점검

## 5. 예상 효과 (계산 근거를 함께)

| 단계 | 지표 | 지금 | 목표 | 근거 |
|---|---|---|---|---|
| 1 | 폰트 전송 | 2.0 MB | ~0.15 MB | 서브셋 실측 통상치 |
| 1 | 첫 페인트 앞 직렬 단계 | 4 | 1 | `@import` 제거 + preload |
| 2 | 셸 DB 왕복 | 20 | ≤6 | 캐시 대상 14회분 |
| 3 | 인증 왕복 | 7 | 2 | 중복 호출 3 + API 왕복 2 제거 |
| 4 | 채널 재계산 왕복 | ~4,000 | ≤10 | 일괄 읽기/쓰기 |
| 5 | 왕복당 지연 | ~190 ms(추정) | ~10 ms | 동일 리전 |

2+3+5가 함께 되면 화면 하나의 서버 왕복이 **27 → 8**, 왕복 지연이 **190 → 10 ms**.
단순 곱으로 **5.1초 → 0.08초** 구간이다. (실제로는 병렬이 섞여 이보다 작지만 방향은 같다.)

## 6. 하지 말 것

- **화면 하나씩 최적화하지 않는다.** 198 B 화면도 20왕복인 것이 증거다. 셸을 안 고치면 아무 효과가 없다.
- **JS 코드 분할에 시간 쓰지 않는다.** 번들은 이미 양호하다.
- **인덱스 추가로 시작하지 않는다.** 테이블이 작아 지금은 효과가 없다(데이터가 커지면 그때).
- **사용자별 데이터를 캐시하지 않는다.** 속도를 위해 사용자가 섞이면 그건 성능 문제가 아니라 사고다.
- **측정 없이 고치지 않는다.** dev 벽시계는 같은 화면이 3.6초와 18.8초로 나온다. 왕복 수로 판정한다.
