## 2. 기획 A — 화면 통합 (모달 제거)

### 2-1. 원칙

> **미팅은 "레코드 생성"이 아니라 "캡처"다.** 이 저장소의 캡처 흐름은 전부 한 화면이다
> (`QuickCreateBar` · `/lead-intake` · GPU 통합입력). 미팅만 모달인 것이 예외다.

동종 UI 통일 정책(§2-5)과 충돌하지 않는다 — **회사·인물·딜은 모달을 그대로 둔다.**
그 셋은 만드는 순간 목적이 달성되는 레코드고, 미팅은 아니다. 이 구분을 문서에 못 박는다.

### 2-2. 화면 하나로 합치는 방법 — `new`와 `[id]`가 같은 컴포넌트다

새 부품 `MeetingWorkspace({ meetingId: string | null })` 하나가 두 라우트를 모두 그린다.

| 라우트 | 넘기는 값 | 상태 |
|---|---|---|
| `/crm/meetings/new` | `meetingId = null` | 아직 저장 안 됨 |
| `/crm/meetings/[id]` | `meetingId = id` | 저장됨 |

**저장 버튼이 없다.** 저장은 사용자가 *내용을 넣기 시작하는 순간* 일어난다:

```
[🎙 녹음 시작] · [파일 선택] · [전사 넣기]  중 무엇이든 처음 누르면
   → POST /api/crm/meetings (제목 비어 있으면 "8/21 미팅"으로 자동)
   → router.replace(`/crm/meetings/${id}`)      ← 화면은 그대로, 주소만 바뀐다
   → 그 다음 원래 하려던 동작을 이어서 실행
```

사용자 눈에는 **화면이 한 번도 안 바뀐다.** 모달도, 목록 복귀도, 재클릭도 없다.

**왜 버튼을 누를 때 만드나(미리 안 만드나)**: 미리 만들면 들어왔다 나간 사람마다 빈 미팅이 쌓인다.
**왜 저장 버튼을 안 두나**: 저장 버튼이 있으면 "저장 → 다시 열기"가 다시 생긴다. 그게 지금 문제다.

### 2-3. 레이아웃

`RecordLayout` 3열은 **전사가 없을 때 좌우가 비는 문제**(F-9)가 있다. 상태에 따라 다르게 그린다.

**(가) 내용이 아직 없을 때 — 캡처 화면**

```
← 미팅

┌ 이 미팅은  ─────────────────────────────────── [접기 ▾] ┐
│ 제목  [                     ] ← 비우면 "8/21 미팅"       │
│ 날짜 [2026-08-21] 시각 [14:00]                          │
│ 회사 [ 검색… ▾ ]   딜 [ 검색… ▾ ]   장소 [        ]     │
└─────────────────────────────────────────────────────────┘

┌ 회의 내용 ──────────────────────────────────────────────┐
│                                                          │
│         ┌───────────────────────────────┐               │
│         │       🎙  녹음 시작            │  ← 가장 큰 것 │

│    또는   [ 📎 녹음 파일 올리기 ]   [ 📋 전사 붙여넣기 ] │
│                                                          │
│   · 10분마다 자동 저장돼요. 중간에 끊겨도 그때까지는 남아요│
│   · 화면이 꺼지면 녹음이 멈출 수 있어요                  │

```

- 회사·딜을 **안 골라도 시작할 수 있다**(첫 만남은 회사가 CRM에 없다 — 지금 모달의 좋은 판단, 유지)
- 상단 블록은 접힌다. 급할 땐 녹음 버튼 하나만 보이는 게 맞다

**(나) 녹음 중**

```
┌ 회의 내용 ─────────────────── 🔴 녹음 중 ───────────────┐
│                                                          │
│        12:34            ▁▂▅▇▅▂▁  (마이크 레벨)          │
│                                                          │
│   [ ⏸ 일시정지 ]        [ ■ 종료하고 정리 ]              │
│                                                          │
│   구간 1 ✅ 올림   구간 2 ✅ 올림   구간 3 ⏺ 녹음 중     │
└─────────────────────────────────────────────────────────┘
```

레벨 미터는 장식이 아니다 — **마이크가 실제로 소리를 받고 있는지 보여주는 유일한 수단**이다.
(무음 상태로 60분을 녹음하고 끝에서야 아는 것이 이 기능의 최악의 실패다)

**(다) 전사가 있을 때 — 지금의 3열 유지**

```
좌: 이 미팅은 (제목·회사·딜·장소 인라인 편집 · 참석자)   ← PATCH 필요(F-2)
중: 전사 전문 + 요약  (녹음 중이면 진행률)               ← 주인공
우: AI가 찾은 것 (5축 · 근거 클릭 → 전사 해당 줄로 점프)  ← 지금 그대로
```

가운데 열을 넓힌다(`RecordLayout`에 폭 배분 옵션을 **추가**한다 — 기존 화면 3개는 기본값 유지, M-4 추가 전용).

### 2-4. 목록 화면

| 지금 | 바꿀 것 |
|---|---|
| '미팅 기록' → 모달 | → `/crm/meetings/new` 로 이동 |
| 딜/회사 상세 '미팅 기록하기' → `/crm/meetings` | → `/crm/meetings/new?dealId=…` / `?companyId=…` (**죽어 있던 `fixedDealId` prop이 URL 상태로 부활**, F-3) |

`MeetingFormModal.tsx`는 **삭제하지 않는다** — 다른 세션(`crm-picker`)이 claim한 파일이다.

## 3. 기획 B — 녹음 → 전사 → 분석 파이프라인

### 3-1. 설계를 지배하는 세 제약 (분석서 §2-3)

| 제약 | 값 | 이 설계의 답 |
|---|---|---|
| Vercel 요청 본문 | 4.5MB | **API로 오디오를 안 보낸다.** 브라우저 → Storage 직행 |
| 함수 실행 | 300초 | **10분 구간 단위로 쪼개서** 여러 틱에 나눠 처리 |
| AI 출력 | 32,768토큰 | 10분 구간 전사 ≈ 8~12k 토큰 → **절단 없음** |

→ **10분 구간(part)이 세 제약을 동시에 푸는 단위다.** 이것이 이 설계의 축이다.

### 3-2. 녹음 — 10분마다 레코더를 새로 연다

```ts
// 개념 (구현 아님)
const stream = await navigator.mediaDevices.getUserMedia({
  audio: { echoCancellation: true, noiseSuppression: true, channelCount: 1 },
})
// mimeType 협상: audio/webm;codecs=opus → audio/mp4(Safari/iOS) → 없으면 이유를 말하고 멈춘다
// audioBitsPerSecond: 32_000  (음성 모노 · 60분 ≈ 14MB)
// PART_MS = 10 * 60 * 1000 마다  recorder.stop() → 새 recorder.start()
```

**왜 `timeslice`가 아니라 레코더 회전인가**
`MediaRecorder`의 `timeslice` 조각은 **첫 조각에만 헤더가 있다.** 2번째 이후는 단독으로 디코딩이 안 되므로
따로 전사할 수 없다. 레코더를 다시 시작하면 **구간마다 완결된 오디오 파일**이 나온다.

**이 구조가 그냥 얻어 주는 것 넷**

1. **정지 후 대기가 짧다** — 구간 1~5는 회의 중에 이미 올라가 전사까지 끝나 있다. 종료 시점에 남은 건 마지막 구간뿐
2. **크래시 내성** — 브라우저가 죽어도 올라간 구간은 남는다 (최대 유실 = 마지막 10분 미만)
3. **진행이 보인다** — "3/6 구간 전사됨"을 정직하게 말할 수 있다
4. **출력 절단이 없다** — §3-1

**정직하게 말해야 하는 제약(화면에 고지)**
- 탭이 백그라운드로 가거나 화면이 꺼지면 모바일에서 녹음이 멈출 수 있다 → `navigator.wakeLock` 요청 + `visibilitychange` 감지 시 경고 배너
- 마이크 권한 거부 / iframe / 비보안 컨텍스트 → `/lead-intake`의 `envWarn` 진단 패턴을 **재사용**한다(같은 진단을 두 벌로 만들지 않는다)
- 1차에서는 진행 중 구간을 IndexedDB에 보관하지 않는다 → "마지막 10분은 유실될 수 있어요"를 **화면에 적는다.** 2차에서 보관 추가

### 3-3. 업로드 — 서명 URL로 Storage 직행

```
POST /api/crm/meetings/[id]/recordings/sign   { partIdx, mime }
   → 권한·워크스페이스 확인 → Supabase createSignedUploadUrl(path) 발급
   → path = `${workspaceId}/${meetingId}/${partIdx}.webm`

브라우저 → (서명 URL로 직접 PUT) → Storage      ← 우리 API를 안 거친다

POST /api/crm/meetings/[id]/recordings        { partIdx, storagePath, durationSec, mime }
   → CrmMeetingRecording(status=UPLOADED) 생성 + 전사 큐 적재 + 드레인 1회 킥
```

**새 버킷 `crm-meeting-audio`** (마이그레이션 1개)
- private · `file_size_limit` 200MB · mime 화이트리스트(`audio/webm`,`audio/mp4`,`audio/mpeg`,`audio/wav`,`audio/m4a`)
- RLS: 경로 1단계 = 사용자의 workspace. 읽기·쓰기는 실제로는 전부 서버 service_role 경유(방어 심층화)
- **정책 패턴은 `151_ai_chat_attachments.sql`을 그대로 따른다** (버킷 정책이 pooler 롤로 실패할 수 있다는 주의사항 포함)

### 3-4. 전사 — 기존 `SttAdapter`에 어댑터 하나를 **추가**한다

인터페이스는 이미 있다. **새로 만들지 않는다.**

```ts
// lib/crm/stt/adapter.ts  — 기존 파일에 추가
export function geminiSttAdapter(apiKey, model): SttAdapter   // vendor: 'gemini'
```

- Gemini Files API로 오디오 업로드 → `generateContent`에 audio part로 첨부
- 출력은 JSON 배열 `[{ startSec, speaker, text }, …]` — `lib/ai/json-recover.ts` 재사용
- 모델은 **`lib/ai/gemini-model.ts` SSOT**를 통해 고른다. 모델명 하드코딩 금지(지시 #126)
  - `supportsJsonMode()` 옆에 **`supportsAudio()`를 추가**한다(추가 전용, M-4). Gemma·임베딩 모델은 오디오 불가
- **이전 구간의 마지막 몇 줄 + 확정된 화자 목록을 프롬프트에 함께 준다** → 구간이 바뀌어도 화자 이름이 이어진다
  (안 주면 구간마다 "화자1"이 다른 사람이 된다. 이건 실제로 생기는 문제라 1차부터 넣는다)

**왜 Gemini인가 (권고, 최종 결정은 §7)**

| 후보 | 장점 | 단점 |
|---|---|---|
| **Gemini** ✅ | 키·SSOT·재시도·폴백이 **이미 있다**(0원 추가) · 한국어 양호 · 긴 오디오 지원 | 화자 분리가 프롬프트 의존이라 완벽하지 않음 |
| Clova Speech | 한국어 화자분리 최상 | 새 계약·새 키·새 설정 |
| Whisper(OpenAI) | 정확도 좋음 | 25MB/요청 제한 · 화자분리 없음 · 키는 있음 |
| Deepgram | 실시간·화자분리 | 한국어 상대적 약세 · 새 계약 |

→ **Gemini로 시작한다.** 어댑터 인터페이스가 이미 있으므로 나중에 Clova로 바꾸는 것은 **파일 하나 추가**다.
`sttAdapterFor()`가 `'clova'`·`'deepgram'`에 대해 **여전히 "아직 안 붙었다"고 말하는 원칙은 유지**한다(조용히 mock으로 안 떨어진다).

**설정**
- `PLANNED_SETTINGS`의 `stt.vendor`를 `SETTING_DEFS`로 **승격**한다(선택지: 자동/Gemini)
- `stt.api_key`는 **승격하지 않는다** — Gemini 키는 호스트에 이미 있다(CRM은 키를 갖지 않는다는 기존 원칙 유지)
- 업체 선택 UI를 새로 만들지 않는다 → `components/ui/ModelPickerModal` / `ModelSelectField` 사용(지시 #125)

### 3-5. 잡 — 기존 크론 드레인 패턴 재사용

**새 시스템을 만들지 않는다.** `/api/cron/analyze-drain`과 CRM 잡 3종이 이미 쓰는 모양을 그대로 쓴다.

```
POST/GET /api/crm/jobs/meeting-stt        ← machine-auth.ts SSOT (CRON_SECRET · CI_WORKER_TOKEN)
   export const maxDuration = 300 ; DEADLINE_MS = 270_000
   ① UPLOADED 구간을 락 걸고 집는다 (TRANSCRIBING 전이 — 기존 state-machine이 판정)
   ② 여러 구간을 병렬 전사 (구간끼리 독립이다)
   ③ 세그먼트 저장 (startMs += partIdx * PART_MS  ← 전체가 하나의 시간축)
   ④ 마지막 구간까지 TRANSCRIBED 면 → 추출을 자동 발화
   실패: retryCount++ , 3회 초과 FAILED + error 기록 (기존 규칙 그대로)
```

- `vercel.json` crons에 `*/2 * * * *` 추가
- **업로드 완료 API가 드레인을 1회 킥**한다(fire-and-forget). 크론만 믿으면 최대 2분을 기다린다 — `analyze-drain`이 이미 같은 이중 구조
- **락 회수용 컬럼이 필요하다**: `CrmMeetingRecording`에 `createdAt`만 있고 `updatedAt`이 없다 → `updatedAt`·`claimedAt` 추가(추가 전용 마이그레이션)

**소요 추정 (60분 회의)**

| 단계 | 시간 |
|---|---|
| 구간 1~5 | 회의 중에 업로드·전사 완료 (사용자 대기 0) |
| 종료 → 마지막 구간 업로드 | ~5초 (2~3MB) |
| 마지막 구간 전사 | 30~60초 |
| 5축 추출 + 요약 | 30~60초 |
| **합계(사용자 체감)** | **약 1~2분** — 명세 목표 10분 대비 여유 |

### 3-6. 추출 자동 발화 + 멱등성 (F-5)

- 지금은 **사람이 버튼을 눌러야만** 추출이 돈다. 전사가 끝나면 **자동으로 돈다**로 바꾼다(명세 §3.2-4)
- 'AI로 정리하기' 버튼은 **'다시 정리하기'로 남긴다** — 프롬프트가 바뀌었거나 결과가 나쁠 때 필요하다
- **멱등 키**를 건다: 같은 `(meetingId, recordingSetHash)`로 이미 성공한 run이 있으면 새 run을 만들지 않는다
- 다시 정리하면 **이전 run의 PENDING 제안을 EXPIRED로 거둔다**(이미 사람이 판단한 ACCEPTED·REJECTED는 안 건드린다 — `deleteMeeting`이 이미 쓰는 규칙 재사용)

### 3-7. 요약 — 죽어 있는 6개 경로를 살린다 (F-1)

**같은 추출 호출의 응답에 `summary` 필드를 추가한다.**

> 명세 §3.2-7은 "별도 경량 모델 호출"이라고 했지만 **따르지 않는다.**
> 호출을 하나 더 만들면 실패 지점이 하나 더 생기고 비용·지연이 늘어난다.
> 이미 전사 전문을 프롬프트에 넣고 있으므로 같은 응답에서 받는 것이 싸고 안전하다.
> — **명세에서 벗어나는 결정이므로 여기에 이유를 남긴다.**

- 요약은 **`meeting_summary` 제안으로 인박스에 간다**(절대규칙 1 유지 — AI가 코어에 직접 안 쓴다).
  라벨(`format/suggestion.ts`)과 판정 경로(`apply-policy.ts`)는 **이미 있다.** 생산자만 없었다.
- 수락하면 `crm_meeting.summaryMd`에 기록 → 그 순간 **6개 경로가 처음으로 값을 받는다**
  (목록 배지 · 딜/회사 배지 · CSV · 단계 점검 AI · 다음 행동 AI · 상세 표시)
- 녹음 상태를 `SUMMARIZED`로 전이 → 도달 불가였던 상태가 살아난다
- **정제 계약**: v0.7.571의 "생략 지양 · 수량 상한 금지"를 그대로 적용한다(지시 #126).
  `"3~6개 항목"` 같은 수량 상한을 쓰지 않는다 — 수량은 결과값이다.
- `wired.test.ts`의 `MUST_BE_WIRED`에 **요약 생산 함수를 등재**한다. 같은 사고가 다시 나면 커밋 전에 걸리게.

### 3-8. 관계·삭제 계약 (R-1 ~ R-6)

새 참조가 생기므로 **마이그레이션과 같은 커밋에서** 계약에 선언한다.

| 부모 → 자식 | 종류 | 구현 |
|---|---|---|
| 미팅 → 녹음 구간 | **소유** | FK CASCADE (이미 있음) |
| 녹음 구간 → 전사 세그먼트 | **소유** | FK CASCADE (이미 있음) |
| 미팅 → Storage 오디오 객체 | **소유** | FK 불가 → 미팅 삭제 시 **오디오 객체도 지운다**(코드 + 정리 잡) |
| 미팅 → AI 제안 | **작업** | 이미 EXPIRED 처리 있음 |

- **`previewDelete`에 "녹음 N개(총 M분)도 함께 삭제됩니다"를 넣는다** — 되돌릴 수 없는 일이므로(R-5)
- 오디오 보관 기간(§7 결정 필요)이 정해지면 만료 정리 잡을 붙인다

## 4. 하지 않을 것 (경계)

| 안 하는 것 | 이유 |
|---|---|
| **실시간 자막(Web Speech API)** | Chrome 전용 · 무음에서 끊김 · 백그라운드 불가. 녹음(정본)과 두 벌이 되면 어느 게 진실인지 모른다. 원하면 3차에서 **보조 표시**로만 |
| **화자 자동 실명 매칭** | 목소리로 사람을 특정하는 것은 정확도가 낮고 틀리면 CRM에 잘못된 참석자가 들어간다. 1차는 **사람이 이름을 지정**하면 전체에 반영 |
| **회사·인물·딜 모달 제거** | 그 셋은 만드는 것이 목적인 레코드다. 동종 UI 통일(§2-5)을 깨는 쪽은 미팅만이다 |
| **`/meeting-notes`(회의노트)와 통합** | 다른 제품 영역(사내 회의록)이고 지금 다른 세션이 손대는 중이다. 다만 **`lib/ai/*` SSOT는 공유**한다 |
| **명세대로 QStash 도입** | 이 저장소에 QStash가 없다. Vercel 크론 + 드레인 패턴이 이미 돌고 있다. **입구를 두 종류로 만들지 않는다** |
| **오디오 원본 무기한 보관** | 비용과 개인정보. 보관 기간은 사용자 결정(§7) |

## 6. 검증 계획 (E-1 ~ E-6)

**`완벽히 끝냈습니다`는 아래를 전부 통과해야만 쓴다.** 브라우저 판정은 G3(`crm-qa`)에 요청한다(M-15).

### 정상 경로
1. 딜 상세 → '미팅 기록하기' → **딜이 물려 온 상태로** 캡처 화면이 열린다
2. 제목 안 적고 🎙 누름 → 주소가 `/crm/meetings/[id]`로 바뀌지만 **화면은 그대로**
3. 5분 이상 실제로 말한다 → 레벨 미터가 움직인다 → 종료
4. 전사가 실제로 뜬다 → 요약이 뜬다 → 인박스에 제안이 쌓인다
5. 인박스에서 수락 → **목록 배지가 '정리됨'으로 바뀐다**(F-1이 살아난 증거)
6. CSV 내보내기의 '정리됨' 칸에 값이 있다

### 예외·경계 (E-4 — 전부 밟는다)
| 무엇 | 기대 |
|---|---|
| 마이크 권한 거부 | 읽을 수 있는 안내 + 붙여넣기 경로 안내 |
| 마이크 없음 / 비보안 컨텍스트 / iframe | `envWarn` 진단 문구 |
| 녹음 중 새로고침 | 이미 올라간 구간은 남는다 · 화면이 그 사실을 말한다 |
| 녹음 중 탭 백그라운드 | 경고 배너가 뜬다 |
| 1초 녹음(무음) | "소리가 거의 없어요" — 지어낸 전사를 만들지 않는다 |
| 지원 안 하는 파일(mp4 영상·txt) | 형식 안내, 조용히 실패하지 않는다 |
| 200MB 초과 파일 | 상한 안내 |
| 전사 실패(키 없음·429·모델 404) | `GeminiCallError.userMessage`가 화면에 뜬다 |
| 구간 3만 실패 | 3회 재시도 후 **"6구간 중 1구간 실패"를 말한다** — 부분 실패를 숨기지 않는다 |
| '다시 정리하기' 두 번 | 제안이 두 벌 안 생긴다 (F-5) |
| 빈 전사로 추출 | "확실한 내용을 못 찾았어요" (지금 동작 유지) |
| 미팅 삭제 | 오디오·구간·세그먼트·미처리 제안이 함께 사라진다 · 확인창이 그 목록을 보여준다 |
| 남의 워크스페이스 미팅 id | 404 |
| 없는 id | 404 |

### E-5 · E-6
- 위 전 과정에서 **콘솔 오류 0**
- 브라우저로 못 밟는 것(구간 경계 시간축 오프셋, 락 회수 타이밍)은 **계산으로 밟되 실측 앵커를 함께 박는다**
  예: 실브라우저 녹음에서 구간 2의 첫 세그먼트 `startMs`를 실측 → 같은 입력으로 계산 함수가 같은 값을 내는지 단정으로 고정
