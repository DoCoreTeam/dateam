**① 회의노트를 안 봤다.** `/crm/meetings`만 보고 CRM 안에 녹음·전사·요약을 새로 짓겠다고 했다.

## 1. 두 기능은 같은 사건을 두 벌로 기록하고 있다

| | 회의노트 `/meeting-notes` | CRM 미팅 `/crm/meetings` |
|---|---|---|
| 규모 | **3,968줄** | 약 1,200줄 |
| 기획 이력 | v0.7.184 → 269 (**문서 세트 5벌**) | 없음 |
| 표 | `meeting_notes` (마이그 117·118) | `crm_meeting` |
| 소유 | 사람(`user_id`) + 부서 | 워크스페이스 |
| 본문 | `body_html`(Tiptap) + `body_plain` | **없음** |
| 전사 자리 | `transcript` **컬럼 있음** | `crm_transcript_segment`(구간·화자·시각) |
| 오디오 자리 | `audio_drive_id` · `audio_duration_sec` **컬럼 있음** | `fileUrl`(주석만) |
| 참석자 | `attendees[]` + `attendee_user_ids[]` + **조직원 매칭 SSOT** | `attendeesJson` |
| AI 요약 | `summary` + `decisions` — **작동함** | `summaryMd` — **생산자 0곳**(F-1) |
| AI 추출 | 할 일 · 일정 · 하이라이트 · 참석자 | 5축 WHO/WHAT/WHERE/RISK/NEXT |
| 반영처 | `daily_logs` · `calendar_events` | CRM 제안 → 회사·딜·인물·할일 |
| 목록 | 목록·날짜·**캘린더** 3뷰 + 검색·정렬·페이지 | 자작 `<ul>`, 검색 없음 |

### 결정적 발견 셋

**① 녹음은 회의노트의 예약된 Phase 2였다.** 마이그 117에 컬럼과 주석이 그대로 있다:

```sql
transcript         text,   -- Phase2: 음성 전사 (nullable)
audio_drive_id     text,   -- Phase2: Google Drive 파일 ID (nullable)
audio_duration_sec int,    -- Phase2: 음성 길이(초) (nullable)
```

**"녹음은 구글드라이브에"가 처음부터 설계돼 있었다**(D2와 정확히 일치). 세 컬럼 모두 현재 **읽는 코드도 쓰는 코드도 0곳**.

**② CRM 5축 프롬프트는 이미 회의노트 본문을 먹을 수 있다.**
`meeting-extract.v1.ts`가 `ExtractSourceKind = 'meeting' | 'note'` 두 어투를 갖는다 → **새 프롬프트 불필요.**

**③ 두 AI가 같은 것을 두 번 뽑는다.**
참석자(`attendees` ↔ `WHO`) · 할 일(`tasks` ↔ `NEXT`)이 완전 중복이고, 근거 계약도 다르다
(`source_quote` 문자열 vs `evidence{segmentIds[], quote}`).

## 2. 원칙 — 원본은 하나, 쓰임은 둘

> **"무슨 회의였나"** = 제목·시각·참석자·본문·전사·오디오 → **회의노트가 원본(SSOT)**
> **"그걸로 뭘 하나"** = 사내 반영(일일업무·캘린더) / 영업 반영(회사·딜·제안) → **각자**

`crm_meeting`은 지우지 않는다. **영업 문맥을 담는 그릇**으로 남는다(회사·딜 연결, 5축 실행 이력, 제안 근거, 활동 타임라인).
다만 원본을 자기가 갖지 않고 회의노트를 가리킨다.

## 3. 연결 — "발행", 세 방향

**방향 A · 회의노트 → CRM**
```
회의노트 상세 → [영업 CRM에 올리기] → 회사·딜 고르기
   → POST /api/crm/meetings/from-note { noteId, companyId, dealId }
        · crm_meeting 생성 — title·startedAt·location 복사, note_id 저장
        · 전사 스냅샷을 crm_transcript_segment 로 복사
        · 요약·결정사항도 스냅샷 → summaryMd (F-1 해소)
```

**방향 B · CRM에서 만들면 회의노트가 함께 생긴다** — **D5 확정: 예**
```
CRM 캡처 화면에서 녹음/파일/붙여넣기 시작
   → meeting_notes 행 생성 (user_id = 만든 사람, status='draft', visibility='crm')
   → crm_meeting 생성 + note_id 연결
```
`status='draft'`로 만들어 개인 회의노트 목록을 어지럽히지 않는다.

**방향 C · 이미 쓴 노트 가져오기** — CRM 캡처 화면의 네 번째 입구 `[📓 회의노트에서 가져오기]`

### 3-1. 왜 참조가 아니라 스냅샷인가

| 참조만 한다면 | 스냅샷을 두면 |
|---|---|
| 개인이 노트를 지우면 **팀의 영업 기록이 사라진다** | 팀 기록은 남는다 |
| 인박스 제안의 근거(`segmentId`)가 **원본 편집으로 깨진다** | 발행 시점이 보존돼 근거가 유지된다 |
| 워크스페이스 격리와 개인 소유 RLS를 **넘나드는 조회**가 생긴다 | 각자 자기 경계 안에서만 읽는다 |

이 저장소는 같은 개념을 주간보고 `weekly_report_snapshots`에서 이미 쓴다.

### 3-2. 어긋남을 숨기지 않는다

`crm_meeting.note_synced_at`보다 노트의 `updated_at`이 크면 CRM에 배지 —
**"원본이 그 뒤 수정됐어요 · 다시 가져오기"**. 다시 가져오면 새 스냅샷 + 새 5축 run,
이전 PENDING 제안은 `EXPIRED`(사람이 판단한 ACCEPTED·REJECTED는 안 건드린다 — 기존 규칙 재사용).
**CRM 쪽에서 전사를 고치지 않는다** — 원본은 노트다. 고치려면 노트로 가는 버튼을 준다.

## 4. 공개 범위 — 설정으로 (D6)

> D6 원문: *"그건 설정으로 하면 되는데 미팅에서 생성하면 기본으로 공개이고 수정 할 수 있음 되지 나만보기 라던지"*

**`meeting_notes.visibility` 컬럼을 추가한다**(추가 전용).

| 값 | 누가 읽나 | 언제 기본값이 되나 |
|---|---|---|
| `private` | 본인 + admin (**지금 RLS 그대로**) | **회의노트에서 만들 때** |
| `crm` | 본인 + admin + **연결된 CRM 워크스페이스 멤버** | **CRM 미팅에서 만들 때**(방향 B) |

- **언제든 바꿀 수 있다.** 상세 화면 상단에 공개 범위 선택 — `공개 (영업팀이 봄)` ↔ `나만 보기`
- **읽기 공개이지 편집 공개가 아니다.** `UPDATE`·`DELETE`는 여전히 **본인만**. 화면 문구도 그렇게 쓴다.
- **RLS는 확장만 한다.** 기존 SELECT 정책(본인 OR admin)을 그대로 두고 `OR (visibility='crm' AND 같은 워크스페이스 CRM 멤버)`를 덧붙인다.
  마이그 117이 이미 *"확장지점: … 조건을 OR로 추가"*라고 적어 둔 자리다.
- **`private`인데 CRM에 발행된 경우**: CRM 화면은 **자기 스냅샷만** 보여주고 `[회의노트 열기]`는 안 그린다.
  즉 **발행해도 원본을 안 열어 줄 수 있다** — 스냅샷 구조라 가능한 일이다.
- 나중에 `dept`(부서 공개)를 더할 자리를 남긴다. `check` 제약에 값을 추가하는 것으로 끝난다.

## 5. 녹음 → 전사 → 정리 (D7)

### 5-0. 타이밍 계약 — 전사는 자동, 분석은 버튼

> D7 원문: *"녹음 끝나자마자 전사 작업은 시작하고, AI 분석은 버튼으로 누르게"*

```
녹음 중  ─ 10분 구간이 닫힐 때마다 ─→ 업로드 → 전사   (사용자 개입 0)
[■ 종료] ─→ 마지막 구간 업로드 → 전사 → 전사 전문이 화면에 뜬다
                                        ↓
                            [ ✨ AI로 정리하기 ]      ← 사람이 누른다
                                        ↓
                       요약 · 결정사항 · 할 일 · (연결됐으면) 5축
```

**왜 전사는 자동인가** — 전사는 기계적 변환이고 사람이 확인할 것이 없다. 안 해 두면 다음 단계가 아예 막힌다.
**왜 분석은 버튼인가** — 셋 다다.
① 사용자가 **전사를 먼저 훑고 잘못 들린 곳을 고칠 수 있다**(고친 뒤 분석해야 결과가 맞는다)
② 전사는 길어서 분석 비용이 크다 — 안 볼 회의까지 자동으로 돌릴 이유가 없다
③ 사용자 지시

**기존 타이핑 경로는 안 건드린다.** 회의노트는 v0.7.257에서 *"저장 시 자동 분석 + 헤더 버튼"*으로 확정했다.
타이핑한 본문은 짧고 방금 사람이 쓴 것이라 자동이 자연스럽다. **녹음 경로만 버튼**이고, 이 차이를 화면이 설명한다.

### 5-1. 녹음 — 그냥 브라우저 녹음 (D7: "녹음 자체는 그냥 녹음")

특별한 인프라가 없다. `MediaRecorder` 하나다.

```
audio/webm;codecs=opus (없으면 audio/mp4 — Safari) · mono · 32kbps
→ 60분 ≈ 14MB · 10분 구간 ≈ 2~3MB
PART_MS = 10분마다 recorder.stop() → 새 recorder.start()
```

**왜 `timeslice`가 아니라 레코더 회전인가**: `timeslice` 조각은 **첫 조각에만 헤더가 있어** 단독 전사가 불가능하다.
레코더를 다시 시작하면 구간마다 완결된 파일이 나온다. 그래서 얻는 것 넷:

1. **회의 중에 구간 1~5가 이미 전사까지 끝난다** → 종료 후 대기가 거의 없다
2. 브라우저가 죽어도 올라간 구간은 남는다 (최대 유실 = 마지막 10분 미만)
3. "3/6 구간 전사됨"을 정직하게 말할 수 있다
4. 업로드 한 건이 **2~3MB라 Vercel 본문 4.5MB 한도 안** → 서명 URL 없이 서버 경유로 단순하게

전체 파일을 한 번에 올리는 입구(회의실 녹음기 파일 등)는 브라우저에서 10분씩 잘라 올린다
(`decodeAudioData` — `lib/ci/production/video-analyze.ts`가 이미 쓰는 WebAudio 기법).

D3에 따라 **녹음 고지 문구는 없다.** 다만 마이크 권한 거부·iframe·비보안 컨텍스트 진단은
`/lead-intake`의 `envWarn` 패턴을 재사용한다 — 그건 고지가 아니라 **실패 원인 안내**다.
D4에 따라 **모바일 최적화·`wakeLock`은 2차**로 미룬다.

### 5-2. 보관 — 우리 구글드라이브 (D2)

`lib/google-drive.ts`에 필요한 게 전부 있다. **새로 만들지 않는다.**
연결은 **조직 계정 1개**(`oauth_tokens` · `maybeSingle()`) — D2가 가리키는 "우리 설정된 구글드라이브"가 이것이다.

| 이미 있는 함수 | 용도 |
|---|---|
| `refreshTokenIfNeeded()` | 토큰 자동 갱신 |
| `ensureFolder(name, parentId)` | `AX사업본부 / 회의녹음 / 2026-08` |
| `uploadFile(buf, name, mime, folderId)` | 업로드 → `fileId` |
| `streamFile(fileId)` | 다운로드 — **전사가 여기서 받는다** |
| `getDriveConnectionStatus()` | 끊겼을 때 화면이 말할 수 있다 |

**자동삭제**
- **전사에 성공한 구간의 오디오만** 지운다. 실패한 것은 남긴다 — 안 그러면 재시도가 불가능해진다.
- 기본 **30일**, 설정으로 변경 가능(`meeting.audio_retention_days`).
- `drive_file_id`를 지우지 않고 `audio_deleted_at`을 찍는다 — 그래야 *"왜 재생이 안 되지"*에 답할 수 있다.
- 잡 `/api/meeting-notes/jobs/audio-purge`(일 1회) — `machine-auth.ts` SSOT 사용.
- 화면 문구: *"녹음 파일은 30일 뒤 지워집니다. 전사와 요약은 남습니다."*

### 5-3. 전사 — 오픈소스 모델, GPU 없이 (D1 + D7)

#### 조사 ① 어떤 오픈소스 모델이 가장 정확한가

2026년 Open ASR Leaderboard 상위권 (실측 조회 2026-08-22):

| 모델 | WER | 언어 | 라이선스 | 크기 | 한국어 |
|---|---|---|---|---|---|
| ARK-ASR-3B | 5.04% | 미명시 | Apache-2.0 | 3B | ? |
| Granite Speech 4.1 2B | 5.33% | **6** | Apache-2.0 | 2B | ✗ |
| Cohere Transcribe | 5.42% | **14** | Apache-2.0 | 2B | ? |
| Canary-Qwen-2.5B | 5.63% | **영어 전용** | CC-BY-4.0 | 2.5B | ✗ |
| Qwen3-ASR-1.7B | 5.76% | **52** | Apache-2.0 | 1.7B | 가능성 높음 |
| Parakeet TDT 0.6B v3 | 6.32% | 25 (유럽어) | CC-BY-4.0 | 0.6B | ✗ |
| MOSS-Transcribe-preview-2B | — | **50+** | Apache-2.0 | 2B | 가능성 높음 |
| Meta Omnilingual ASR | 다양 | **1,600+** | Apache-2.0 | 0.3~7B | ✓ |
| **Whisper large-v3** | — | **99** | **MIT** | 1.55B | **✓ 명시 지원** |

**핵심**: 리더보드 상위는 **전부 영어 벤치마크**이고, 한국어를 명시적으로 지원하면서
런타임·생태계가 갖춰진 것은 **Whisper large-v3**다. 한국어 WER은 공개 자료 기준 **5~10%** 수준.
업계 정리도 같다 — *"정확도로는 10여 개 모델에 추월당했지만, 다국어에서는 여전히 올바른 기본값"*.

> **`turbo`가 아니라 `large-v3`(full)를 쓴다.** turbo는 6배 빠르지만 정확도가 1~2%p 떨어진다.
> 비용 차이는 60분 회의 하나에 **55원 vs 150원** — D7이 "매우 정확한"을 강조했으므로 **95원으로 정확도를 산다.**

#### 조사 ② GPU 없이 어디서 돌리나

**Groq 서버리스** — 오픈소스 모델(whisper-large-v3)을 남의 GPU에서 돌린다. 우리가 살 것도 운영할 것도 없다.

| 항목 | 값 |
|---|---|
| 속도 | **1시간 오디오 → 약 15초** (10분 구간이면 3초 미만) |
| 비용 | large-v3 **$0.111/시간** · turbo $0.04/시간 (OpenAI Whisper API 대비 89% 저렴) |
| 파일 한도 | **100MB**(유료) — 우리 구간은 2~3MB라 여유 |
| 언어 | 99개 언어, **한국어 포함** |
| 데이터 | **기본 미보존 · 학습에 안 씀** · Zero Data Retention 자체 설정 가능 |

**실감 비용**: 60분 회의 ≈ **150원**. 하루 5건 × 22일 = **월 약 1만 6천원.**

**대안 어댑터**(같은 인터페이스로 언제든 교체)

| 경로 | 장점 | 단점 |
|---|---|---|
| **Groq**(권고) | 인프라 0 · 15초 · 매우 저렴 · 데이터 미보존 | 오디오가 외부로 나간다 |
| OpenRouter | 3개 프로바이더 자동 failover · 더 저렴($0.0288/시간) | 경로가 한 겹 더 |
| 사내 1대(`whisper.cpp`) | **오디오가 사내를 안 떠난다** · 완전 무료 | CPU면 60분 ≈ 30~60분 |
| 브라우저(`transformers.js`) | 기기를 안 떠남 · 비용 0 | 브라우저에 올릴 수 있는 모델은 작아 **정확도가 떨어진다** — D7의 "매우 정확한"과 충돌 |

**브라우저 전사는 하지 않는다.** ① 정확도 요구와 충돌 ② D2로 오디오가 어차피 드라이브로 간다
③ **탭을 닫는 순간 남은 구간이 영원히 안 된다** — "자리를 떠도 끝나 있다"가 이 기능의 핵심 가치다.

#### 구현 형태

- CRM의 `SttAdapter` 인터페이스를 **공용으로 올린다**(`lib/crm/stt` → `lib/stt`). 회의노트와 CRM이 같은 어댑터를 쓴다.
- `groqWhisperAdapter()`를 **추가**한다. `sttAdapterFor()`가 안 붙은 업체에 대해
  **조용히 mock으로 안 떨어지고 사실을 말하는** 기존 원칙은 그대로.
- **키는 호스트 시스템 설정 → 통합에 둔다** (`org_content` META: `stt_provider` · `stt_api_key` · `stt_model`).
  화면은 `IntegrationCard` + `LABEL` 상수 재사용(§2-5), 모델 선택은 `ModelSelectField`/`ModelPickerModal`(지시 #125).
  → CRM `PLANNED_SETTINGS`의 `stt.vendor`·`stt.api_key`는 **승격하지 않고 제거**한다.
  CRM은 키를 갖지 않는다는 기존 원칙과 일치하고, 회의노트(사내)도 같은 키를 쓴다.
- **이전 구간의 마지막 몇 줄과 확정된 화자 목록을 프롬프트에 함께 준다** → 구간이 바뀌어도 화자 이름이 이어진다.

#### 잡 — 기존 크론 드레인 패턴 그대로

```
POST/GET /api/meeting-notes/jobs/transcribe    ← machine-auth.ts SSOT
   maxDuration = 300 · DEADLINE_MS = 270_000
   ① UPLOADED 구간을 락 걸고 집는다 (TRANSCRIBING 전이)
   ② Drive streamFile → Groq → 세그먼트 저장 (start_ms += partIdx × 10분)
   ③ 마지막 구간까지 TRANSCRIBED 면 → 화면에 [✨ AI로 정리하기] 버튼 활성화
   실패: retryCount++ , 3회 초과 FAILED + error 기록
```

- `vercel.json` crons에 `*/2 * * * *` 추가 + **업로드 완료 API가 드레인을 1회 킥**(fire-and-forget).
  `analyze-drain`이 이미 같은 이중 구조다.

┌ 이 회의 ────────────────────────────────────────────────┐

│ 👁 공개 (영업팀이 봄) ▾        ← D6 공개 범위 선택        │

└──────────────────────────────────────────────────────────┘
┌ 회의 내용 ──────── [정제본 | 원본 | 전사] ──────────────┐  ← '전사' 탭만 추가
│  ┌ 녹음 ───────────────────────────────────────────┐    │  ← 새 블록
│  │ [🎙 녹음 시작]   또는   [📎 녹음 파일 올리기]    │    │
│  │ 12:34  ▁▂▅▇▅▂▁   구간1 ✅ 구간2 ✅ 구간3 ⏺      │    │

## 7. AI 중복 — 1차는 입력만 통일

- 두 AI가 **같은 원본**(회의노트 본문 + 전사 세그먼트)을 읽게 한다. 이것만으로 지시는 달성된다.
- **프롬프트는 안 건드린다.** 회의노트 AI는 v0.7.571에서 막 고쳐 지금 잘 돌고 있다 —
  여기를 건드리면 **두 화면이 동시에 회귀 위험**에 들어간다.
- 중복 반영 방지: CRM 인박스의 `NEXT` 제안 카드에 한 줄 —
  *"이 회의는 회의노트에서도 할 일 N건을 뽑았습니다"* + 노트 링크. **자동 판정은 안 한다**(제목 대조는 틀린다).
- **2차(별도 기획)**: 프롬프트를 합쳐 한 번에
  `{ summary, decisions, attendees, tasks, events, highlights, five_axis? }`. 근거 계약을 하나로 통일하고
  `five_axis`는 CRM에 연결된 회의에서만 요청한다.

**F-1(죽은 요약 배선)은 1차에서 해소된다.** CRM `summaryMd`는 노트의 `summary`+`decisions`를 발행 시 스냅샷으로 받는다.
따로 만들 필요가 없다. 그 순간 목록 배지·딜/회사 배지·CSV·단계 점검 AI·다음 행동 AI·상세 **6개 경로가 살아난다.**
`wired.test.ts`에 등재해 재발을 막는다.

## 10. 검증 (E-1 ~ E-6) — 브라우저 판정은 G3에 요청

### 정상 경로
1. 회의노트를 쓰고 `[영업 CRM에 올리기]` → 회사·딜 선택 → CRM 미팅이 생긴다
2. CRM 미팅 상세에 **노트 본문·요약·결정사항**이 보이고 `[열기]`로 노트로 간다
3. 인박스에 5축 제안 → 수락 → **목록 배지가 '정리됨'으로 바뀐다**(F-1이 살아난 증거)
4. 노트를 수정 → CRM에 **"원본이 그 뒤 수정됨"** → `[다시 가져오기]` → 새 제안, 옛 PENDING 만료
5. CRM에서 새 미팅 → **회의노트에도 생기고 `visibility='crm'`** (D5·D6)
6. 회의노트 상세에서 **공개 → 나만 보기**로 바꾼다 → CRM에서 `[회의노트 열기]`가 사라진다(스냅샷은 남는다)
7. 녹음 → 구간이 Drive에 쌓인다 → **종료 후 약 10초 뒤 전사** → `[✨ AI로 정리하기]` 누름 → 요약·5축

### 예외 (전부 밟는다)
마이크 권한 거부 · 마이크 없음 · 비보안 컨텍스트 · 녹음 중 새로고침 · 1초 무음 녹음 ·
지원 안 하는 파일 · 100MB 초과 · **Drive 연결 끊김**(토큰 만료·용량 초과) · **STT 키 미등록** ·
Groq 429/타임아웃 · 구간 3개 중 1개만 실패 · 발행 두 번(멱등) · 노트 삭제 후 CRM 미팅 열기 ·
**남의 회의노트 id로 발행 시도**(403) · **`private` 노트를 남이 CRM에서 열기 시도**(403) ·
빈 본문으로 AI 정리 · 회사·딜 없이 발행

### 한국어 정확도 확인 (D1 후속)
실제 우리 회의 녹음 **3건**으로 `whisper-large-v3` vs `turbo`를 재고,
**고유명사·숫자·회사명 오류를 세어** 모델을 고정한다. 공개 벤치마크 수치를 그대로 쓰지 않는다.
같은 표본으로 `Qwen3-ASR`·`MOSS-Transcribe`도 한 번 재 본다 — 더 나으면 어댑터만 바꾸면 된다.
