# 리드 큐 재기획 — "1,500개를 하나씩"이 왜 생겼고 어떻게 없애나

작성 2026-08-17 · 대상 v0.7.539 · 조사: 운영 DB 실측 + 코드 전수 + 실브라우저
**구현하지 않았다. 이 문서는 분석과 기획이다.**

---

## 0. 결론 한 줄

> 지적 두 개는 **같은 문제 하나**다.
> 회사의 영업 자산 378곳이 **아무도 통과할 수 없는 큐 안에 갇혀 있고**,
> 그래서 CRM의 모든 새 화면이 빈 화면으로 렌더된다.
>
> 그리고 그 큐의 1,514건 중 **1,136건은 같은 내용을 네 번 복사한 것**이다.
> 사람이 하나씩 볼 일이 애초에 없었다.

숫자 하나로 요약하면 이렇다.

| | |
|---|---|
| 인박스가 남았다고 말하는 건수 | **1,514** |
| 그중 실제 원본 | **378** (사본 1,136건 = 75%) |
| 사람이 판단할 가치가 있는 것 | **86** |
| 화면이 실제로 도달할 수 있는 것 | **20** (페이지 없음·건너뛰기 없음) |

---

## 1. "나아진 게 없다" — 왜 그렇게 보이는가

지난 판에서 새로 만든 것은 실재한다. `오늘` 화면, 알림 종, `Cmd+K`, 딜 카드의 다음 할 일,
멈춘 딜 AI 제안, 들여오기, 단계 CRUD. 코드에 있고 라우트도 산다.

**그런데 전부 "데이터를 보여 주는 화면"이다.** 그리고 볼 데이터가 없다.

실측 (2026-08-17 운영 DB):

| 테이블 | 건수 |
|---|---|
| `crm_deal` | **2** |
| `crm_company` | **14** |
| `crm_person` | **4** |
| `crm_task` | 14 |
| `crm_meeting` | 11 |

`/crm/today`를 실제로 열어 읽은 문구 그대로다.

```
김도현님, 급한 건 다 처리하셨어요.
지금 볼 게 없어요
진행 중인 딜 1건 · 13곳이 등록돼 있어요
```

**딜 1건짜리 CRM에서는 어떤 기능을 더 붙여도 화면이 달라지지 않는다.**
파이프라인 예상 매출도, 멈춘 딜 감지도, 단계 체류 시간도, 다음 할 일 자동 생성도
전부 딜이 수십 건 있을 때 의미가 생기는 장치다.

그리고 그 딜을 만들 재료 — 회사 378곳, 담당자, 금액, 수요 등급 — 은
**이미 시스템 안에 있다.** `lead_intakes`에 1,514행으로 들어와 있고,
5월 26일부터 82일째 큐에 갇혀 한 발짝도 못 나왔다.

> **그래서 "나아진 게 없다"는 정확한 관찰이다.**
> 개선은 전부 파이프라인 *하류*에 했는데, 막힌 곳은 *상류*였다.

## 2. 인박스 1,514건 해부 — 전부 실측

### 2-1. 4분의 3이 사본이다

```
pending 총건수            1,514
고유 bulk_import_row        378   ← 엑셀 원본의 행 번호
```

같은 회사의 4행을 꺼내 비교하면 **완전히 동일하다.**

```
(주)탈로스 · 4행
  10:13:03  bulk_import_row 275  fit 55  tackeun.kim@taloscorp.io
  10:13:16  bulk_import_row 275  fit 55  tackeun.kim@taloscorp.io
  11:43:57  bulk_import_row 275  fit 55  tackeun.kim@taloscorp.io
  11:43:57  bulk_import_row 275  fit 55  tackeun.kim@taloscorp.io
```

회사당 행 수 분포도 이 사실을 그대로 말한다.

| 회사당 행 수 | 회사 수 | 리드 수 |
|---|---|---|
| 4~6건 | **376** | 1,506 |
| 2~3건 | 2 | 6 |

**원인**: 2026-05-26 엑셀 대량 들여오기가 **네 번 실행**됐고,
`lead_intakes`에 멱등키가 없다. `\d lead_intakes` 확인 결과 유니크 제약은 `id`(PK) 하나뿐이다.
`(user_id, source, bulk_import_row)` 유니크가 없으므로 **다음 엑셀에서도 똑같이 배수가 된다.**

### 2-2. 화면이 도달할 수 있는 것은 20건뿐이다

`app/api/crm/lead-import/route.ts`가 받는 쿼리 파라미터는 `limit` 하나다.
**`offset`도 커서도 없다.** UI는 파라미터 없이 부르므로 언제나 `limit=20`.

그리고 카드의 액션은 두 개뿐이다 — `회사만 옮기기` / `딜까지 만들기`.
**건너뛰기·보관·제외가 없다.**

> 즉 마음에 안 드는 리드는 **영원히 목록 맨 위에 남는다.**
> 다음 20건을 보려면 지금 20건을 CRM에 집어넣는 수밖에 없다.
> 큐가 아니라 **막힌 관**이다.

### 2-3. 정렬이 주석과 다르다 — 그리고 하필 최악이 위로 온다

```ts
// 적합도가 높은 것부터 — 1,517건을 위에서부터 훑을 때 쓸모 있는 것이 먼저 나와야 한다
.order('created_at', { ascending: false })
```

주석은 적합도 순이라고 말하고, 코드는 생성 시각 순이다.
그런데 1,510건이 **전부 같은 날(2026-05-26) 생성**됐으므로 이 정렬은 사실상 무작위다.

실제 상위 20건을 API로 뽑아 본 결과:

| | |
|---|---|
| 고유 회사 | **10곳** (각 2벌씩 나란히 표시) |
| 적합도 | 전부 40~60 |
| 수요 강도 | 전부 `Low` |
| 금액 | 전부 없음 |

**적합도 70+ 86건은 화면에서 도달 불가능하다.**
사용자가 처음 만나는 20장은 하필 가장 가치 없는 20장이고, 그마저 절반이 중복이다.

### 2-4. 화면이 "다 옮겼어요"라고 말한다

실브라우저에서 `/crm/inbox`를 열고 시각별로 읽었다.

| 경과 | 화면 문구 | 진실 |
|---|---|---|
| 5초 | **다 옮겼어요** | 1,514건 남음 |
| 8초 | 1,514건 남음 | ✅ |

`LeadImport.tsx`의 초기 state가 `pending = 0`이고, 배지가
`pending === 0 ? '다 옮겼어요' : …`이라 **로딩 중에 완료를 주장한다.**
같은 병(로딩을 빈 상태로 렌더)이 이전 보고서 §병 D에도 있었고, 여기서 재발했다 —
이번엔 거짓말의 방향이 더 나쁘다. 사용자가 그 화면을 닫게 만든다.

### 2-5. 상태값이 실제와 어긋나 있다

```
status = 'crm_registered'  인데  crm_company_id·linked_account_id 둘 다 NULL   378건
옛 accounts 테이블 실제 건수                                                     12건
```

378건이 "CRM에 등록됨"이라고 자기를 표시하고 있는데 **연결된 레코드가 하나도 없다.**
그 상태값을 믿고 만든 어떤 판단도 틀린다.

### 2-6. 옛 화면도 똑같이 20건에 막혀 있다

`app/(member)/lead-intake/page.tsx` — `.order('created_at', desc).limit(20)`.
검색·필터·페이지 없음.

> **같은 1,514행 위에 화면이 둘 있는데, 둘 다 21번째 행에 도달할 수 없다.**

## 3. 진짜 원인 — 목록을 큐로 만들었다

여기까지의 결함은 전부 증상이다. 원인은 설계 판단 하나다.

| | 인박스(큐) | 리드(목록) |
|---|---|---|
| 성격 | **비워야 하는 것** | **찾아 쓰는 것** |
| 성공 | 0건 | 필요할 때 원하는 걸 찾음 |
| 정렬 | 도착순 | 관련도순 |
| 안 고른 것 | 남는다(압박) | 그냥 있는다 |
| 예 | 승인 대기, 결재 | 주소록, 카탈로그 |

**리드 1,514건은 목록이다. 그런데 인박스 안에, 진척 배지(`1,514건 남음`)와 함께 넣었다.**

그 순간 세 가지가 자동으로 따라온다.

1. 전량 처리가 목표가 된다 → "1,500개를 하나씩" 이라는 일이 생긴다
2. 건너뛰기를 안 만들게 된다 → 큐는 비워야 하는 것이니 "안 함"이라는 선택지가 설계에 없다
3. 검색·필터를 안 만들게 된다 → 큐는 위에서부터 처리하는 것이니 찾을 이유가 없다

**지금 화면의 결함 세 개가 전부 이 판단 하나에서 나왔다.**
사용자가 "정신이 나간거야?"라고 한 것은 UI 비판이 아니라 **모델 오류를 정확히 짚은 것**이다.

## 4. 더 좋은 방법 — 재기획

### 원칙 4개

| | |
|---|---|
| **P1** | **사본은 사람에게 보여 주지 않는다.** 기계가 접을 수 있는 것을 사람에게 세게 하지 않는다 |
| **P2** | **전량 처리라는 목표를 없앤다.** 리드는 비우는 것이 아니라 꺼내 쓰는 것이다 |
| **P3** | **등급이 다르면 처리 방식이 다르다.** 86건과 225건에 같은 카드를 쓰지 않는다 |
| **P4** | **사람에게는 하루치만 준다.** 1,514도 378도 사람이 볼 숫자가 아니다 |

### 단계 1 — 사본을 접는다 (1,514 → 378)

- `(user_id, source, bulk_import_row)`가 같은 그룹의 **최초 1건만 대표**로 삼는다.
- 나머지 1,136건은 **지우지 않는다.** `superseded_by`(대표 행 id)를 채워 숨긴다 → 되돌릴 수 있다.
- 화면은 사실을 밝힌다: `사본 1,136건을 접었습니다 · 펼쳐 보기`.
- **재발을 같이 막는다**: `(user_id, source, bulk_import_row)` 부분 유니크 인덱스 +
  대량 들여오기를 `upsert`로 전환. 이걸 안 하면 다음 엑셀에서 또 배수가 된다.

> 되돌릴 수 없는 삭제가 아니라 표시이므로 **운영 데이터 승인 없이 진행 가능**하다(M-12).

### 단계 2 — 인박스에서 리드를 뺀다

`/crm/inbox`는 **AI 제안 확인 전용**으로 되돌린다(원래 용도이자 화면 설명 그대로).
리드는 **`/crm/leads`** 라는 자기 화면으로 나간다. 사이드바에서 `회사` 위.

이것만으로 "1,514건 남음"이라는 진척 배지가 사라진다 — **압박의 출처가 배지였다.**

### 단계 3 — `/crm/leads`는 표준 목록으로 만든다

호스트 §2-6 그대로. 새로 그리지 않는다.

```
useListQuery  (URL이 진실 — 공유·새로고침에 조건이 살아남는다)
ListToolbar   검색 · 필터 · 정렬 · 보기 · 선택 작업
ListSurface   ColumnDef 한 벌 (표/카드 동시)
ListPager     pages
```

**필터 축은 이미 데이터에 있다. 새로 만들 것이 없다.**

| 축 | 값 (실측 분포) |
|---|---|
| 세그먼트 | Mid-Market 1,381 · Enterprise 48 · 공공 46 · 파트너 12 · 스타트업 2 |
| 수요 강도 | High 412 · Medium 1,038 · Low 50 |
| 적합도 | 80+ 80 · 60–79 530 · 40–59 902 |
| 금액 | 있음 231 |
| 연락 가능 | 이메일 있음 1,374 |

- **정렬 기본값 = 적합도 DESC** (지금 코드 주석이 말하던 그대로. 코드만 그렇지 않았다)
- 행 클릭 → 리드 상세(원문 그대로 + 무엇이 만들어질지 미리보기)
- **행 액션 3개**: `영업으로 올리기` · `나중에`(스누즈) · `제외`(보관)
  → **안 고른 것도 처리가 된다.** 이게 없어서 큐가 막혔다.

### 단계 4 — 등급마다 다른 처리

원본 378건을 실측 기준으로 나눴다.

| 등급 | 기준 | 건수 | 평균 적합도 | 사람이 하는 일 |
|---|---|---|---|---|
| **A** | 금액 있음 또는 적합도 70+ | **86** | 77 | **하나씩 본다** |
| **B** | 수요 High | 31 | 68 | 묶음 승인 |
| **C** | 나머지 | 36 | 60 | 묶음 승인 |
| **D** | 설명이 `프로스펙트:` 상투구 | **225** | 55 | **옮기지 않는다** |

**D 225건을 회사로 등록하지 않는 이유**: 회사 목록이 14곳에서 239곳이 되고,
그중 225곳은 대화가 시작된 적 없는 이름이다. 그러면 이번엔 **회사 목록이 막힌다**.
지금 리드 큐가 겪는 일을 회사 목록에 옮겨 붙이는 셈이다.

> D는 검색 가능한 리드 목록에 그대로 둔다. 필요해지면 그때 한 건 올린다.
> **이것이 "전량 이관"을 버린다는 말의 실제 내용이다.**

### 단계 5 — 사람에게는 하루치만 준다

`/crm/today`에 카드 하나를 더한다.

```
새 리드 3건
  ㆍA등급 · 아직 아무도 연락 안 한 것 중 위에서 3건
  ㆍ각 카드: 회사 · 담당자 · 적합도 · 금액 · 근거 한 줄
  ㆍ[영업으로 올리기] [나중에] [제외]
  ㆍ3건 처리하면 다음 3건
```

A등급 86건 = **약 4주치**. 사용자는 1,514도 378도 86도 보지 않는다. **3을 본다.**

### 부수 수정 (같은 작업에 포함)

| | 무엇 |
|---|---|
| a | 로딩 중 `다 옮겼어요` 렌더 금지 — `loading`이면 배지 자체를 숨긴다 |
| b | `status='crm_registered'` 378건 정합성 정리 — 연결이 없으면 그 상태를 주장하지 않는다 |
| c | 옛 `/lead-intake` 화면을 `/crm/leads`로 일원화 (같은 데이터 위 화면 2개 = §2-6 그 자체) |
| d | 이관 후 `load()` 전체 재조회 → 옮긴 행만 목록에서 제거 |

## 5. 무엇이 달라지나

| | 지금 | 재기획 후 |
|---|---|---|
| 화면이 말하는 남은 건수 | 1,514 | **378** (사본 접음) |
| 사람이 도달 가능한 건수 | **20** | 378 전부 (검색·필터·페이지) |
| 사람의 개별 판단 횟수 | 1,514 (실제로는 불가) | **86** |
| 묶음 결정 | 없음 | 2회 (B·C) |
| 안 고른 리드 | 큐에 영원히 남음 | 스누즈·보관으로 빠짐 |
| 상위 20건 품질 | 적합도 40–60·수요 Low·절반 중복 | 적합도 순 상위 |
| 하루에 마주하는 숫자 | 1,514 | **3** |
| 파이프라인 재료 | 갇힘 | A 86건이 딜로 흐름 |

그리고 **`오늘`·딜 보드·예상 매출·멈춘 딜·체류 시간이 전부 비로소 켜진다** —
그 화면들이 안 켜졌던 이유가 딜 2건이었기 때문이다.

## 6. 구현 순서 (승인 대기 — 착수하지 않음)

| # | 무엇 | 되돌릴 수 있나 | 승인 |
|---|---|---|---|
| 1 | 사본 접기 마이그레이션 (`superseded_by` 표시) + 멱등 유니크 인덱스 | ✅ 표시만 | **운영 DB 변경 — 필요** |
| 2 | `/crm/leads` 표준 목록 신설 + 인박스에서 리드 분리 | ✅ | 불요 |
| 3 | 등급 판정 SSOT (`lib/crm/domain/lead-grade.ts`) + 3액션(올리기·나중에·제외) | ✅ | 불요 |
| 4 | `오늘`에 `새 리드 3건` 카드 | ✅ | 불요 |
| 5 | 부수 수정 a~d | ✅ | 불요 |

1번만 사용자 승인이 필요하다. 2~5는 되돌릴 수 있는 형태라 승인 없이 갈 수 있다.

## 7. 결정이 필요한 것 — 사용자만 아는 사실

| | 질문 | 왜 물어야 하나 |
|---|---|---|
| **Q1** | 그 엑셀 378곳은 **실제 영업 대상 명단**인가, 아니면 수집한 후보 리스트인가 | 실제 명단이면 D 225건도 회사로 올려야 한다. 후보 리스트면 지금 안이 맞다 |
| **Q2** | 등급 A 기준을 **금액 있음 or 적합도 70+**(86건)로 잡았다. 더 좁혀도 되나 | 86건 = 4주치. 2주치를 원하면 적합도 80+(80건 중 원본 기준)로 좁힌다 |
| **Q3** | 사본 1,136건을 **표시로 숨김**으로 할지 **물리 삭제**할지 | 표시 숨김을 권한다(되돌릴 수 있음). 삭제를 원하면 별도 승인 |

**부록 — 실측 재현 방법**

```sql
-- 사본 비율
select count(*) 전체, count(distinct parsed_data->>'bulk_import_row') 원본
from lead_intakes where crm_migrated_at is null;

-- 등급 분포
with u as (
  select distinct on (parsed_data->>'bulk_import_row')
    coalesce((parsed_data->>'fit_score')::int,0) fit,
    coalesce((parsed_data->>'deal_value_billion')::numeric,0) amt,
    trim(coalesce(parsed_data->>'gpu_demand_intensity','')) dem,
    trim(coalesce(parsed_data->>'deal_description','')) dsc
  from lead_intakes
  where crm_migrated_at is null and parsed_data->>'bulk_import_row' is not null
  order by parsed_data->>'bulk_import_row', created_at
)
select case when amt>0 or fit>=70 then 'A' when dem='High' then 'B'
            when dsc like '프로스펙트%' then 'D' else 'C' end, count(*)
from u group by 1 order by 1;
```
