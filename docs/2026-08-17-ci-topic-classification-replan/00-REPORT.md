# 수집함이 전부 "요리"인 이유와 주제 분류 재설계

작성 2026-08-17 · 대상 `/ci/inbox` 주제 분류 · **기획 문서(구현 없음)**

---

## 0. 질문에 먼저 답한다

> **"이거 하드코딩 된거니? AI가 분석한거니?"**

**둘 다 아닙니다. 세 번째 답이 있습니다.**

`apps/web/lib/ci/analysis/classify.ts:83-90`에 이런 조항이 있습니다.

```ts
// 주제가 딱 하나뿐인 워크스페이스라면 그것으로 본다 — 콜드 스타트 구간 배려
if (input.topics.length === 1) {
  return {
    topicId: input.topics[0].id,
    confidence: 0.55,
    source: 'auto',
    reason: '워크스페이스에 주제가 하나뿐이라 그것으로 두었습니다',
  }
}
```

이 워크스페이스에 등록된 주제는 **"요리" 하나뿐**입니다. 그래서 제목에 "요리"라는 글자가 없어도, 그 영상이 싸이의 강남스타일이어도, **주제가 하나뿐이라는 이유만으로** 요리가 됩니다.

DB 실측이 이를 그대로 증명합니다.

| topic_source | confidence | 건수 | 무엇인가 |
|---|---|---|---|
| auto | **0.550** | **305** | ← 위 조항이 찍은 것. 아무것도 판단하지 않았다 |
| ai_verified | 0.80~1.00 | 15 | AI가 봤지만 고를 주제가 "요리"뿐이었다 |
| auto | 0.700 | 1 | 제목에 실제로 "요리" 글자가 있었다 |

**320건 중 305건은 판정이 아니라 기본값입니다.** 나머지 15건은 AI가 판정했지만, 후보 목록에 "요리" 하나만 넣고 물었으니 AI도 요리라고 답할 수밖에 없었습니다.

## 1. "웹서치 조금만 해도 알 만한 것" — 지적이 정확합니다. 실은 더 심합니다

웹서치까지 갈 것도 없습니다. **필요한 정보는 이미 우리 DB 안에 있거나, YouTube가 공짜로 주고 있는데 안 읽고 있습니다.**

### 1-1. 채널 설명은 이미 수집해 놓고 분류에 안 씁니다

`ci_channels.description` 컬럼에 이미 들어 있는 값입니다.

| 채널 | DB에 이미 있는 설명 |
|---|---|
| LuisFonsiVEVO | `Luis Fonsi en Vevo – Videoclips oficiales, Lyric videos, Sesiones en vivo…` |
| officialpsy | `PSY Official YouTube Channel` |
| 추성훈 ChooSungHoon | `유튭 신입 아조씨임다. 추성훈의 여생 잘 부탁드림니다.` |

그런데 분류 코드(`lib/ci/jobs/stages.ts:123`)가 읽는 것은 이것뿐입니다.

```ts
.select('id, title, caption, topic_id, topic_source, ci_channels ( topic_id )')
//                                                   ^^^^^^^^^^^^^^^^^^^^^^
//                          채널에서 topic_id만 가져온다. description도 이름도 안 본다.
```

"Videoclips oficiales"라고 스페인어로 써 있는 채널을 요리로 분류한 이유는, **그 문장을 아예 읽지 않았기** 때문입니다.

### 1-2. YouTube가 주제를 구조화해서 주는데 요청조차 안 합니다

`lib/ci/connectors/youtube.ts:101`의 API 호출입니다.

```ts
`${API_BASE}/videos?part=snippet,contentDetails,statistics&id=...`
//                       ^ topicDetails가 없다
```

같은 API에 `topicDetails`를 한 단어 추가하면 무엇이 오는지, **실제로 호출해서 확인했습니다.**

| 영상 | categoryId | tags | topicCategories |
|---|---|---|---|
| 파퀴아오 600억 집공개 | 22 (인물·블로그) | 추성훈, 야노시호, 유도, **ufc** | **Boxing, Lifestyle** |
| 진심을 담아 말씀드립니다 | 22 | 〃 | **Sport** |
| 박진영 편의점 먹방 | 22 | 〃 | **Food, Lifestyle** |

YouTube는 이미 "이건 스포츠·격투기 출신자의 라이프스타일 채널이고, 이 영상은 음식이다"라고 **구조화된 데이터로 말해주고 있었습니다.** 시스템은 이걸 한 글자도 요청하지 않고, 사용자가 손으로 만든 "요리" 하나에 텍스트 매칭을 시도하다 실패하자 310건을 사람에게 떠넘겼습니다.

## 3. 왜 이렇게 됐나 — 구조 원인 6가지

한 줄 버그가 아닙니다. 설계가 여섯 군데에서 같은 방향으로 기울어 있습니다.

### 원인 1. 콜드스타트 조항이 판정을 대체했다

`classify.ts:83` — "주제가 하나면 그것으로 본다"는 배려가, 주제가 하나인 동안 **모든 판정을 무력화**합니다. 배려가 아니라 우회로입니다.

### 원인 2. 두 단계 판정이 같은 것을 본다

설계는 "1차 규칙 → 2차 LLM"의 깔때기입니다. 그런데 **두 단계가 보는 입력이 제목+설명으로 동일**합니다. 같은 증거를 두 번 보면 두 번째는 첫 번째를 못 이깁니다. 실제로 15건의 AI 판정도 전부 "요리"였습니다.

### 원인 3. 후보가 하나면 AI를 불러도 의미가 없다

프롬프트에 후보 주제를 넣어주는데(`classify.ts:110`), 그 목록이 `["요리"]` 한 줄입니다. AI에게 "요리인가 아닌가"를 물으면서 정답지에 요리만 놓았습니다.

### 원인 4. 채널이라는 가장 강한 증거를 안 쓴다

`ci_channels.topic_id`는 **14개 채널 전부 NULL**입니다. 채널 귀속 경로(`confidence 0.6`)는 코드에 있으나 데이터가 없어 한 번도 작동하지 않았습니다. 채널을 채우는 화면도 자동 경로도 없습니다.

### 원인 5. 검토 단위가 콘텐츠다

임계값 0.85, 콜드스타트 경로 0.55 → **구조적으로 100% 미달**. 결과는 `pending 310 / 321 = 96.6%`.
확정 API는 `POST /api/ci/contents/[id]/topic` — **1건 단위뿐**입니다. 채널 묶어보기(`ChannelGroupedList`)는 있으나 묶어서 확정하는 기능은 없습니다.

> 게시물 1만 개면 클릭 1만 번입니다. 지적하신 그대로입니다.

### 원인 6. 근거를 저장은 하는데 화면에 안 보인다

`stages.ts:198`이 판정 시도 기록(`ai_attempts`)을 `ci_jobs.payload`에 남깁니다. 그런데 검토 목록이 보여주는 것은 **주제 셀렉트와 "55%" 숫자뿐**입니다.

**"이거 하드코딩이니 AI가 분석한 거니?"라는 질문 자체가, 화면이 근거를 감춘 결과입니다.** 시스템은 알고 있었는데 말하지 않았습니다.

## 4. 재설계 — 원칙 세 가지

### 원칙 1. 검토는 예외다. 지금은 규칙이 되어 있다

> "검토라는 건 정말 정말 난해하거나 구분이 어려울 때 하는 거야"

동의합니다. 그러려면 **판단을 포기하기 전에 볼 것을 다 봐야** 합니다. 지금은 제목 하나 보고 안 되면 바로 사람을 부릅니다.

### 원칙 2. 검토 단위는 콘텐츠가 아니라 채널이다

사람에게 물어야 할 질문은 이것입니다.

- ❌ "이 영상 주제 뭐예요?" × 10,000번
- ✅ "이 채널 뭐 하는 채널이에요?" × 10~50번

채널 하나를 확정하면 그 채널 콘텐츠 전량이 확정됩니다. 실측으로 **추성훈 1번 = 311건, VEVO 3번 = 8건**입니다.

### 원칙 3. 모르면 모른다고 한다

"미분류"는 실패가 아니라 정직입니다. 억지로 하나에 밀어 넣은 320건보다, "8건은 음악, 311건은 라이프스타일, 나머지는 아직 모름"이 훨씬 쓸모 있습니다.

## 5. 판정 사다리 — 각 단이 서로 다른 증거를 본다

현재는 2단이고 둘 다 같은 것을 봅니다. 새 사다리는 **단마다 증거가 다릅니다.**

| 단 | 무엇을 보는가 | 비용 | 처리 단위 | 신설 여부 |
|---|---|---|---|---|
| **L0** 플랫폼 신호 | `categoryId` · `topicDetails` · `tags` | 0 (수집 시 동봉) | 전건 | **신설** |
| **L1** 채널 정체성 | 채널 신호 집계 + `description` + 구독자·영상수 | 채널당 1회 | 채널 | **신설** |
| **L2** 콘텐츠 텍스트 | 제목·설명 규칙 매칭 | 0 | 전건 | 기존 |
| **L3** AI 판정 | **L0~L2를 전부 묶어서** 1회 | 채널당 1회 + 이탈분 | 소량 | 기존(입력 교체) |
| **L4** 사람 | 채널 단위 질문 1개 | 사람 | 채널 | 기존(단위 변경) |

### 각 단의 설계

**L0 — 플랫폼이 주는 것을 버리지 않는다**
- 수집 시 `part=snippet,contentDetails,statistics,topicDetails`로 한 단어 추가. **추가 쿼터 비용 없음**(같은 호출)
- `categoryId` · `topicCategories` · `tags`를 콘텐츠 행에 그대로 저장 (지금은 받고도 버림)
- 플랫폼별 신호 품질이 다르다: YouTube 풍부 / TikTok·Instagram 빈약 → 빈약한 플랫폼은 L1·L3 비중을 높인다

**L1 — 채널 정체성을 먼저 세운다 (핵심 신설)**
- 채널의 콘텐츠 신호를 집계해 "이 채널은 무엇인가"를 먼저 판정
- 일치도(최빈 카테고리 비율)를 함께 산출 → **100%면 자동 확정, 60% 미만이면 사람에게**
- 채널 설명·태그를 함께 본다. 여기서 웹검색이 실제로 유효한 자리다 — YouTube 신호가 결측인 77건(24%)이나 TikTok·Instagram처럼 API가 빈약한 플랫폼은 **채널 프로필 텍스트 + 공개 검색 결과**가 유일한 단서
- 결과를 `ci_channels.topic_id`에 기록 → 지금 전부 NULL인 필드가 처음으로 살아난다

**L2 — 텍스트 규칙 (기존 유지, 콜드스타트 조항만 삭제)**
- `classify.ts:83`의 `topics.length === 1` 조항 **삭제**. 주제가 하나뿐이면 "그것이 맞는지"를 판정해야지 "무조건 그것"이 아니다
- 주제가 0개인 상태도 정상으로 인정한다

**L3 — AI에게 제대로 물어본다**
- 지금: 제목 + 설명 + 주제이름목록
- 바꿈: 제목 + 설명 + **채널명 + 채널설명 + 채널태그 + 영상카테고리 + topicCategories** + 주제목록 + 정정사례
- 후보 주제가 1개 이하이면 AI를 부르지 않는다 (부를 이유가 없다)
- 호출 단위를 콘텐츠에서 **채널**로 올린다 → 1만 건이 아니라 채널 수만큼

**L4 — 사람은 채널만 본다**
- "이 채널은 이렇게 보입니다. 맞나요?" 한 화면에 채널 카드로
- 근거를 반드시 함께 보여준다 (아래 §7)

## 6. 1만 건일 때 실제로 무슨 일이 일어나는가

> "엄청난 건수를 (만약 채널에 1만개의 게시물이 있으면) 그걸 다 검토해? 사람이?"

### 지금

| | |
|---|---|
| 사람 클릭 | **9,660회** (96.6% pending) |
| LLM 호출 | 9,660회 (임계 미달 전건) |
| 결과 | 전부 같은 주제 |

### 재설계 후 (채널 1개 · 게시물 1만 건 가정)

| 단계 | 처리량 | 사람 | LLM |
|---|---|---|---|
| L0 플랫폼 신호 | 10,000건 | 0 | 0 |
| L1 채널 정체성 | 1채널 | 0 (일치도 100%면 자동) | 0 |
| L2 텍스트 규칙 | 10,000건 | 0 | 0 |
| 채널 주제 상속 | 10,000건 | 0 | 0 |
| **이탈 감지** | 순수 계산 | 0 | 0 |
| L3 AI (이탈분만) | 수십~수백건 | 0 | 수십~수백 |
| L4 사람 | **채널 1개** | **1회** | 0 |

**클릭 9,660회 → 1회.**

### 이탈 감지란

채널 주제가 정해지면 콘텐츠는 그것을 **상속**합니다. 개별 판정은 콘텐츠 신호가 채널 정체성과 **다를 때만** 합니다.

- 추성훈 채널의 Food 71건·Film 22건 → **이탈 아님.** 라이프스타일 채널의 정상 스펙트럼
- 만약 그 채널에 Music 영상이 하나 섞이면 → **이탈.** 이때만 개별 판정

이탈 판정은 집계 비교이므로 **LLM도 사람도 필요 없습니다.**

## 7. 지적하지 않으셨지만 같이 고쳐야 할 것

### 7-1. 주제 체계를 사용자가 맨손으로 만들게 두면 안 된다

지금 온보딩은 빈칸을 주고 "주제를 만드세요"라고 합니다. 사용자는 "요리" 하나를 넣고 끝냈고, 시스템은 그때부터 **세상을 요리 하나로** 봤습니다.

**바꿈:** 채널을 등록하면 시스템이 먼저 읽고 제안합니다.

> 채널 5개를 분석했습니다.
> **음악** 3채널 8건 · **먹방·여행·셀럽** 1채널 311건 · **기타** 1채널 1건
> 이대로 주제를 만들까요? [이름 수정] [만들기]

사용자는 **만드는 게 아니라 확인**합니다. 주제 체계가 데이터에서 올라옵니다.

### 7-2. 콘텐츠 하나에 주제 하나는 애초에 무리다

현재 스키마는 `ci_contents.topic_id` 단일 FK입니다. 그런데 추성훈 채널 한 개 안에 Entertainment 132 · Lifestyle 79 · Food 71 · Film 22가 섞여 있습니다.

**바꿈:** 주 주제 1 + 부 주제 N. 통계·비교는 주 주제로, 검색·필터는 부 주제까지.

### 7-3. 확신도를 숫자로 던지지 말고 세 구간으로 말한다

"55%"는 사용자에게 아무 의미가 없습니다.

| 구간 | 화면 표기 | 동작 |
|---|---|---|
| 확정 | (표시 없음) | 그냥 쓴다 |
| **추정** | `추정` 배지 + 근거 | 쓰되 통계 가중치를 낮춘다 |
| 미분류 | `미분류` | 쌓아 두고, 일정 수 넘으면 한 번에 묻는다 |

미분류를 검토 큐로 밀어 넣지 않습니다. **모르는 것은 모르는 채로 두는 것이 정상 상태**입니다.

### 7-4. 근거를 화면에 올린다 (이번 질문의 직접 원인)

`ai_attempts`는 이미 저장되고 있습니다. 목록에 한 줄만 보이면 됩니다.

> **먹방·여행** `추정`
> 채널 태그 `유도·ufc`, 영상 카테고리 `인물·블로그` 100%, 주제 신호 `Food·Lifestyle` — 그래서 이렇게 봤습니다.

이 한 줄이 있었으면 "하드코딩이니 AI니"를 물으실 일이 없었습니다.

### 7-5. 채널 중복 5쌍 — 별개 결함이지만 분류를 망친다

`ci_channels` 14행 중 **5쌍이 같은 채널의 중복**입니다.

| 채널 | 행 A | 행 B |
|---|---|---|
| 추성훈 | 메타 있음 (KR, 544영상, 설명 O) | **메타 없음** |
| officialpsy | 메타 있음 (218영상) | **메타 없음** |
| LuisFonsiVEVO | 693영상 | 692영상 |
| jawed / OneRepublicVEVO | 각 2행 | |

채널 단위 판정으로 가면 **중복 채널은 곧 판정 분열**입니다. UCM 채널 키 통합이 L1의 선행 조건입니다.

### 7-6. 정정 학습 루프가 한 번도 안 돌았다

`ci_corrections` **0건**. 설계상 사용자 정정이 다음 분류 프롬프트에 들어가게 되어 있는데(`loadCorrectionExamples`), 사용자가 310건 앞에서 손을 놓았으니 학습 재료가 0입니다.

**검토 부담을 낮추는 것이 곧 학습을 살리는 길입니다.** 채널 단위로 5번 확정하면 정정 5건이 즉시 쌓입니다.

### 7-7. 수집 편향 — 311 vs 나머지 9

한 채널이 97%입니다. 이 상태에서는 "평소 대비" 같은 비교 지표도 사실상 한 채널 내부 비교입니다. 채널 확보 전에는 비교 지표를 **표시하지 않거나 표본 부족을 명시**해야 합니다.

| 순서 | 내용 | 규모 | 효과 |

| **6** | L3 프롬프트 입력 교체 (채널 맥락 주입) | 프롬프트 | AI 판정 실질화 |

## 9. 한 줄 요약

> 시스템은 판단하지 않았습니다. **주제가 하나뿐이라 그 하나를 찍었고**, 확신이 없다는 이유로 96.6%를 사람에게 넘겼습니다. 그러면서 YouTube가 공짜로 주는 주제 신호도, 자기가 이미 저장해 둔 채널 설명도 읽지 않았습니다.
>
> 고칠 곳은 분류 알고리즘이 아니라 **"무엇을 보고 판단하는가"와 "누구에게 무엇을 묻는가"**입니다.
