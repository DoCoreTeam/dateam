# dacrm 전수 진단 + 재기획 보고서

작성 2026-08-17 · 대상 v0.7.538 · 조사 방법: 실브라우저 실측 + 코드 전수 + 운영 API 조회 + 외부 정설 조사
**구현하지 않았다. 이 문서는 분석과 기획이다.**

---

## 0. 결론 한 줄

> 지금 dacrm은 **데이터 모델은 제대로 된 CRM인데, 화면은 메뉴별 폼 모음**이다.
> 사용자의 직관("그냥 메뉴별로 폼만 낸 것 같다")이 정확하다.
> 그리고 그 병이 가장 날카롭게 드러난 곳이 하필 사용자가 물은 **영업 단계의 "안 봄 / 알려 줌 / 막음"**이다.

숫자 하나로 요약하면 이렇다.

| | |
|---|---|
| 영업 단계 화면의 토글 버튼 | **342개** (파이프라인 3 × 단계 19 × 조건 6 × 수준 3) |
| 그중 켜진 것 | **0개** |
| AI 자동 반영 설정 행 | 16개 → 켜진 것 **0개** |
| 자동화 규칙 | **0개** |

즉 사용자가 본 화면은 **아무 일도 하지 않는 342개의 스위치**였다.
"뭐가 어떻게 되는지 모르겠다"의 정답은 — **아무것도 안 된다**.

---

## 1. "안 봄 / 알려 줌 / 막음"이 대체 무엇인가

### 1-1. 실제 뜻 (사용자 질문에 대한 직접 답)

딜을 **그 단계로 옮길 때**, 6가지 사실이 채워졌는지 검사할지를 정하는 스위치다.

- 검사 대상 6가지: 금액 · 마감 예정일 · 담당자 · 고객 담당자 · 회사 · 다음 할 일
- **안 봄** = 이 단계에서는 검사하지 않는다
- **알려 줌** = 비어 있어도 옮겨는 주고, "금액이 아직 없어요"라고 말해 준다
- **막음** = 비어 있으면 그 단계로 못 옮긴다

**AI와 아무 관계가 없다.** 순수한 규칙 검사다.
사용자가 "AI가 자동으로 한다는 건가?"라고 물은 것은 오해가 아니라 **화면이 그렇게 읽히도록 만들어져 있어서**다(§2-1).

업계에서는 이걸 **exit criteria(단계 이탈 조건)**라고 부른다. 개념 자체는 정당하다 —
조건이 없으면 파이프라인은 카드 옮기기 놀이가 되고, "계약 협상 10억"이 금액 없는 딜일 수 있다.
문제는 개념이 아니라 **이 화면이 그 개념을 사람에게 내놓은 방식**이다.

### 1-2. 왜 못 알아봤나 — 구조적 원인 6가지 (전부 실측)

**① 주어가 없다.**
"안 봄"은 *누가* *무엇을* 안 보는지가 빠진 두 글자 동사다. 한국어로도 어색하고, 시스템 용어도 아니다.
설명은 화면 맨 위 한 줄과 버튼의 `title=` 툴팁뿐이다. 툴팁은 **마우스를 올려야만** 나오고, 스크린리더는 대개 읽지 않는다.
사용자가 "시스템용 언어는 아닌 것 같고"라고 한 것이 정확하다 — 시스템 용어도 아니고 사람 말도 아닌, **중간 지대의 축약어**다.

**② 342개가 한 화면에 있다.**
조건 6개 × 수준 3개 = 18개 버튼이 단계마다 **똑같이 반복**된다. 단계 19개 × 파이프라인 3개.
같은 목록이 19번 반복되는 화면에서 사람이 읽는 것은 첫 번째뿐이고, 나머지는 벽이다.

**③ 위치가 업계와 거꾸로다.**
표준(Pipedrive)은 **필드 쪽에 붙인다** — *금액 필드*를 열고 "이 필드는 어느 파이프라인·단계에서 필수인가"를 정한다.
필드는 6개뿐이므로 설정 지점도 6곳이다.
우리는 반대로 *단계*를 열고 그 안에 6개 필드를 전부 나열했다. 그래서 **단계 수만큼 설정 지점이 늘어난다**.

**④ 켜도 채울 방법이 없는 조건이 있다 — 심각.**
`담당자`를 '막음'으로 켜면 **그 단계는 영원히 잠긴다.**
딜의 담당자(`ownerId`)를 설정하는 UI가 **CRM 전체에 0개**이기 때문이다.

```
lib/crm/services/deal.ts        ownerId 저장 지원   ✅
lib/crm/domain/entry-criteria.ts owner 조건 판정    ✅
lib/crm/services/verify.ts       담당자 확정 대상    ✅
lib/crm/services/audit-view.ts   '담당자' 라벨       ✅
app/(crm)/**/*.tsx               담당자 입력 칸      ❌ 0건
```

딜 폼(이름·회사·파이프라인·단계·금액·통화·마감일)에도, 딜 상세 속성 카드에도, 회사 폼에도 담당자가 없다.
**뒤는 다 됐는데 사람이 값을 넣을 창구만 없다.**

**⑤ 켜기 전에 결과를 못 본다.**
"막음으로 켜면 지금 이 단계 딜 12건 중 5건이 걸립니다" 같은 미리보기가 없다.
효과는 나중에 **누군가 딜을 옮기려다 막혔을 때** 처음 나타난다. 그래서 켠 사람과 막힌 사람이 다르다.

**⑥ 막혔을 때 문구가 어색하다.**
`이 단계로 옮기려면 금액이(가) 필요합니다` — 조사 미처리.
같은 뿌리의 문제가 단계 이름 검증에서도 재발했다(`단계 이름을(를) 입력해 주세요`).

## 2. 전수 조사 — 같은 병이 어디에 또 있나

진단명 7개로 정리한다. 모두 실측 근거가 있다.

### 병 A — "기본값이 꺼짐": 설정은 있는데 제품은 아무 일도 안 한다

| 설정 | 규모 | 지금 켜진 것 | 어디 |
|---|---|---|---|
| 단계 진입 조건 | 342 토글 | **0** | `/crm/process` |
| AI 자동 반영 | 16행 (회사·인물·딜 필드) | **0** | `/crm/settings` |
| 자동화 규칙 | 무제한 | **0** | `/crm/settings` |
| AI 예산 | — | 0원(=AI 꺼짐)인데 AI 화면은 그대로 열린다 | `/crm/settings` |

**결과**: 신규 사용자가 실제로 만나는 제품은 이 기능들이 **전부 없는** 제품이다.
그런데 화면 문구는 도처에서 "AI가 …해 줍니다"라고 말한다.

- 미팅: "회의 내용을 넣으면 AI가 누가 나왔고 무엇이 걸림돌인지 뽑아 인박스로 보냅니다."
- 인박스: "AI가 찾아낸 제안을 확인하고 반영하는 곳입니다."
- 변경 이력: "AI가 채운 값도 여기서 확인할 수 있어요."

**말은 AI가 주인공인데, 스위치는 전부 꺼져 있다.** 사용자의 "AI가 자동으로 한다는 건가?"는 여기서 나온 혼란이다.

### 병 B — "만들었는데 부르는 데가 없다"

이 저장소가 `/ci`에서 이미 두 번 겪은 패턴이 CRM에서 재발했다.

| 무엇 | 만든 것 | 부르는 곳 |
|---|---|---|
| `ownerId` (담당자) | 서비스·API·진입조건·감사로그·확정대상 | **UI 0건** |
| `healthScore` (딜 건강도) | 스키마 + v04 마이그레이션이 `fit_score`를 이관까지 함 | **읽는 코드 0건** |
| AI 자동 반영 (회사 6필드) | 설정 카드 + field-config API | 실제 AI 추출축은 who/what/where/risk/next 5개뿐 → **회사 필드를 안 건드림** |
| 확정 자물쇠 | 필드별 확정 UI | 통제할 AI 자동반영 동작이 아직 없음 |

### 병 C — 화면이 흐름이 아니라 "안내판"이다

사용자가 말한 "폼만 낸 느낌"의 정확한 구조적 정체다. **상세 화면이 행동의 종착지가 아니라 다른 화면으로 보내는 표지판**이다.

- 회사 상세 · 인물 없음 → `"인물 화면에서 이 회사로 담당자를 등록하세요"` — **여기서 못 만든다**
- 회사 상세 · 딜 없음 → `"딜 화면에서 이 회사의 영업 건을 만드세요"` — **여기서 못 만든다**
- 딜 상세 · 미팅 없음 → '미팅 기록하기'가 `/crm/meetings` **목록**으로만 보낸다. 보던 딜을 안 데려가서 회사·딜을 처음부터 다시 고른다
- 할 일 화면 · 설명 → `"미팅에서 나온 '다음에 할 일'을 인박스에서 반영하면 여기 쌓입니다"` — 마치 그게 **유일한 경로**인 것처럼 말한다

### 병 D — 화면이 거짓말을 한다 (신뢰 파괴)

**로딩 상태를 빈 상태로 렌더한다.** 회사 상세를 열고 시각별로 실측했다.

| 경과 | 화면이 말하는 것 | 진실 |
|---|---|---|
| 3초 | "딜 0건 · 진행 중인 딜이 없어요" / "인물 0명 · 담당자가 없어요" | 딜 1건 · 인물 1명 |
| 6초 | 동일 | 동일 |
| 10초 | 딜 1건 · 인물 1명 | ✅ |

초기 state가 빈 배열이라 로딩과 "없음"을 구분하지 않는다.
사용자는 3초를 보고 **"데이터가 없네" 하고 나간다.**

같은 계열:
- 딜 상세의 **회사 이름이 늦게 채워진다** — 딜/파이프라인/이력은 `Promise.all`로 병렬인데 회사만 그 뒤 순차(waterfall). 8초 시점 스크린샷에서 `회사 —`, 그 뒤에 `삼성SDS`. QA가 "딜 생성 직후 회사가 —"로 보고한 것과 같은 뿌리다.
- **오늘 화면 '시작하기'**의 현재 강조 단계 설명 줄이 **보라 배경 위 보라 글씨**라 읽을 수 없다. 하필 "지금 이것 하나만 하세요"라고 강조한 자리다.

### 병 E — 용어가 갈린다

| 말 | 뜻 1 | 뜻 2 | 뜻 3 |
|---|---|---|---|
| **기록** | 사이드바 그룹 이름(미팅·할 일) | 변경 이력 화면의 **제목** | 타임라인 입력 라벨 |
| **영업 단계** | 사이드바 메뉴(=파이프라인 관리) | 파이프라인 안의 stage | 리포트 접기 토글이 부르는 것(실제로는 파이프라인) |
| **변경 이력 / 기록** | 사이드바에선 "변경 이력" | 같은 화면 제목은 "기록" | — |

그리고 설정 화면 부제: `"파이프라인·필드·AI·연동을 관리합니다"` — **파이프라인도 필드도 이 화면에 없다.**

### 병 F — 정작 필요한 손잡이는 설정에 없다

멈춘 딜 판정이 이렇게 되어 있다.

```ts
const STALLED_DAYS = 14                       // 전 단계 공통, 하드코딩
const cutoff = now - STALLED_DAYS * 86_400_000
// 기준 시각: deal.updatedAt
```

두 가지가 틀렸다.

1. **전 단계 공통 14일.** '리드'에서 14일과 '계약 협상'에서 14일은 전혀 다른 사건이다.
2. **기준이 `deal.updatedAt`이다.** 이건 *딜 레코드가 수정된 시각*이지 *아무 일도 없었던 기간*이 아니다.
   딜 이름만 고쳐도 정체 타이머가 리셋된다. 진짜 rot timer는 **마지막 활동/할 일/미팅** 기준이어야 한다.

**342개 토글은 주면서, 실제로 조정하고 싶을 이 숫자 하나는 설정에 없다.**

### 병 G — 설정 화면 자체가 증상이다

- 카드 8장이 성격 구분 없이 masonry로 흩어진다. 로딩 속도가 달라 **첫 줄이 어긋난 채 뜬다**(실측).
- 로딩 중엔 카드 제목도 안 보여서 **무슨 카드인지 모른다**.
- 성격이 완전히 다른 것들이 같은 무게로 나열된다: AI 예산 / 기본 설정 / 자동 반영 / 구글 연동 / 중복 정리 / 자동화 / 들여오기 / 내보내기.
- 영업 단계 화면은 CRM에서 **유일하게** `window.alert`·`confirm`을 쓴다(4회). 질감이 다르고 자동화 테스트가 이 경로를 못 밟는다.

## 3. 사용자가 말한 흐름 vs 지금 제품

사용자가 말한 순서를 그대로 축으로 놓고 대조했다.

| # | 사용자가 말한 것 | 지금 | 근거 |
|---|---|---|---|
| 1 | 인바운드/아웃바운드로 고객·딜 획득 | **없음** | 딜에 획득 경로 필드가 없다. `CrmDeal.source`는 HUMAN/AI(데이터 출처)이지 lead source가 아니다. 인바운드 유입구도 CRM 안에 없다(`/lead-intake`는 CRM 밖 별도 화면) |
| 2 | 정보를 디테일하게, 또는 AI가 작성 | **반쪽** | 딜 폼 7칸(이름·회사·파이프라인·단계·금액·통화·마감). 담당자·고객 담당자·획득 경로·경쟁사·의사결정 구조 없음. AI 작성은 기본 OFF |
| 3 | 등록된 딜에 활동을 주기적으로 기록 | **반쪽** | 타임라인에 노트 입력 1개. 통화·메일·미팅 필터 탭은 있는데 넣는 경로가 빈약. Gmail 연동은 있으나 '확인되지 않은 앱' 경고 상태 |
| 4 | 안 움직이는 거 알려줌 | **있음(약함)** | 14일 하드코딩 + `updatedAt` 기준 (§병 F) |
| 5 | 매출·목표·수익 | **없음** | 스키마에 quota/target/cost/margin 개념이 0. 리포트에 기간 필터 0. 원가 없이 금액 하나뿐이라 **수익을 계산할 수 없다** |
| 6 | 고객 정보를 한 번에 | **반쪽** | 회사 상세의 구조(속성·타임라인·다음 할 일·인물·딜·미팅)는 이 제품에서 가장 잘 된 화면이다. 그런데 **거기서 아무것도 만들 수 없다**(§병 C) |
| 7 | 시점별로 정리 | **없음** | 리포트에 period 개념 자체가 없다. 이번 달/분기/전년 대비가 불가능 |
| 8 | 이력 확인 | **있음(읽기 어려움)** | 감사로그가 JSON 원문·ISO 시각(UTC)·원시 ID를 그대로 노출 |

### 3-1. 그리고 이 회사에만 있는 결정적 공백 — GPU 가격 시스템과의 단절

`lib/gpu/`에 이미 **원가·추천판매가·마진·경쟁사 시세·구성 사다리**가 SSOT로 있다. 콕핏(`/pricing/gpu?tab=cockpit`)도 있다.

그런데 **CRM 딜과 연결이 0이다.** 파이프라인 id가 `pl_gpu`인 것이 전부다.

- '견적·제안'이라는 단계가 있는데 **견적을 만들 수 없다**
- 딜 금액은 **손으로 적는 숫자**다. 근거가 없다
- 원가가 없으니 **수익(사용자 요구 5번)을 계산할 방법이 없다**

이건 결함이 아니라 **미개척 영역**이고, 동시에 이 제품이 시중 CRM 대비 가질 수 있는 **유일한 해자**다.

## 4. 외부 정설 (조사 결과)

| 정설 | 우리 상태 |
|---|---|

| "아무도 안 채우는 20개 필드보다, 모두가 채우는 5개가 낫다" | 조건 6개를 19개 단계에 전부 노출 |
| **도입 실패 1위 원인은 입력 부담.** 영업의 60%가 판매 외 업무, CRM 입력에만 주 3.4시간. 활동 자동 캡처를 하면 주 5시간을 돌려받고 쿼터 달성률 2.2배(Gartner) | 활동 입력이 전부 수동. Gmail 연동만 자동이고 그것도 경고 상태 |
| 현대 CRM(Attio·Folk)은 메일·캘린더를 **계속 빨아들여 고객 그래프**를 만들고, 그 위에서 정체 감지·다음 행동을 제안한다 | 우리는 사람이 채우는 폼이 기반. AI는 미팅 전사 1개 경로뿐 |

## 5. 재기획

### 5-0. 원칙 4개

1. **기본값이 제품이다.** 켜야 동작하는 기능은 없는 기능이다. 좋은 기본값을 켜 두고, 설정은 *끄는* 자리로 바꾼다.
2. **설정을 없애서 푼다.** 342 → 목표 0. 남길 손잡이는 3개 남짓.
3. **화면은 종착지다.** 회사 상세에서 인물·딜·할 일·미팅을 **만들 수 있어야** 한다. "다른 화면으로 가세요"는 금지.
4. **입력을 줄이고 그래프를 채운다.** 사람 입력은 최소로, 메일·미팅·활동 수집은 자동으로.

### 5-1. 영업 단계 조건 재설계 (사용자가 막힌 그 기능)

**폐기**: 단계 × 조건 6 × 수준 3 격자(342개).

**대체 — 4개로 줄인다.**

| | 무엇 | 왜 |
|---|---|---|
| **(a)** | **기본으로 켜진 규칙 하나**: "다음 할 일이 없는 딜은 표시한다" (이미 있음, 유지) | 설정 없이 즉시 동작. Pipedrive의 유일한 강제 규율과 같다 |
| **(b)** | **단계마다 '이 단계의 뜻' 한 줄** (자유 텍스트, 예: "고객이 요구사항을 문서로 줬다") | 이게 진짜 exit criteria다. **검사하지 않고 보여만 준다.** 딜을 옮길 때 그 문장을 한 번 보여 주고 "맞나요?"라고 묻는다 |
| **(c)** | **필수 값은 필드 쪽으로 이동** — 딜 폼/상세에서 필드마다 "○○ 단계부터 필요" 배지. 수준은 2단계(필요/아님) | 업계 표준 위치. 설정 지점이 필드 수(6)로 고정된다 |
| **(d)** | **기본값**: 성사(WON) 단계의 **금액만** 필수 | "수주는 금액 없이 성립할 수 없다"는 유일한 무조건 참인 명제 |

추가 규칙 2개:

- **켜기 전 영향 미리보기 필수** — "지금 이 단계 딜 12건 중 5건이 걸립니다"
- **채울 UI가 없는 조건은 목록에 띄우지 않는다** — 담당자는 입력 칸이 생기기 전까지 숨긴다

용어도 바꾼다: `안 봄 / 알려 줌 / 막음` → **`검사 안 함 / 비어 있으면 알려 주기 / 비어 있으면 못 옮기게`**
(길어도 상관없다. 이건 자주 읽는 라벨이 아니라 **한 번 이해하면 되는 라벨**이다.)

### 5-2. 메뉴·정보구조 재편

현재: 사이드바 15항목 / 4그룹.

```
현재                              제안
─────────────────────────        ─────────────────────────
오늘                             오늘        ← 인박스를 흡수
인박스          ┐                딜          ← 획득경로·담당자·마지막활동 표시
딜              │                고객        ← 회사 + 인물을 탭으로 통합
회사            │                활동        ← 미팅 + 할 일 + 타임라인 통합
인물            │                성과        ← 리포트 + 목표 + 수익
[기록] 미팅·할일 │                설정        ← 영업단계·멤버·연동·AI·데이터·변경이력
[보기] 리포트·변경이력            ─────────────────────────
[설정] 영업단계·멤버·설정          [돌아가기] 홈·업무·캘린더 (유지)
[돌아가기] 홈·업무·캘린더
```

핵심 변경 3가지와 이유:

- **인박스를 없앤다** → 오늘 화면의 한 구역으로. AI 제안을 별도 메뉴로 두면 "AI 전용 방"이 되어 아무도 안 들어간다.
- **회사 + 인물 → 고객.** 지금은 같은 대상을 두 메뉴에서 찾는다. 사용자가 말한 "고객정보도 한번에 찾을 수 있고"가 여기다.
- **미팅 + 할 일 → 활동.** 사용자가 말한 "활동을 매일이든 주기적이든 기록하고"가 한 곳에 있어야 한다.

### 5-3. 딜 상세 재설계

**지금 문제**: 화면의 절반을 `단계 이동 이력`이 차지한다. 그 내용은 실측하면 이렇다.

```
리드 → 요구사항 파악    8/16 23:37 · 첫 진입
요구사항 파악 → 리드    8/16 23:37 · 42초 머무름
리드 → 요구사항 파악    8/17 00:55 · 1시간 머무름
...
```

**테스트하며 왔다 갔다 한 로그가 제품 화면의 주인공**이다.
정작 필요한 금액·마감·담당자는 왼쪽 좁은 칼럼에 `—`로 비어 있고, 채우라는 유도도 없다.

**제안 — 3단 구조**

| 위치 | 무엇 | 왜 |
|---|---|---|
| 상단 | **이 딜의 한 줄 판정** + 인라인 채우기 — "계약 협상 12일째 · 금액 미정 · 다음 할 일 없음" | 열자마자 "그래서 뭘 해야 하지"에 답한다 |
| 중앙 | **활동 타임라인** (메일·미팅·통화·노트, 자동+수동) | 여기가 주인공이어야 한다. 사용자 요구 3번 |
| 우측 | 사람 · 다음 할 일 · **연결된 견적** | 행동을 그 자리에서 |
| 하단(접힘) | 단계 이동 이력 | 감사용이지 일상용이 아니다 |

### 5-4. 신규 — 목표·수익 (사용자 요구 5번, 스키마 추가 필요)

지금 스키마에 **없다.** 추가해야 하는 최소 단위:

```prisma
model CrmTarget {          // 목표
  scope     TargetScope    // WORKSPACE | MEMBER | PIPELINE
  scopeId   String?
  periodKey String         // '2026-Q3' | '2026-08'
  amountMinor BigInt
  currency  String
}

model CrmDeal {
  costMinor  BigInt?       // 원가 — 수익 계산의 전제
  quoteId    String?       // GPU 견적 연결 (§5-5)
  leadSource CrmLeadSource // 획득 경로 (§5-6)
}
```

리포트에 축 3개 추가: **기간(월/분기)** · **담당자** · **획득 경로**.
지금 리포트는 이 셋이 전부 없어서 "이번 달 목표 대비 얼마"를 물을 수 없다.

### 5-5. 신규 — GPU 견적 연결 (이 제품의 유일한 해자)

'견적·제안' 단계에서 `lib/gpu/` 콕핏을 그 자리에서 부른다.

```
딜 상세 → [견적 만들기]
  → 모델·장수·기간 선택 (lib/gpu SSOT)
  → 원가 · 추천판매가 · 경쟁사 시세가 딜에 붙는다
  → 딜 금액이 '손으로 적은 숫자'에서 '근거 있는 금액'이 된다
  → 리포트에서 수익(마진)이 나온다
```

이것 하나가 **사용자 요구 2번(디테일한 정보)·5번(수익)을 동시에 닫는다.**
그리고 시중 CRM이 절대 못 하는 일이다 — 우리만 원가를 안다.

### 5-6. 신규 — 획득 경로 (사용자 요구 1번)

`CrmDeal.leadSource` 추가:

```
인바운드 : 웹문의 · 소개 · 전시/세미나 · 기존고객확장
아웃바운드: 콜드메일 · 콜드콜 · 링크드인
파트너   : 파트너사 소개
```

리포트 축으로 쓰면 "인바운드가 성사율이 3배 높다" 같은 판단이 처음 가능해진다.
지금은 이 구분이 **데이터에 존재하지 않아서** 물어볼 수조차 없다.

### 5-7. 정체 판정 고치기

- 기준 시각: `deal.updatedAt` → **마지막 활동/할 일/미팅 시각**
- 임계값: 전 단계 공통 14일 → **단계별**(기본값 제공 + 설정 1곳)

## 6. 순서 — 무엇부터

> 사용자 질문: "뭐부터 시작해야 하는지 아직도 모르겠네."

### 6-1. 우리가 고칠 순서

| 단계 | 무엇 | 왜 이 순서인가 |
|---|---|---|
| **0** | **거짓말부터 멈춘다** — 로딩≠빈 상태, 오늘 화면 대비, 조사 처리, 용어 통일, 설정 부제 수정 | 신뢰의 바닥. 화면이 거짓말하는 동안엔 어떤 기능을 더해도 안 믿는다 |
| **1** | **342 토글 철거 + 조건 재설계**(§5-1) | 사용자가 지금 막힌 바로 그 지점 |
| **2** | **담당자 UI + 획득 경로 + 딜 상세 재설계**(§5-3·5-6) | "폼 모음"에서 벗어나는 최소 단위 |
| **3** | **화면을 종착지로**(§5-2 C병 해소) + 메뉴 재편 | 흐름이 이어지기 시작한다 |
| **4** | **목표·수익 + 리포트 기간축**(§5-4) | 사용자 요구 5·7번 |
| **5** | **GPU 견적 연결**(§5-5) | 여기서 이 제품이 다른 CRM과 달라진다 |
| **6** | **활동 자동 캡처 기본 ON**(메일·캘린더) | 입력 부담 제거 — 도입 실패 1위 원인 |

**0~2단계까지가 "지금 화면이 이상하다"의 해소**이고, **3~6단계가 "그냥 폼 모음"에서 벗어나는 일**이다.

### 6-2. 제품이 사용자에게 안내해야 할 순서 (온보딩 재설계)

현재 '시작하기' 4단계는 방향이 맞다. 다만 **1번이 하필 342 토글 화면으로 보낸다.**

```
지금                                    제안
1 영업 단계를 우리 회사에 맞게 정리      1 회사와 연락처를 넣으세요 (또는 엑셀에서 가져오기)
2 회사와 연락처를 등록                   2 진행 중인 영업 건을 딜로 만드세요
3 첫 딜을 만들어 보세요                  3 딜마다 다음에 할 일을 정하세요
4 딜마다 다음에 할 일을 정하세요          4 (선택) 단계 이름을 우리 말로 바꾸세요
```

**데이터부터, 설정은 마지막에.** 지금은 반대다 — 아무 데이터도 없는 사람에게 가장 추상적인 설정을 먼저 시킨다.

## 7. 사용자만 결정할 수 있는 것 4가지

이 넷은 코드나 외부 자료로 답이 안 나온다.

1. **목표는 누구 단위인가** — 회사 전체 / 부서 / 담당자별? (스키마 `TargetScope`가 여기서 갈린다)
2. **수익의 원가를 어디서 가져오나** — GPU 콕핏 자동 연결 / 딜에 수기 입력 / 둘 다?
3. **메일·캘린더 자동 수집을 기본 ON으로 해도 되나** — 프라이버시 결정이라 제품이 정할 수 없다
4. **파이프라인 3개(GPU 인프라·공공·파트너십)를 실제로 다 쓰나** — 지금 딜은 전부 GPU 인프라에 있고, 리포트가 안 쓰는 2개를 계속 센다
