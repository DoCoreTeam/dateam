# 프로젝트관리(/lead-intake) 전면 진단 — "AI CRM"은 가능한가

작성: 2026-08-11 · 기준 버전 v0.7.423 · 작성자 Claude (코드 + 운영 DB 실측)

> **한 줄 결론**: 가능하다. 그런데 **없는 건 입력창이 아니라 출구다.** 사용자가 원한 "입력창 하나"는 이미 만들어져 있고 꽤 잘 만들어져 있다. 죽은 이유는 입력 뒤에 아무 일도 일어나지 않기 때문이고, 결정적으로 **한 번 대량 투입했다가 379건을 전량 삭제한 사고**로 신뢰가 끊겼기 때문이다.

## 0. 조사 방법 (주장의 근거)

추측 배제. 두 가지 소스만 사용했다.

| 소스 | 범위 |
|---|---|
| 코드 | `app/(member)/lead-intake/*`, `app/api/leads/*`, `lib/gemini-lead.ts`, `lib/lead-bulk-import.ts`, `app/(member)/layout.tsx`, `lib/work/*`, `lib/daily/schedule-candidates.ts`, `app/api/projects/*`, 마이그 009/015/017/020/101/182/183 |

DB를 직접 본 게 이 보고서의 핵심이다. 코드만 봤으면 "기능은 다 있는데 왜 안 쓰지?"에서 끝났을 것이다.

## 1. 실측 — 지금 실제로 무슨 일이 벌어져 있나

### 1-1. 이 메뉴는 **67일째 방치**되어 있다

```
lead_intakes  1,517건   마지막 입력 2026-06-05   (오늘 2026-08-11 기준 67일)
accounts         12건   마지막 생성 2026-07-15
contacts          1건
deals             1건
deal_activities   0건
```

### 1-2. "AI가 입력창 하나에서 분석" — 실사용 **2건**

| source | 건수 | 의미 |
|---|---:|---|
| `xlsx_bulk` | 1,512 | 엑셀 대량 투입 1회 |
| `file` | 3 | 파일 첨부 |
| `prompt` | **2** | **텍스트 직접 입력** |
| `voice` / `card_scan` | 0 | 음성·명함 촬영 |

사용자가 원한 바로 그 흐름(텍스트 붙여넣기 → AI 분석)은 **평생 2번** 쓰였다. 음성 입력, 명함 촬영은 구현돼 있는데 **한 번도 안 쓰였다.** 즉 이 화면은 "AI CRM"으로 쓰인 적이 없고, **엑셀 일괄 업로더로 딱 한 번 쓰이고 버려졌다.**

### 1-3. 가장 심각한 발견 — "CRM 등록" 배지 **379건 중 378건이 거짓**

```sql
status='crm_registered' 인 379건 중
  linked_account_id 살아있음 :   1
  linked_deal_id    살아있음 :   1
  linked_account_id IS NULL  : 378
  converted_at      IS NULL  : 378
```

`lead_intakes.linked_account_id`는 `ON DELETE SET NULL`이다 (`009_lead_management.sql:189-191`). 즉 **378건은 거래처·영업기회를 실제로 만들었다가, 그 거래처들이 나중에 통째로 삭제된 것**이다.

복원되는 사건 순서:

```
2026-05-26  엑셀 1,512행 대량 투입 → AI 파싱
2026-05-26  검수 없이 379건 CRM 일괄 등록 (거래처·담당자·영업기회 생성)
   ~06-05   결과물이 쓸 만하지 않음 → 생성된 거래처 전량 삭제
   06-05~   아무도 다시 안 들어옴
```

화면에는 지금도 378건이 **"CRM 등록"** 초록 배지를 달고 앉아 있다. 실체는 없다. **사용자가 화면을 못 믿게 된 결정적 순간이 여기다.**

### 1-4. 남아 있는 거래처 12건의 정체 — CRM 데이터가 아니다

```
gcube, High Reso, Konsttech, Tensordock, Voltage Park,
CoreWeave, Equinix Metal          → source=supplier_migration  (GPU 공급사 이관)
NHN Cloud, FPT, konst tech        → source=supplier            (GPU 공급사)
__rls_smoke_626542                → 테스트 찌꺼기가 운영 DB에 잔존
삼성SDS                            → source=민간DB              ← 유일한 리드 유래
```

- 리드에서 만들어진 진짜 거래처는 **삼성SDS 1건뿐**이고, 이건 입력 폼 placeholder에 적힌 예시(`삼성SDS 김철수 부장`) 그 자체다. **= 개발자 테스트 1건**
- `Konsttech`와 `konst tech`가 **둘 다 살아있다** → 중복 방지가 실제로 실패한 실증
- 운영 DB에 테스트 계정 `__rls_smoke_626542` 방치

### 1-5. 1,136건은 화면에서 도달조차 불가

`status='completed'` 1,136건이 검수도 등록도 안 된 채 영구 정체 중이다. 그런데 화면은 **최근 20건만** 보여준다 (`page.tsx:49` `.limit(20)`). 검색·필터·페이징·전체보기 **전부 없다.** 1,116건은 UI에서 존재하지 않는 데이터다.

## 2. 진단 — 왜 죽었나 (구조적 원인 7가지)

### 원인 1. 입력은 있는데 **출구가 없다** ★근본

이 화면은 `입력 → AI 파싱 → 거래처/담당자/영업기회 INSERT`까지 하고 **끝난다.** 등록 다음에 사용자에게 돌아오는 것이 아무것도 없다.

- `deals.next_action` / `next_action_date`: AI가 뽑아서 저장까지 한다. 그런데 사용처를 전수 조사하면 `DealForm`(입력폼), `deals/[id]`(상세 표시), API 3개뿐. **캘린더에도, 일일업무에도, 홈 화면에도 안 나온다.** 즉 "다음에 뭘 해야 하는지"를 AI가 알아냈는데 아무도 알려주지 않는다.
- `deal_activities` **0건**: 영업 활동 타임라인 테이블이 있는데 한 줄도 안 쌓였다.
- 등록하면 화면에서 사라지고, 그 리드가 어떻게 됐는지 추적할 경로가 없다.

**CRM은 "넣는 곳"이 아니라 "오늘 뭘 할지 알려주는 곳"이다. 지금은 넣는 곳만 있다.**

### 원인 2. AI가 **정제만 하고 판단을 안 한다**

`gemini-lead.ts`의 파이프라인은 `추출 → fit_score 채점 → 끝`이다. 빠진 판단:

- **중복 판정 없음.** `lead_intakes.duplicate_of` 컬럼이 스키마에 있는데(`009:194`), 전체 코드에서 사용처는 `types/database.ts` 타입 선언 **한 줄뿐**. 구현 0.
- **기존 거래처 매칭 없음.** `bulk-confirm`의 매칭 조건(`route.ts:53-69`)은 ① 사업자번호 완전일치 ② 이름 **완전일치** 둘뿐. `Konsttech` ≠ `konst tech`로 판정 → 중복 생성. GPU 도메인에서 이미 겪고 해결한 문제인데(`resolveCompetitorId`, `merge_competitors_apply` RPC, 별칭 테이블) **CRM은 그 자산을 안 쓴다.**
- **"이건 애매하니 사람이 봐라"가 없음.** 신뢰도가 낮아도 그냥 등록된다.

### 원인 3. 검수 없는 일괄 등록 → 쓰레기 → 전량 삭제 → 신뢰 붕괴 ★사고 원인

프로젝트 규약(`CLAUDE.md §5-3`)은 명시한다: **"추출/제안형 AI는 후보 체크리스트로 제시 → 사용자가 선택 → 일괄 반영. 자동 등록 금지."**

텍스트 1건 경로는 이 규약을 지킨다(`ParsedCard` 보여주고 사용자가 버튼 클릭). 그런데 **대량 경로는 이 규약을 통째로 우회한다.** 1,512행을 파싱해서 379건을 검수 화면 없이 밀어넣었고, 결과는 전량 삭제였다.

### 원인 4. 이름과 경계가 무너져 있다

같은 개념에 이름이 4개다.

| 사용자가 보는 것 | 실제 | 데이터 |
|---|---|---|
| 사이드바 **"프로젝트관리"** | `/lead-intake` | intake 1,517 |
| 페이지 제목 **"리드 인테이크"** | 같은 화면 | — |
| **"프로젝트"** | `/work/projects` (별도 시스템) | projects 8 / **project_items 0** |
| **"AI 작업공간"** | `/ai-chat/projects` | `ai_projects` |

사용자가 "프로젝트 관리"를 누르면 CRM 리드 화면이 나온다. 진짜 프로젝트 기능은 업무 메뉴 안에 따로 있고, 그것도 **실행 항목 0건**이다. **사용자가 이 화면이 뭐 하는 화면인지 모르는 게 정상이다.**

### 원인 5. 연결 자산이 이미 있는데 **서로를 모른다**

이게 가장 아까운 부분이다. 필요한 부품이 다 있는데 배선이 안 돼 있다.

| 이미 있는 것 | 위치 | 현재 상태 |
|---|---|---|
| 일일업무 ↔ 거래처/영업기회/담당자 **AI 자동연결** (신뢰도 + 학습 피드백) | 마이그 101, `lib/work/autolink-run.ts` | `work_entity_links` **1건** |
| 프로젝트 ↔ 일일/회의/주간/거래처/영업기회 **범용 관계** | 마이그 183 | `project_relations` 7건 (전부 마이그 시드, 사람이 만든 것 0) |
| 일일업무 → 캘린더 **후보 추천 → 확인 → 등록** (검증된 패턴) | `lib/daily/schedule-candidates.ts` | 작동 중 (캘린더 53건) |
| 회의노트 → 업무·일정 추출 | `meeting-notes` | 12건 |
| KST 시간 SSOT | `lib/datetime/kst.ts` | 작동 중 |
| 감사로그·되돌리기 | 마이그 146/148, `restore-action` | 작동 중 |

**"업무·캘린더랑 연결되면 좋겠다"는 사용자의 바람은 부품이 이미 다 있다.** 리드/거래처만 이 배선에서 빠져 있다.

### 원인 6. "AI 자연어 실행"이 실은 **정규식**

v0.7.422 커밋명은 "AI 프로젝트 통합과 **자연어 실행** 체계 구현". 실제 구현(`lib/work/project-command.ts` 전문 13줄):

```ts
const RULES = [
  ['milestone', /^(?:마일스톤|이정표)\s*(?:추가|등록)?\s*[:：-]?\s*(.+)$/i],
  ['task',      /^(?:할일|작업|업무)\s*(?:추가|등록)?\s*[:：-]?\s*(.+)$/i],
  ...
]
```

`"할일 추가: X"` 포맷에서 벗어나면 **400 에러**. AI 호출 0회. 사용자가 "다음 주에 삼성SDS 미팅 잡아줘"라고 치면 실패한다. `project_items` 0건인 이유다.

### 원인 7. admin 전용 → **리드를 만드는 사람이 못 쓴다**

`lead-intake/layout.tsx:5`의 `requireAdmin()` + `(member)/layout.tsx:134`의 그룹 필터로 관리자만 접근한다. 그런데 명함을 받고 미팅을 하고 리드를 만드는 사람은 현장 영업 담당이다. **입력 주체가 화면에 못 들어온다.** 데이터가 안 쌓이는 구조적 이유다.

## 3. 보안 — 지금 안 터졌지만, 채우는 순간 터지는 것

`lead_intakes`와 `accounts`의 RLS SELECT 정책을 DB에서 직접 확인했다.

```sql
lead_intakes_select_all  SELECT  USING (EXISTS (SELECT 1 FROM profiles
                                        WHERE id = auth.uid() AND deleted_at IS NULL))
accounts_select_all      SELECT  USING (동일)
```

**로그인한 사용자면 누구나 전 직원의 리드·거래처를 전부 읽을 수 있다.** 화면과 API는 admin 게이트가 있지만, RLS는 열려 있다. 브라우저의 anon 키 + 일반 사용자 세션으로 PostgREST를 직접 호출하면 우회된다.

- **지금 실피해**: 거의 없음. 데이터가 사실상 비어 있다(거래처 12건, 그중 11건이 GPU 공급사).
- **위험 시점**: AI CRM을 만들어 데이터가 차는 **바로 그 순간**, 그리고 원인 7을 풀어 member에게 개방하는 순간, 전사 영업정보 열람 경로가 된다.
- 조치: 개방 전에 `org-scope` 기반 SELECT 정책으로 교체 필수. 조직도 권한 체계는 이미 있다.

부수: 운영 `accounts`에 테스트 행 `__rls_smoke_626542` 잔존 → 정리 대상.

## 4. 사용자가 원한 것 vs 현실 — 정확한 gap

| 원한 것 | 현실 | 판정 |
|---|---|---|
| 입력창 하나에 아무거나 | **이미 있음.** 텍스트·붙여넣기·드래그&드롭·파일·사진·음성 통합 입력 (`LeadIntakeForm.tsx`) | ✅ 잘 만들어짐 |
| AI가 분석해서 정제 | **이미 있음.** Gemini 추출 + 필드 정규화 + fit 점수 | ✅ 작동함 |
| 데이터를 CRM에 넣어줌 | **있음.** 거래처·담당자·영업기회 생성 | ⚠️ 중복·병합 처리 없음 |
| **정제된 데이터를 믿을 수 있음** | 없음. 중복 생성, 거짓 상태 배지 378건 | ❌ |
| **업무와 연결** | 없음. next_action이 업무로 안 감 | ❌ (부품은 있음) |
| **캘린더와 연결** | 없음. next_action_date가 캘린더로 안 감 | ❌ (부품은 있음) |
| **넣은 뒤에 뭘 할지 알려줌** | 없음 | ❌ |

**사용자가 놓친 지점**: 문제를 "입력"으로 진단했는데, 실제 결손은 **출력(다음 행동)과 신뢰(중복·되돌리기)** 쪽에 있다. 입력창을 더 좋게 만들어도 안 쓰인다 — 지금 입력창은 이미 충분히 좋은데 2번 쓰였다.

## 5. 그래서, 그렇게 동작하긴 어려운가? — 냉정한 판정

### 가능하다. 단 "완전 자동"은 불가능하고, 그걸 목표로 잡으면 또 실패한다.

**가능한 근거 (부품 재고 실사)**

- 추출 AI: `gemini-lead.ts` 검증됨
- 엔티티 매칭 + 신뢰도 + 오답 학습: `lib/work/autolink-*` — **이미 만들어 놓고 안 쓰는 중**
- 후보 제시 → 사람 확인 → 등록 패턴: `schedule-candidates.ts` (캘린더에서 실제로 작동)
- 범용 관계 테이블: `project_relations` (daily_log/meeting_note/weekly_report/account/deal 지원)
- 되돌리기·감사: `audit_log` 트리거 + `restore-action`
- 표기 변형 병합 노하우: GPU 도메인의 `resolveCompetitorId` + 병합 RPC + 별칭 테이블 + 사람 게이트

**불가능한 부분 (여기서 정직해야 함)**

회사명 표기 변형(`Konsttech`/`konst tech`/`(주)콘스트테크`), 같은 사람의 이메일 2개, 같은 건이 다른 제목으로 두 번 들어오는 것 — 이건 결정론으로 못 잡고 LLM도 100%는 못 잡는다. **GPU 시세에서 이미 이 벽에 부딪혔고**, 거기서 채택한 원칙이 정답이다:

> **확정분은 오차 0으로 자동, 애매한 건 명시적으로 보류하고 사람에게 1클릭으로 물어본다. 조용히 추측해서 넣지 않는다.**

"AI가 다 알아서"를 목표로 잡으면 → 애매한 걸 조용히 추측 → 쓰레기 축적 → 전량 삭제 → **2026-05-26 사고 재연.**

## 6. 분석의 재분석 — 내 1차 진단에서 틀렸거나 약했던 것

사용자 지시대로 위 분석을 다시 공격했다.

**(a) "출구가 없어서 죽었다"는 인과가 정말 맞나?**
반론: 애초에 입력이 2건뿐이라 출구를 논할 단계도 아니었던 것 아닌가?
재검토: 둘 다 맞다. 순서가 있다. ① 대량투입으로 데이터는 한 번 찼다(1,517건) ② 출구가 없어서 그 데이터가 아무 가치를 못 냈다 ③ 그래서 전량 삭제했다 ④ 그 뒤로 아무도 안 들어왔다. **출구 부재가 신뢰 붕괴의 원인이고, 신뢰 붕괴가 미사용의 원인이다.** 인과 유지. 다만 "입력 UX가 나빠서"는 **기각** — 입력 UX는 좋다.

**(b) admin 전용이 진짜 원인인가, 결과인가?**
반론: 쓸모없으니 admin에 가둬둔 것일 수도 있다(원인이 아니라 결과).
재검토: 검증 불가. 코드 이력으로는 처음부터 admin이었다. **원인 순위에서 7위로 내리고, "개방은 신뢰 회복 뒤"로 순서를 바꾼다.** 지금 개방하면 378건 거짓 배지를 전 직원이 보게 된다 — 더 나쁘다.

**(c) "부품이 다 있다"가 과장 아닌가?**
자기검증: `work_entity_links` 1건, `project_relations`는 전부 마이그 시드, `project_items` 0건. **부품들이 "작동 검증됨"이 아니라 "코드가 존재함" 수준인 것도 있다.** 실제로 사람 손에서 검증된 건 캘린더 후보 패턴(53건)과 일일업무(236건)뿐. 표현 수정: **"검증된 부품 2개(일일·캘린더) + 미검증 부품 3개(autolink·relations·project_items)"**. 미검증 부품에 의존하는 단계는 리스크로 표시해야 한다.

**(d) ±9시간 시간 버그를 의심했다 → 기각**
`schedule-candidates.ts`가 `new Date(y, m, d, 9)` 로컬 생성자를 쓴다. 서버(UTC)에서 돌면 KST 18:00이 된다. 그러나 호출부 `daily/page.tsx`가 `'use client'`이므로 브라우저(KST)에서 실행된다. **현재는 버그 아님.** 단, 이 함수를 서버 라우트에서 재사용하는 순간 ±9h 사고가 난다 — CRM 연결 시 그대로 갖다 쓰면 밟는다. **주의 표시 필요.**

**(e) 내가 놓쳤던 것 — 회의노트**
1차 분석에서 회의노트(12건, 8/10까지 활발)를 빼먹었다. **B2B 영업에서 리드가 실제로 발생하는 자리는 미팅이다.** 회의노트는 이미 쓰이고 있고 AI 추출도 붙어 있다. **리드 캡처 지점으로 별도 인테이크 화면보다 회의노트가 훨씬 자연스럽다.** 이건 설계를 바꿀 만한 발견이다.

**(f) 근본 재검토 — 별도 메뉴로 두는 게 맞나?**
CRM은 입력이 귀찮아서 죽는다. 이 프로젝트에서 실제로 살아있는 화면은 일일업무(236건)·캘린더(53건)·회의노트(12건) — **매일 여는 곳**이다. 죽은 화면은 프로젝트관리(67일)·프로젝트(항목 0). 결론: **별도 메뉴를 아무리 잘 만들어도 안 열린다. CRM은 일일업무·회의노트 안으로 스며들어야 한다.** 별도 화면은 "쌓인 걸 보는 곳"이지 "넣는 곳"이 아니어야 한다.

## 7. 권고 설계 — 무엇을, 어떤 순서로

1. **자동 등록 금지.** 후보 제시 → 사람 확인 → 반영 (`CLAUDE.md §5-3` 준수)
2. **애매하면 보류.** 추측해서 넣지 않는다. 보류함이 곧 할 일 목록
