## 0. 한 줄 결론

> **의도는 정확하고 스키마도 잘 잡혀 있다. 그런데 지금 이 시스템은 "돌지 않는다".**
> 링크를 넣으면 잡이 큐에 쌓이지만 **그 큐를 부르는 사람이 세상에 아무도 없고**(크론 미등록), 콘텐츠 링크는 그 계정으로 **확장되지 않으며**, 채널/프로필 링크는 **입구에서 거부**되고, "모니터링"에는 **주기적으로 지켜보는 코드가 없다.** 어시스턴트는 **AI가 아니라 정규식 12개**다.
> 그리고 가장 중요한 것: **"계정의 모든 게시물"은 유튜브에서만, 그것도 API 키가 있어야 가능하다.** 나머지 5개 플랫폼은 구조적으로 불가능하다. 이건 버그가 아니라 **기획을 고쳐야 하는 제약**이다.

## 2. 의도의 정식화

사용자 진술을 시스템 계약으로 옮기면 이렇다.

> **입력**: 링크 1개. 콘텐츠든 프로필이든 채널이든 **사용자가 종류를 알려주지 않는다.**
> **출력**:
> ① 그 계정의 **게시물 모집단**
> ② 각 게시물의 **메타 + 시계열 지표**
> ③ 그 계정의 **평소 대비** "잘 된 것" 판정
> ④ **왜 잘 됐는지**의 관측 근거
> ⑤ ①~④ 전부를 **출처·시각·방법과 함께 영구 보관** ← 이것이 "1차 프로세스"

여기서 파생되는 불변식 3개:

- **I-1. 콘텐츠 링크 = 채널 링크다.** "잘 됨"은 그 계정의 평소 대비로만 정의되므로, 콘텐츠 1건을 받으면 그 계정 전체 훑기는 **선택이 아니라 필수**다.
- **I-2. 모집단 없이 판정 없다.** 비교군이 얇으면 배수를 내지 않는 현재 설계(최소 8건)는 옳다. 문제는 모집단을 **채우는 경로가 없다**는 것.
- **I-3. 모르는 것은 모른다고 말한다.** 현재 코드가 이미 잘 지킨다(`completeness`, `sweep_error`, "543개 중 15개"). **이건 지켜야 할 자산이다.**

## 3. 지금 링크를 넣으면 실제로 일어나는 일

### 3-A. 유튜브 **영상** 링크를 홈 입력칸에 넣는다

```
LinkIntakeBox → POST /api/ci/ingest
  → ci_contents 1행 생성 (source='inbox', ingest_status='queued')
  → ci_jobs 에 ingest 잡 1건 적재
  → 화면: "1건 수집을 시작했습니다"
  → ★ 여기서 끝. 잡을 처리하는 워커를 부르는 것이 아무것도 없다.
```

워커를 수동으로 돌렸다고 가정해도:

```
handleIngest → 영상 메타 수집 → upsertChannel 로 채널 행 생성
  → is_monitored = false, 채널 스윕 잡 없음        (handlers.ts:235)
  → 그 채널의 형제 게시물 0건
  → derive: 비교군을 source='monitoring' 인 형제로만 센다  (derive.ts:56 + corpus.ts)
     inbox 로 넣은 건의 형제는 0 → outlier_baseline_n = 0
  → 8 미만이라 배수 미산출                          (metrics.ts:8)
  → 배수 1.5 미만이라 크리에이티브 분석 미발화       (stages.ts:505)
  → ★ "왜 잘 됐나"는 영원히 나오지 않는다.
```

**결과: 영상 링크 1개로는 의도한 것 중 아무것도 얻지 못한다.**

### 3-B. 유튜브 **채널/프로필** 링크를 같은 칸에 넣는다

```
parseContentUrl(채널URL) → null                    (ingest/route.ts:43)
  → rejected: "유튜브, 틱톡, 인스타, 페북, X, 스레드 링크만 받을 수 있습니다"
```

**거부된다.** 채널 등록은 `/ci/monitoring` 화면의 **다른 입력칸 + 다른 API**(`POST /api/ci/channels`)로만 된다. 즉 **입구가 2개이고 서로를 모른다.**

### 3-C. 어시스턴트에 물어본다

```
"무엇이든 물어보세요" (placeholder)
  → parseIntent = 정규식 12개.  LLM 호출 0.  대화 이력 0.
  → 채널 URL 만 붙이면: "채널/구독/관심" 단어가 없어 ingest.add 로 → 파싱 실패 → "지원하지 않는 주소"
  → "왜 이게 잘됐어?" · "추성훈 채널에서 제일 잘된 영상" · "이 채널 분석해줘"
     → 전부 "무슨 뜻인지 확실하지 않아 아무것도 실행하지 않았습니다"
```

**사용자가 말한 "아예 말을 안 듣는다"는 정확한 관찰이다. 어시스턴트에는 AI가 없다.**

### 3-D. 홈 입력칸에 자연어를 넣는다 (제품이 스스로 유도한다)

홈 입력칸 placeholder는 `"무엇을 도와드릴까요. 링크를 붙여넣거나 예: 요리 주제에서 이번 주 떡상 보여줘"`(HomeView.tsx:57).
그런데 이 칸은 **오직 `/api/ci/ingest`로만 보낸다.** 문장을 넣으면 공백으로 쪼개(LinkIntakeBox.tsx:28) 단어 6개를 URL로 전송 → **오류 6줄**이 뜬다.

> 제품이 자기 입으로 시킨 행동을 자기가 오류로 되돌려준다. 신뢰가 여기서 무너진다.

## 5. 사용자가 짚지 않은 것 — 추가로 발견한 것

> 지시 범위 밖이거나 사용자가 언급하지 않은 발견 **8건**. 고치지 않았고 여기 기록만 한다.

1. **설정 21개 중 9개가 소비처 0.** 바꿔도 아무 일이 일어나지 않는다.
   `ingest.refresh_interval_hours` · `ingest.collect_window` · `data.retention_days` · `analysis.size_bands` · `ai.automation_level` · `ai.daily_call_limit` · `publish.default_time` · `publish.checklist` · `alert.brief.send_at` · `notify.channels` · `account.timezone`
   → 이 프로젝트의 알려진 함정("표·설정만 만들고 소비 코드 0")이 **그대로 재발**했다.
2. **`analysis.size_bands` 소비처 0의 결과**: `size_band` 열을 **쓰는 코드는 있는데 채우는 코드가 없다.** 채널 상세의 "규모 구간"은 **영구히 "판정 전"**이다.
3. **"일간 브리핑"은 설정만 있고 발송 코드가 없다.** `alert.brief.send_at`을 아무리 맞춰도 아무것도 오지 않는다.
4. **`notify.channels`는 수신 채널을 고르게 하지만 실제 발송은 앱 내 `ci_notifications`뿐.** 외부 전달 경로가 없다.
5. **홈 "자동 업데이트" 카드가 거짓 신호를 준다.** `newCount`는 **성공한 잡 수**이지 새 콘텐츠 수가 아니다. 진행률은 최근 잡 200건 기준이라 큐가 비면 영구히 "대기 · 100% · 신규 200"으로 굳는다. (`queries/home.ts:64-92`)
6. **주제가 1개면 모든 콘텐츠가 그 주제로 자동 배정된다**(확신도 0.55). 콜드 스타트 배려로 넣은 의도적 설계지만, **실측 결과 PSY·Luis Fonsi·OneRepublic·"Me at the zoo"가 전부 "요리"로 태깅**돼 있다. 이 값이 `topic_percentile`(같은 주제 상위 %) 모집단에 그대로 들어가 **지표를 오염**시키고, 검토 큐를 21건 중 19건으로 부풀린다. (`analysis/classify.ts:84`)
7. **핸들이 URL 인코딩된 채 저장된다.** 실측: `@%C3%A4%CC%872`. 디코딩 단계가 없다.
8. **채널 스윕 실패는 수집함에서 볼 수 없다.** 홈 카드의 "실패 N건 보기"는 `/ci/inbox?tab=failed`(콘텐츠 목록)로 가는데, 채널 대상 실패 잡은 콘텐츠가 아니라 거기 뜨지 않는다.

## 6. 구조적 한계 — 기획을 바꿔야 하는 것

**이 두 가지는 코드를 아무리 고쳐도 해결되지 않는다. 기획 차원의 결정이 필요하다.**

### 6-1. "계정의 모든 게시물"은 **유튜브에서만** 가능하다

`fetchChannelFeed`는 유튜브가 아니면 즉시 거부한다:

```
lib/ci/connectors/channel-feed.ts:96
  "{platform}는 공개 게시물 목록을 제공하지 않아 채널 일괄 수집을 할 수 없습니다.
   게시물 링크를 직접 넣어 주세요"
```

틱톡·인스타·페이스북·X·스레드는 **콘텐츠 링크 1건씩**만 처리된다(oEmbed/메타태그). 이건 우리 구현의 부족이 아니라 **각 플랫폼이 공개 목록을 안 주기 때문**이다.

> **결정 필요**: "모든 플랫폼에서 계정 전체 분석"을 약속에서 내리고 **유튜브 우선**을 명시할 것인가, 아니면 비공식 경로(스크래핑·서드파티 API)를 감수할 것인가. 지금처럼 화면이 6개 플랫폼을 나란히 약속하면 5개에서 반드시 실망한다.

### 6-2. ~~유튜브도 API 키가 없으면 최근 15개만 본다~~ → **정정: 키는 있다. 막는 것은 다른 둘이다**

> **1차 보고 정정.** 채널에 남은 오류 문구(`"YouTube API 키가 없어…"`)를 근거로 "키가 없다"고 보고했다. **틀렸다.**
> DB에 키가 있고(39자), 실제로 호출해 유효함을 확인했다 — 추성훈 채널 **544개**와 uploads 재생목록이 정상 응답한다.
> 그 문구는 **08-12 스윕 당시의 기록**이다. 그 뒤 키가 추가됐지만 **아무도 다시 훑지 않아 15개인 채로 굳어 있다.**

정정하고 나니 "전량 수집"을 막는 진짜 원인 둘이 드러난다. **둘 다 우리가 고칠 수 있는 것이다.**

**① 재훑기가 없다** (P1-1의 직접 피해). 스윕은 채널을 추가한 시점에 한 번 돈 것이 전부다. **조건이 좋아져도 시스템이 스스로 다시 시도하지 않는다.**

**② 중복 채널이 전량 수집을 막는다** (P0-5와 연결된 새 발견).

```
lib/ci/jobs/stages.ts:337-343
  const realChannelId = isProvisionalKey(ch.external_id) ? null : ch.external_id
  const full = platform==='youtube' && realChannelId ? await fetchAllUploads(...) : null
```

`handle:@…` 임시 키로 만들어진 채널 행은 **키가 있어도 전량 경로를 아예 시도하지 않고** RSS(15개)로 내려간다.
실측상 추성훈은 두 행으로 쪼개져 있고 그중 하나가 `handle:@choosunghoon_ajossi`다.

> **결론: 6-2는 "결정이 필요한 전제 조건"이 아니라 "P0-5 + P1-1을 고치면 사라지는 결함"이다.**
> 키 발급 결정도, 쿼터 예산도 필요 없다 — 544개 전량 수집이 12유닛, 일 한도 10,000의 **0.12%**다.

### 6-3. 그래도 남는 진짜 한계: 시계열

실행 경로를 무엇으로 정하든, **지표 스냅샷이 정해진 시각에 찍혀야 "조회 속도"와 "평소 대비"가 성립한다.**
실측상 콘텐츠 21건 중 **다음 촬영이 예약된 것은 1건**뿐이다(나머지는 추적 종료 판정으로 삭제됨). 시계열이 사실상 없다.
→ 접속자 기반은 사람이 없는 시간에 촬영이 밀린다. 그래서 §7-0에 **백스톱과 지연 표기**가 함께 들어간다.

## 7. 재설계 — 목표 상태

### 7-0. 실행 경로 — 크론을 늘리지 않고 큐를 돌린다

> **요구**: 크론은 부가 비용이 드니 **첫 접속자가 큐를 처리**하게 하고 싶다.
> **결론**: 가능하다. 그리고 실측해 보니 **접속자 트리거의 최대 난제가 이미 해결돼 있다.** 다만 선행 수정 3개와 백스톱 1개가 필요하다.

#### 먼저, 비용의 실체를 정확히

| 통념 | 실측 |
|---|---|
| "크론을 추가하면 비용이 붙는다" | Vercel은 크론 자체에 요금을 매기지 않는다. 과금 대상은 **크론이 부른 함수의 실행 시간**이다 |
| "지금은 크론이 없다" | **이미 `/api/cron/analyze-drain`이 매분(`* * * * *`) 돌고 있다** (`apps/web/vercel.json:14-16`) |

즉 **진짜 비용은 "크론이냐 아니냐"가 아니라 "얼마나 자주, 얼마나 오래 도느냐"**다.
그리고 이미 매분 도는 크론이 있으므로, **거기에 CI 드레인을 얹으면 크론 슬롯 추가는 0**이다.

→ 그래서 **접속자 트리거를 주 경로로, 기존 크론 편승을 백스톱으로** 두는 것이 가장 싸다.

#### 선행 수정 (이거 없이 접속자 트리거를 켜면 사고가 난다)

| | 무엇 | 왜 접속자 트리거에서 치명적인가 |
|---|---|---|
| **P0-6** | `claimJobs`가 `running` 좀비를 회수하지 않는다 | **브라우저를 닫을 때마다 잡이 `running`으로 죽는다.** 크론은 한 프로세스가 끝까지 돌지만 접속자는 언제든 이탈한다. 회수 없이는 큐가 좀비로 막힌다 |
| **P0-7** | `claimJobs`에 워크스페이스 경계가 없다 | 서비스 토큰으로만 부를 땐 무해했다. **사용자 세션으로 트리거하는 순간 남의 워크스페이스 잡을 처리**하게 된다 |
| **신규** | 워커가 `CI_WORKER_TOKEN`만 받는다 | 브라우저가 부를 엔드포인트는 **세션 인증**이어야 한다. 토큰을 클라이언트에 내보내면 큐가 외부에 열린다 |

#### 왜 "응답 후 백그라운드"가 아니라 "브라우저가 때리는" 방식인가

서버에서 응답을 먼저 보내고 뒤에서 계속 일하려면 런타임 지원이 필요한데, 실측 결과 **둘 다 없다**:

```
Next.js 14.2.29   → after() 없음 (Next 15부터 도입)
@vercel/functions → 미설치 (waitUntil 사용 불가)
```

아무 장치 없이 `void doWork()`로 던지면 **Vercel이 응답 반환 시점에 인스턴스를 동결/종료해 작업이 잘린다.**
패키지를 추가하는 선택지도 있지만, 이 제품에는 **브라우저가 때리는 방식이 더 낫다** — 의존성 0이고, 화면을 보는 동안 크론보다 촘촘하게 돌며, 진행 상황을 그 자리에서 보여줄 수 있다.

#### 설계: 3겹

**A. 주 경로 — 브라우저 하트비트 (비용 0 · 의존성 0)**

```
CI 셸에 <QueueDriver /> 클라이언트 컴포넌트를 하나 마운트한다

  화면 진입      → 즉시 POST /api/ci/queue/drain   (세션 인증)
  이후            → document.visibilityState === 'visible' 인 동안만 N초 간격 반복
  응답에 remaining → 남아 있으면 간격을 줄여 몰아친다 / 0이면 간격을 늘린다

서버(/api/ci/queue/drain)
  · requireCiMemberApi 로 세션·워크스페이스 확정
  · claimJobs(limit=5, workspaceId) — 소량만
  · 실행 예산 8초를 넘기면 남은 건 다음 틱으로 넘기고 즉시 반환
  · { processed, remaining, stuck } 을 돌려준다
```

- **첫 접속자가 기다리지 않는다.** 소량·짧은 예산으로 끊고, 나머지는 다음 틱이 가져간다.
- **동시 접속 안전.** `claimJobs`가 이미 조건부 UPDATE로 원자적이라(`queue.ts:96-110`) 같은 잡을 두 번 집지 않는다. **접속자 트리거의 가장 큰 난제가 이미 풀려 있다.**
- **폭주 방지.** 워크스페이스 단위로 "마지막 드레인 이후 X초 미만이면 스킵"을 둔다. 외부 API 쿼터를 동시에 태우지 않기 위해서다.
- **화면이 정직해진다.** "수집 중 3/12"를 그대로 보여준다 — 지금 홈의 가짜 "자동 업데이트" 카드(§5-5)를 이 진짜 신호로 교체한다.

**B. 백스톱 — 이미 도는 크론에 얹기 (크론 추가 0)**

`/api/cron/analyze-drain`에 CI 드레인 호출을 더한다. 이미 매분 도니 **스케줄도 슬롯도 늘지 않는다.**
비용이 걱정되면 게이트를 단다: *"마지막 CI 드레인 이후 15분이 지났을 때만 실행"* — 할 일이 없으면 수백 ms에 끝난다.

- 이걸 빼면: **밤새 아무도 안 들어오면 스냅샷도 채널 재훑기도 멈춘다.** "평소 대비"와 "조회 속도"는 시계열이라 정확도가 직접 깎인다(§6-3).
- 사장님이 크론을 아예 원치 않으시면 B는 빼도 A만으로 동작한다. **다만 그때는 "사람이 접속한 날에만 데이터가 자란다"는 것을 화면이 말해야 한다** — 조용히 비어 있으면 안 된다.

**C. 정직성 규약 — 밀린 것을 숨기지 않는다**

- 스냅샷에 **예정 시각 대비 실제 촬영 지연**을 남기고, 속도(velocity)는 예정 간격이 아니라 **실제 간격**으로 계산한다.
- 채널 카드에 **"마지막 훑은 시각 / 다음 예정"**을 표시한다. 접속이 없어 밀렸으면 밀렸다고 보인다.
- 큐가 N분 이상 안 돌면 홈에 **"수집이 멈춰 있습니다"**를 띄운다. 조용한 정지 금지.

#### 이 방식이 크론보다 나은 점 / 못한 점

| | 브라우저 하트비트(A) | 크론 |
|---|---|---|
| 비용 | 사람이 볼 때만 실행 → **사실상 0** | 할 일이 없어도 매번 깨어난다 |
| 반응 속도 | 화면 여는 즉시 · 이후 수십 초 간격 | 스케줄 간격에 묶임 |
| 진행 표시 | **그 자리에서 보인다** | 다음 새로고침까지 모름 |
| 무인 시간 | ❌ **아무도 없으면 안 돈다** | ✅ 돈다 |
| 중단 내성 | 브라우저 이탈 시 잡이 죽는다 → **P0-6 선행 필수** | 프로세스가 끝까지 돈다 |

> 요약하면 **A는 "사람이 볼 때 빠르고 공짜", B는 "사람이 없을 때 최소한"**이다. 둘을 겹치면 크론을 늘리지 않고도 빈틈이 없다.

### 7-1. 입구는 하나, 종류는 시스템이 판별한다

```
사용자: 링크 1개 (무엇이든)
   ↓
parseAnyCiUrl(input)          ← 신설 SSOT (ucm/url.ts 안에서 content/channel 판별을 합친다)
   ↓
 ├ kind='channel'  → 채널 등록 + 즉시 전체 훑기 + 모니터링 ON 제안
 └ kind='content'  → 콘텐츠 적재 + ★그 채널을 함께 확보하고 전체 훑기를 동반 예약★
   ↓
 어느 쪽이든 결과 화면은 같다: "이 계정" 화면
```

핵심 변경: **콘텐츠 링크가 채널 훑기를 반드시 동반한다**(불변식 I-1). 다만 훑기는 사용자 요청 경로에서 동기 실행하지 않고 잡으로 건다. 화면은 "이 계정 전체를 훑고 있습니다 — 지금까지 N/M"을 진행 상태로 보여준다.

### 7-2. 화면: "계정 화면"이 1급 시민이 된다

지금은 수집함(1)·모니터링(2)·트렌드(3)의 3단계 흐름이고 채널은 목록의 한 행이다. 의도에 맞추려면 **채널(계정)이 분석의 단위**가 되어야 한다.

| 구역 | 지금 | 목표 |
|---|---|---|
| 모니터링 목록 | 채널명·플랫폼·구독자·주제·상태 | + **수집 N/전체 M · 마지막 훑은 시각 · 최근 떡상 건수 · 최고 배수 · 다음 훑기 예정** |
| 채널 상세 | 게시물 카드 격자(정렬 없음) | **① 계정 요약(평소 조회수 중앙값·업로드 주기·주 포맷) ② 잘 된 게시물 상위 N(배수순 기본) ③ 왜 잘 됐나 — 상위군 vs 중앙군 대조표 ④ 전체 게시물(정렬·필터)** |
| 수집 한계 | `sweep_error` 한 줄 | 상시 배지: "543개 중 15개(2.8%)만 봅니다 — 전체를 보려면 YouTube API 키 필요" + 설정 바로가기 |

### 7-3. "왜 잘 됐나"를 계정 단위로 산출한다 (가장 큰 기획 공백)

현재 `ci_patterns`는 **주제 단위**라 계정 1곳에서는 절대 뜨지 않는다. **채널 단위 대조 분석**을 신설한다.

```
채널 C 의 게시물 N건 중
  상위군 = outlier_index 상위 20% (최소 3건)
  중앙군 = 중앙값 ±20% (최소 3건)
두 군의 관측 가능한 차이를 나열한다:
  - 썸네일 유형/문구 길이 · 후킹 유형 · 제목 패턴
  - 길이(초) 중앙값 · 발행 요일/시각 · 키워드
각 항목마다: 상위군 비율 vs 중앙군 비율 + 표본 수 + "근거 부족" 판정
```

**규칙**: 표본이 얇으면 공식을 만들지 않고 **"아직 말할 수 없다 — N건 더 필요"**를 표시한다. (기존 승격 기준 철학 유지)
**그리고 크리에이티브 분석 발화 조건을 바꾼다**: 상위군만이 아니라 **중앙군도 분석**해야 대조가 성립한다(P2-2).

### 7-4. 모니터링을 실제로 "지켜보게" 한다

```
신설 잡: channel.sweep.due  (워크스페이스 단위, 워커 tick 때 함께)
  대상: is_monitored = true 이고
        last_sweep_at < now() - ingest.refresh_interval_hours
  → 채널 스윕 잡을 건다
```
+ `isMonitored` 토글 ON 시 즉시 1회 스윕
+ 채널 행에 "다음 훑기 예정" 표시 → 사용자가 살아 있음을 눈으로 본다

### 7-5. 어시스턴트를 진짜 AI로

```
사용자 발화
  ↓
① 규칙 해석 (지금 것 유지 — 빠르고 공짜, LLM 장애 시 폴백)
  ↓ 못 잡으면
② LLM 의도 해석: 커맨드 카탈로그 + 현재 화면(route·대상 id) + 최근 대화 3턴을 주고 고르게 한다
  ↓
③ 실행 등급은 지금 규약 유지 (safe/write 실행 · guarded는 제안만) ← 이 설계는 옳다, 지킨다
  ↓
④ 답변: 목록만이 아니라 "왜"에 답한다
```

**신설 커맨드**
| 커맨드 | 답하는 질문 |
|---|---|
| `content.explain` | "이거 왜 잘됐어?" → 해당 콘텐츠의 배수·백분위·속도 + 크리에이티브 + 발행 맥락을 **문장으로** |
| `channel.analyze` | "이 계정 분석해줘" → §7-3 대조 결과 요약 |
| `channel.top` | "여기서 제일 잘된 거" → 배수 상위 N |
| `data.status` | "왜 데이터가 없어?" → 수집 진행·한계·막힌 지점 (이게 없어서 사용자가 고장을 진단할 수 없다) |

**동시에 정리할 것**: `route` 실제 사용 · "바꿔/변경" 하이재킹 제거 · 죽은 커맨드 2개 처리 · placeholder를 실제 능력에 맞추기(또는 능력을 올리기 — 후자 권장).

## 8. 실행 계획

각 단계는 **"무엇이 끝났다고 말할 수 있는가"**를 함께 정의한다. 검증 없이 다음으로 넘어가지 않는다.

### 단계 0 — 심장 박동 (없으면 나머지가 전부 무의미) · **크론 추가 없음**
선행 3개를 먼저 고친다. 순서를 바꾸면 사고가 난다.
1. **P0-6** `claimJobs`가 `running` + `locked_at < now()-5분`인 잡도 회수하도록 (기존 `analyze-drain`의 STALL 규약과 동일하게 맞춘다)
2. **P0-7** `claimJobs(limit, workerId, workspaceId)` — 워크스페이스 경계 추가
3. **세션 인증 드레인 엔드포인트** `POST /api/ci/queue/drain` 신설 (`requireCiMemberApi`, 소량·짧은 예산, `{processed, remaining}` 반환). 기존 토큰 워커는 그대로 둔다
4. CI 셸에 `<QueueDriver />` 마운트 — 화면이 보이는 동안만 반복 (§7-0 A)
5. 백스톱: 기존 `analyze-drain`에 CI 드레인 1줄 + "15분 게이트" (§7-0 B · **채택 여부는 §9-2 결정**)
6. 큐가 멈추면 홈에 **"수집이 멈춰 있습니다"** — 조용한 정지 금지

- **완료 판정 ①**: 링크를 넣고 **화면만 열어둔 채** 수십 초 뒤 제목·썸네일·지표가 채워진다
- **완료 판정 ②**: 처리 도중 **탭을 닫았다가 다시 열면** 남은 잡이 이어서 처리된다(좀비 없음)
- **완료 판정 ③**: 두 탭을 동시에 열어도 같은 잡이 두 번 실행되지 않는다(`ci_job_runs`로 확인)

### 단계 1 — 링크 단일 입구
- `parseAnyCiUrl` SSOT 신설, ingest가 채널/콘텐츠를 모두 받는다 (P0-2)
- 콘텐츠 링크가 채널 스윕을 동반 예약 (P0-3)
- 채널 잡 체인 분기 수정 (P0-4)
- **완료 판정**: 채널 URL·영상 URL·숏츠 URL·`@handle` 4종을 **같은 칸**에 넣어 전부 "이 계정" 화면에 도달

### 단계 2 — 채널 동일성 (데이터 신뢰의 기반)
- `parseChannelPage`가 **페이지 소유자 ID만** 취하도록 수정 (canonical / `channelMetadataRenderer.externalId` 우선, 첫 매칭 금지)
- `addChannel` 양방향 조회(핸들로 기존 `UC…` 행 탐색)
- 기존 중복 5쌍 병합 마이그레이션(콘텐츠 재귀속 + 파생값 재계산) — **되돌릴 수 없으므로 사용자 승인 필요**
- 핸들 URL 디코딩
- **완료 판정**: 같은 채널을 `@handle`·`/channel/UC…`·영상 링크 3경로로 넣어도 **행이 1개**. 저장된 `UC…`가 실제 소유자와 일치(YouTube API로 대조)

### 단계 3 — 모니터링을 살린다
- 주기 재훑기 잡 + `ingest.refresh_interval_hours` 실제 소비 (P1-1,3)
- `isMonitored` ON 시 즉시 스윕 (P1-2)
- 목록에 수집률·마지막/다음 훑기·최근 떡상 노출 (P1-5)
- **완료 판정**: 모니터링 ON 후 설정한 주기가 지나면 사람이 아무것도 안 해도 새 게시물이 늘어난다

### 단계 4 — "왜 잘 됐나"를 계정 단위로
- 채널 단위 대조 분석 신설 (§7-3)
- 크리에이티브 분석에 중앙군 포함 (P2-2)
- 채널 상세 재구성 (§7-2)
- **완료 판정**: 게시물 30건 이상 있는 채널에서 "상위군은 X가 n/m, 중앙군은 k/m"이 **표본 수와 함께** 나온다. 표본이 얇으면 "말할 수 없다"가 나온다

### 단계 5 — 어시스턴트
- LLM 의도 해석 + 폴백 (§7-5)
- 신설 커맨드 4개 · 컨텍스트 실사용 · 하이재킹 제거 · 대화 이력
- **완료 판정**: "이거 왜 잘됐어?" "이 계정 분석해줘" "왜 데이터가 없어?" 3개에 **근거 있는 문장**으로 답한다

### 단계 6 — 정직성 부채 청산
- 소비처 0 설정 9개: **구현하거나 화면에서 내린다.** (그대로 두는 것이 최악)
- `size_band` 산출 · 홈 "자동 업데이트" 신호 정정 · 단일주제 자동배정을 '가배정'으로 표시하고 백분위 모집단에서 제외
- **완료 판정**: 설정 화면의 모든 항목에 대해 "바꾸면 무엇이 달라지는가"를 한 줄로 답할 수 있다

## 10. 검증 계획 — "진짜 되는가"를 어떻게 증명하나

이 프로젝트에서 **tsc·lint·단위 테스트가 전부 초록인데 브라우저가 결함을 잡아낸 전례**가 반복됐다. 그래서 완료 판정은 정적 검증이 아니라 **실제 경로 관측**으로 한다.

1. **엔드투엔드 1회**: 새 워크스페이스 → 채널 링크 1개 투입 → **사람이 아무것도 하지 않고** 대기 → 게시물 N건, 배수, 상위/중앙 대조가 화면에 뜨는지
2. **동일성 검증**: 같은 채널 3경로 투입 → 채널 행 1개 · 저장된 `UC…`가 YouTube API 응답과 일치
3. **지속성 검증**: 모니터링 ON 후 주기 경과 → 자동으로 게시물이 늘어나는지
4. **어시스턴트**: 준비된 질문 10개(잘 되는 것 4 / 애매한 것 3 / 못 하는 것 3)로 회귀 세트를 만들고, **못 하는 것에는 못 한다고 답하는지**까지 본다
5. **가드 신설**: 설정 키에 소비처가 없으면 실패하는 정적 테스트(§5-1 재발 방지) — 이 프로젝트의 알려진 함정이므로 가드가 필요하다

> **이번 점검에서 브라우저 실화면 검증은 하지 않았다.** dev 서버(:3000)는 살아 있으나 여러 세션이 공유하는 환경이고, 로그인 세션 확보와 운영 워커 수동 기동이 필요해 **다른 세션의 작업 상태를 오염시킬 위험**이 있었다. 위 결함은 전부 **소스 + 운영 DB 실측**으로 확인했다.

## 11. 하지 말 것

- **화면부터 손대지 말 것.** 지금 UI가 비어 보이는 진짜 이유는 UI가 아니라 **데이터가 안 들어오기 때문**이다. 단계 0~2 없이 화면을 고치면 예쁜 빈 화면이 된다.
- **"모르는 것을 모른다고 말하는" 현재 설계를 훼손하지 말 것.** `completeness`·`sweep_error`·"543개 중 15개"·"근거 부족"은 이 시스템의 **가장 잘 만들어진 부분**이다. 데이터가 얇다고 추정치로 채우면 제품이 거짓말을 시작한다.
- **어시스턴트에 guarded 실행을 열지 말 것.** "되돌리기 어려운 일은 AI가 몰래 하지 않는다"는 현재 규약은 옳다.
- **새 표·새 설정을 먼저 만들지 말 것.** 이 프로젝트는 이미 같은 실수를 했다(설정 9개 소비처 0). **소비하는 코드를 먼저 쓰고 그 다음에 저장소를 만든다.**
- **병렬 시스템 신설 금지.** 목록은 `ListToolbar/ListSurface/ListPager`, 상태는 `EmptyState/ErrorState/SkelList`를 쓴다. 채널 화면도 예외가 아니다.
