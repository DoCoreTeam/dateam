1차 보고 정정 — “유튜브 API 키가 없다”는 틀렸다

채널에 남은 오류 문구("YouTube API 키가 없어…")를 근거로 삼았는데, 그건 08-12 스윕 당시의 기록이었다. 그 뒤 키가 추가됐지만 아무도 다시 훑지 않아 15개인 채로 굳어 있는 것이다. 이 정정으로 “전량 수집을 막는 것”이 키가 아니라 재훑기 부재(P1-1) + 중복 채널(P0-5)임이 드러났다 — 둘 다 우리가 고칠 수 있다.

관측 / 링크를 넣는 순간

지금 실제로 일어나는 일

① 유튜브 영상 링크를 홈 입력칸에 넣는다

POST /api/ci/ingest
  → ci_contents 1행 생성 (source='inbox', ingest_status='queued')
  → ci_jobs 에 ingest 잡 1건 적재
  → 화면: "1건 수집을 시작했습니다"
  → 여기서 끝. 이 잡을 처리하는 워커를 부르는 것이 없다.

워커를 수동으로 돌렸다고 가정해도:

handleIngest → 영상 메타 수집 → upsertChannel 로 채널 행 생성
  → is_monitored=false, 채널 스윕 잡 없음
  → 그 채널의 형제 게시물 0건
  → 비교군은 source='monitoring' 인 형제만 센다 → baseline_n = 0
  → 8 미만이라 배수 미산출
  → 배수 1.5 미만이라 크리에이티브 분석 미발화
  → "왜 잘 됐나"는 영원히 나오지 않는다.

② 유튜브 채널·프로필 링크를 같은 칸에 넣는다

parseContentUrl(채널URL) → null
  → rejected: "유튜브, 틱톡, 인스타, 페북, X, 스레드 링크만 받을 수 있습니다"

채널 등록은 /ci/monitoring 화면의 다른 입력칸 + 다른 API로만 된다. 입구가 둘이고 서로를 모른다.

“아예 말을 안 듣는다”는 정확한 관찰이다. 어시스턴트에는 AI가 없다.

④ 홈 입력칸에 자연어를 넣는다 — 제품이 스스로 유도한다

홈 입력칸은 "링크를 붙여넣거나 예: 요리 주제에서 이번 주 떡상 보여줘"라고 안내한다. 그런데 이 칸은 오직 수집 API로만 보낸다. 문장을 넣으면 공백으로 쪼개 단어 6개를 URL로 전송해 오류 6줄을 띄운다.

제품이 자기 입으로 시킨 행동을 자기가 오류로 되돌려준다. 신뢰가 여기서 무너진다.

통념실측
“크론을 추가하면 비용이 붙는다” Vercel은 크론 자체에 요금을 매기지 않는다. 과금 대상은 크론이 부른 함수의 실행 시간이다
“지금은 크론이 없다” 이미 /api/cron/analyze-drain이 매분 돌고 있다 — 크론 슬롯은 이미 열려 있다

즉 진짜 비용은 “크론이냐 아니냐”가 아니라 얼마나 자주, 얼마나 오래 도느냐다. 그리고 이미 매분 도는 크론이 있으므로 거기에 CI 드레인을 얹으면 크론 추가는 0이다. 그래서 접속자 트리거를 주 경로로, 기존 크론 편승을 백스톱으로 두는 것이 가장 싸다.

왜 “응답 후 백그라운드”가 아니라 “브라우저가 때리는” 방식인가

Next.js 14.2.29    → after() 없음 (Next 15부터 도입)
@vercel/functions  → 미설치 (waitUntil 사용 불가)

아무 장치 없이 void doWork()로 던지면 Vercel이 응답 반환 시점에 인스턴스를 동결·종료해 작업이 잘린다. 패키지를 추가하는 선택지도 있지만, 이 제품에는 브라우저가 때리는 방식이 더 낫다 — 의존성 0이고, 화면을 보는 동안 크론보다 촘촘하게 돌며, 진행 상황을 그 자리에서 보여줄 수 있다.

설계 — 3겹

A. 주 경로 — 브라우저 하트비트          (비용 0 · 의존성 0)

   CI 셸에 <QueueDriver /> 하나를 마운트한다
     화면 진입   → 즉시 POST /api/ci/queue/drain     (세션 인증)
     이후        → visibilityState==='visible' 인 동안만 N초 간격 반복
     remaining   → 남아 있으면 간격을 줄여 몰아친다 / 0이면 늘린다

   서버 /api/ci/queue/drain
     · requireCiMemberApi 로 세션·워크스페이스 확정
     · claimJobs(limit=5, workspaceId) — 소량만
     · 실행 예산 8초 초과 시 남은 건 다음 틱으로 넘기고 즉시 반환
     · { processed, remaining, stuck } 반환

B. 백스톱 — 이미 도는 크론에 얹기        (크론 슬롯 추가 0)
   analyze-drain 에 CI 드레인 1줄 + "마지막 드레인 후 15분 게이트"

C. 정직성 — 밀린 것을 숨기지 않는다
   예정 대비 실제 촬영 지연 기록 · 속도는 실제 간격으로 계산
   채널 카드에 "마지막 훑음 / 다음 예정" · 큐가 멈추면 홈에 경고

첫 접속자가 기다리지 않는다 — 소량·짧은 예산으로 끊고 나머지는 다음 틱이 가져간다. 동시 접속도 안전하다 — 잡 임대가 이미 조건부 UPDATE로 원자적이라 (queue.ts:96-110) 같은 잡을 두 번 집지 않는다. 그리고 지금 홈의 가짜 “자동 업데이트” 카드를 이 진짜 신호로 교체한다.

선행 수정 — 이거 없이 켜면 사고가 난다

항목무엇왜 접속자 트리거에서 치명적인가
P0-6running 좀비 회수 브라우저를 닫을 때마다 잡이 running으로 죽는다. 크론은 한 프로세스가 끝까지 돌지만 접속자는 언제든 이탈한다
P0-7워크스페이스 경계 사용자 세션으로 트리거하는 순간 남의 워크스페이스 잡을 처리하게 된다
신규세션 인증 드레인 워커는 서비스 토큰만 받는다. 토큰을 클라이언트에 내보내면 큐가 외부에 열린다

A와 크론, 무엇을 얻고 무엇을 잃나

브라우저 하트비트 (A)크론
비용사람이 볼 때만 실행 → 사실상 0할 일이 없어도 매번 깨어난다
반응 속도화면 여는 즉시 · 이후 수십 초 간격스케줄 간격에 묶임
진행 표시그 자리에서 보인다다음 새로고침까지 모름
무인 시간아무도 없으면 안 돈다돈다
중단 내성이탈 시 잡이 죽는다 → P0-6 선행 필수프로세스가 끝까지 돈다

A는 “사람이 볼 때 빠르고 공짜”, B는 “사람이 없을 때 최소한”이다. 둘을 겹치면 크론을 늘리지 않고도 빈틈이 없다.

재설계 / 목표 상태

어떻게 되어야 하나

입구는 하나, 종류는 시스템이 판별한다

사용자: 링크 1개 (무엇이든)
   ↓
parseAnyCiUrl(input)                     ← 신설 SSOT
   ↓
 ├ kind='channel'  → 채널 등록 + 즉시 전체 훑기 + 모니터링 ON 제안
 └ kind='content'  → 콘텐츠 적재 + 그 채널 전체 훑기를 반드시 동반
   ↓
 어느 쪽이든 도착지는 같다: "이 계정" 화면

“잘 됨”은 그 계정의 평소 대비로만 정의된다. 그러므로 콘텐츠 1건을 받으면 계정 전체 훑기는 선택이 아니라 필수다.

계정(채널)이 분석의 단위가 된다

구역지금목표
모니터링 목록 채널명 · 플랫폼 · 구독자 · 주제 · 상태 + 수집 N/전체 M · 마지막 훑은 시각 · 최근 떡상 건수 · 최고 배수 · 다음 훑기 예정
채널 상세 게시물 카드 격자, 정렬 없음 ① 계정 요약(평소 조회수 중앙값 · 업로드 주기 · 주 포맷)
② 잘 된 게시물 상위 N (배수순 기본)
③ 왜 잘 됐나 — 상위군 vs 중앙군 대조표
④ 전체 게시물(정렬 · 필터)
수집 한계 오류 문구 한 줄 상시 배지 — “543개 중 15개(2.8%)만 봅니다 · 전체를 보려면 API 키 필요” + 설정 바로가기

“왜 잘 됐나”를 계정 단위 대조로 산출한다

채널 C 의 게시물 N건 중
  상위군 = 배수 상위 20% (최소 3건)
  중앙군 = 중앙값 ±20%  (최소 3건)

두 군의 관측 가능한 차이를 나열한다
  · 썸네일 유형 / 문구 길이   · 후킹 유형     · 제목 패턴
  · 길이(초) 중앙값           · 발행 요일·시각 · 키워드

각 항목: 상위군 비율 vs 중앙군 비율 + 표본 수 + "근거 부족" 판정

표본이 얇으면 공식을 만들지 않고 “아직 말할 수 없다 — N건 더 필요”를 표시한다. 기존 승격 기준의 철학을 그대로 잇는다.

단계별 계획과 완료 판정

각 단계는 “무엇이 끝났다고 말할 수 있는가”를 함께 정의한다. 검증 없이 다음으로 넘어가지 않는다.

0

심장 박동 — 크론 추가 없음

  • P0-6 잡 임대가 running + 잠금 5분 초과인 잡도 회수하도록 (기존 드레인의 STALL 규약과 동일하게)
  • P0-7 잡 임대에 워크스페이스 경계 추가
  • 세션 인증 드레인 POST /api/ci/queue/drain 신설 — 소량·짧은 예산·remaining 반환. 기존 토큰 워커는 그대로 둔다
  • CI 셸에 <QueueDriver /> 마운트 — 화면이 보이는 동안만 반복
  • 백스톱: 기존 크론에 CI 드레인 1줄 + 15분 게이트 (채택 여부는 결정 필요)
  • 큐가 멈추면 홈에 “수집이 멈춰 있습니다” — 조용한 정지 금지

완료 판정 ① — 링크를 넣고 화면만 열어둔 채 수십 초 뒤 제목·썸네일·지표가 채워진다.

완료 판정 ② — 처리 도중 탭을 닫았다 다시 열면 남은 잡이 이어서 처리된다(좀비 없음).

완료 판정 ③ — 두 탭을 동시에 열어도 같은 잡이 두 번 실행되지 않는다.

1

링크 단일 입구

  • parseAnyCiUrl SSOT 신설 — 수집 API가 채널·콘텐츠를 모두 받는다
  • 콘텐츠 링크가 채널 스윕을 동반 예약
  • 채널 잡 체인 분기 수정

완료 판정 — 채널 URL · 영상 URL · 숏츠 URL · @handle 4종을 같은 칸에 넣어 전부 “이 계정” 화면에 도달한다.

2

채널 동일성 — 데이터 신뢰의 기반

  • 채널 페이지에서 소유자 ID만 취한다(첫 매칭 금지)
  • 채널 추가 시 핸들로 기존 UC… 행을 양방향 조회
  • 기존 중복 5쌍 병합 — 콘텐츠 재귀속 + 파생값 재계산 (되돌릴 수 없어 승인 필요)
  • 핸들 URL 디코딩

완료 판정 — 같은 채널을 3경로로 넣어도 행이 1개이고, 저장된 UC…가 실제 소유자와 일치한다(API로 대조).

3

모니터링을 살린다

  • 주기 재훑기 잡 신설 + refresh_interval_hours 실제 소비
  • 모니터링 ON 시 즉시 스윕
  • 목록에 수집률 · 마지막/다음 훑기 · 최근 떡상 노출

완료 판정 — 모니터링을 켜고 주기가 지나면 사람이 아무것도 하지 않아도 새 게시물이 늘어난다.

4

“왜 잘 됐나”를 계정 단위로

  • 상위군 vs 중앙군 대조 분석 신설
  • 크리에이티브 분석에 중앙군 포함(생존자 편향 제거)
  • 채널 상세 재구성

완료 판정 — 게시물 30건 이상 채널에서 “상위군은 X가 n/m, 중앙군은 k/m”이 표본 수와 함께 나온다. 얇으면 “말할 수 없다”가 나온다.

5

어시스턴트

  • LLM 의도 해석 + 규칙 폴백 · 신설 커맨드 4개
  • 화면 컨텍스트 실사용 · “바꿔/변경” 하이재킹 제거 · 죽은 커맨드 정리 · 대화 이력

완료 판정 — “이거 왜 잘됐어?” · “이 계정 분석해줘” · “왜 데이터가 없어?” 세 질문에 근거 있는 문장으로 답한다.

6

정직성 부채 청산

  • 소비처 0 설정 9개 — 구현하거나 화면에서 내린다(그대로 두는 것이 최악)
  • size_band 산출 · 홈 “자동 업데이트” 신호 정정
  • 단일 주제 자동배정을 ‘가배정’으로 표시하고 백분위 모집단에서 제외

완료 판정 — 설정 화면의 모든 항목에 대해 “바꾸면 무엇이 달라지는가”를 한 줄로 답할 수 있다.

유일하게 남은 실행 결정

사람이 없는 시간을 어떻게 할 것인가

접속자 트리거(A)는 확정. 문제는 밤·주말이다. ⓐ 이미 매분 도는 크론에 얹기(크론 추가 0 · 15분 게이트) / ⓑ A만 쓰고 “접속한 날에만 자란다”를 화면에 명시. ⓑ는 스냅샷이 밀려 “조회 속도”와 “평소 대비” 정확도가 깎인다 — 비용 문제가 아니라 정확도를 얼마나 포기할지의 문제다.

약속 수준

“계정 전체”를 유튜브 한정으로 명시할지, 나머지는 “링크 단건”으로 정직하게 낮출지.

되돌릴 수 없음

중복 채널 5쌍을 병합할 것인가

운영 DB 변경이다. 그리고 이걸 안 고치면 키가 있어도 전량 수집이 안 된다.

비용

AI 호출 상한을 어떻게 둘 것인가

계정 전체 훑기 × 대조 분석은 게시물 수에 비례한다. 채널당·일별 상한 정책이 필요하다.

첫 수확

어느 채널부터 열 것인가

병합 직후 재훑기를 걸면 추성훈 채널이 15 → 544건으로 늘어난다. 순서를 정해야 한다.

경계

하지 말 것

  • 화면부터 손대지 말 것. 지금 UI가 비어 보이는 진짜 이유는 UI가 아니라 데이터가 안 들어오기 때문이다. 단계 0~2 없이 화면을 고치면 예쁜 빈 화면이 된다.
  • “모르는 것을 모른다고 말하는” 현재 설계를 훼손하지 말 것. 완전도 · 수집 한계 · “543개 중 15개” · “근거 부족”은 이 시스템에서 가장 잘 만들어진 부분이다. 데이터가 얇다고 추정치로 채우면 제품이 거짓말을 시작한다.
  • 어시스턴트에 guarded 실행을 열지 말 것. “되돌리기 어려운 일은 AI가 몰래 하지 않는다”는 현재 규약은 옳다.
  • 새 표·새 설정을 먼저 만들지 말 것. 이미 같은 실수를 했다(설정 9개 소비처 0). 소비하는 코드를 먼저 쓰고 그 다음에 저장소를 만든다.
  • 병렬 시스템 신설 금지. 목록은 표준 부품, 상태는 공용 상태 부품을 쓴다. 채널 화면도 예외가 아니다.
검증

“진짜 되는가”를 어떻게 증명하나

이 프로젝트에서 타입 검사·린트·단위 테스트가 전부 초록인데 브라우저가 결함을 잡아낸 전례가 반복됐다. 그래서 완료 판정은 정적 검증이 아니라 실제 경로 관측으로 한다.

  1. 엔드투엔드 1회 — 새 워크스페이스에 채널 링크 1개 투입 → 사람이 아무것도 하지 않고 대기 → 게시물·배수·대조가 화면에 뜨는지
  2. 동일성 — 같은 채널 3경로 투입 시 채널 행 1개, 저장된 ID가 플랫폼 응답과 일치
  3. 지속성 — 모니터링 ON 후 주기 경과 시 자동으로 게시물이 늘어나는지
  4. 어시스턴트 회귀 세트 — 질문 10개(되는 것 4 / 애매한 것 3 / 못 하는 것 3). 못 하는 것에 못 한다고 답하는지까지 본다
  5. 가드 신설 — 설정 키에 소비처가 없으면 실패하는 정적 테스트. 이 프로젝트의 알려진 함정이므로 가드가 필요하다

이번 점검에서 브라우저 실화면 검증은 하지 않았다. 개발 서버는 살아 있으나 여러 세션이 공유하는 환경이고, 로그인 세션 확보와 운영 워커 수동 기동이 필요해 다른 세션의 작업 상태를 오염시킬 위험이 있었다. 위 결함은 전부 소스 + 운영 DB 실측으로 확인했다.
