# 목록 심층분석 — "원문 대비 나아졌나/생략됐나" 불투명성 진단 + 검증·해소 기획

> 상태: **분석·기획만 (구현 금지 — 사용자 명시)**. 2026-07-25.
> 질문 원문: "붙여넣은 것 대비 뭐가 나아졌는지·생략됐는지·더 좋은지 나쁜지 알 수가 없다. 양은 줄고 구체화는 떨어지는 느낌. 어떻게 검증하고, 내 우려를 다 보완할 수 있나. 내가 놓친 것까지."

---

## A. 진단 — 왜 그렇게 느껴지나 (코드 근거)

### A-1. 결과는 원문을 **대체(replace)**하지 증강하지 않는다 → 비교 자체가 불가능
- `grouping-actions.ts:125` `item_text = g.title` — 항목에 저장되는 건 **그룹 제목만**(예: "4.1 계정 및 인증").
- 원문 전체 `body_raw`(=`g.bodyRaw`)는 DB에 있지만, **결과 화면(`AnalysisResultItem`)은 `제목 + AI result_text`만 렌더**한다. 원문은 검수 단계(`GroupList`)에서만 보이고 결과에선 사라진다.
- ∴ 사용자는 **"내가 넣은 것"과 "AI가 낸 것"을 나란히 볼 화면이 없다.** "비교 불가"는 느낌이 아니라 구조적 사실.

### A-2. "압축 복원" 전제가 **이미 치밀한 정본 문서**와 정면충돌 → 양↓·구체화↓
- `refine-group.ts buildRefinePrompt`: 원문을 *"작성자가 큰 그림을 한 줄로 압축한 것"* 으로 규정하고 *"압축을 풀어 복원하라"* 고 지시.
- 그런데 붙여넣은 문서는 **FR-ID·수용기준·우선순위 표로 이미 고밀도**. 압축된 게 아니다.
- 이미 펼쳐진 표를 "복원하라"고 하면 AI는 **표를 산문으로 재서술** → 셀 구조 소실, 정보 밀도 하락, 결과적으로 **양이 줄고 덜 구체적**으로 보인다. → 사용자 체감과 정확히 일치.

### A-3. 품질·보존을 재는 장치가 **0** → 시스템도 "나아졌나"를 모른다
- `checkCoverage`는 **취합문이 각 항목 idx를 언급했는지**(라인/인덱스 커버리지)만 본다.
- **원문의 숫자·ID·수용기준이 결과에 남았는지(보존율), 없는 내용을 지어냈는지(충실도)** 를 재는 코드가 전무(grep 0건).
- ∴ "생략됐나 / 더 좋아졌나 / 더 나빠졌나"에 대해 **UI도, 시스템도 아무 신호를 주지 않는다.**

## B. 사용자가 놓친 사각지대 (blind spots)

1. **도구의 원래 용도 역전**: 이 기능은 *희소한 목록*("사용자 확보 10만 명" 한 줄)을 펼치는 설계다. **이미 완성된 정본 문서**를 넣으면 목적이 뒤집힌다(펼칠 게 없는데 펼치라니 → 요약/환각).
2. **"무손실 0줄" 배지의 오해**: 무손실은 **그룹핑 단계의 라인 커버리지**만 보장(원문 줄이 어느 그룹엔가 담김). **항목 심화 단계는 무손실 보장이 없다** — AI가 재서술하며 내용을 잃을 수 있다. 배지를 전체 보장으로 읽으면 위험.
3. **입력 유형별로 필요한 게 정반대**: 희소 목록=확장/구체화, 고밀도 정본=**검증·갭발견·비평**. 한 모드로 둘 다 하려니 둘 다 어정쩡.
4. **모델 종속 품질**: 방금 넣은 flash-lite 폴백은 "완주"는 시키지만 pro 대비 **심화 깊이는 떨어질 수 있다.** "완료"가 곧 "고품질"은 아님.
5. **"더 좋다"의 정의 부재**: 무엇을 기준으로 "더 좋다"인가(정보 밀도? 실행가능성? 구조 보존? 통찰?)를 안 정하면 검증 자체가 성립 안 함.

## C. 검증 전략 — "나아졌나/생략됐나"를 객관 측정 (6종)

| # | 지표 | 정의 | 신호 |
|---|---|---|---|
| C-1 | **보존율(Retention)** | 원문 그룹의 핵심 엔티티(FR/NFR/D/V-ID·숫자+단위·고유명사·표 셀) 추출 → 결과에 남은 비율 | ID·수치 100% 목표, 미달=생략 경고 |
| C-2 | **정보 밀도 변화** | 입력 대비 출력의 (구조 항목 수·숫자 개수·문자수) | "양 줄었나"를 수치로 |
| C-3 | **충실도(Faithfulness)** | 결과의 각 주장이 원문/문서맥락에 근거하는가(LLM-judge: grounded/assumed/invented) | invented=환각 경고 |
| C-4 | **부가가치(Added value)** | 원문에 없던 유효정보(실행 절차·판단기준·수치)를 더했나 vs 단순 재서술 | 재서술만=심화 실패 |
| C-5 | **원문↔결과 diff** | 결과 옆 원문 나란히/토글, 추가=초록·삭제=빨강·변경 하이라이트 | 사용자가 직접 판단 |
| C-6 | **골든셋 평가** | 대표 문서 N개 + 기대 보존/부가가치 기준 → 회귀 자동 평가(GPU pricing golden-set 방식 재사용) | 배포 전 품질 게이트 |

> 핵심: C-1~C-4는 **자동 지표**(시스템이 판단), C-5는 **사람 판단 근거**(UI), C-6은 **회귀 방지**.

## D. 우려를 다 해소하는 설계 (해소 플랜 — 구현 아님)

### D-1. **증강 모드(augment)를 기본으로** — 양이 절대 안 줄게
- 원문을 **verbatim 보존** + 그 아래 "분석/보강"만 덧붙인다. 대체하지 않는다.
- 효과: 양 감소 원천 차단, 원문은 항상 그대로 남음, 구체성 손실 없음.
- 현 "대체(rewrite)" 모드는 **희소 목록 전용 옵션**으로 강등.

### D-2. **입력 유형 자동 판별 → 모드 분기**
- 고밀도 정본(표·ID 다수) → **검증/갭/비평 모드**(무엇이 빠졌나·모순·미결).
- 희소 목록(짧은 항목) → **확장/복원 모드**(현행).
- 문서유형 분류(`classify-doc`) 재활용 + "밀도" 신호(ID/표/평균 줄길이) 추가.

### D-3. **항목별 품질 배지**
- 카드에 3지표: "ID 12/12 보존 · 수치 8/8 · +5 실행기준 추가 · 환각 0". 한눈에 신뢰.

### D-4. **원문↔결과 diff 뷰**
- 카드에 "원문 비교" 토글(body_raw는 이미 저장돼 있음 — 표시만 배선).

### D-5. **생략 감지 + 보수 재생성**
- 원문 엔티티가 결과에서 빠지면 "누락: FR-103·30일·PASS인증" 경고 → 자동 보수 패스 1회.

### D-6. **모델 품질 고지**
- 폴백으로 경량 모델 사용 시 "경량 모델로 분석됨(pro 쿼터 소진)" 배지 → 기대치 관리.

## E. "다 해소 가능한가?" 판정

- **가능**: D-1(증강)·D-4(diff)·C-1(보존율)·D-5(생략경고)로 "생략·양감소·비교불가"는 **완전 해소**.
- **부분적 한계**: "객관적으로 더 좋아졌다"의 **완전 자동 판정은 불가능**(품질은 부분적으로 주관). 
  → 현실적 최선 = **시스템은 "무엇이 추가/삭제/유지됐고 무엇이 근거 없는가"까지 보장**하고, "더 좋은가"의 최종 판단은 **사용자에게 근거(diff+지표)와 함께 위임**. 
  → 이 경계를 UI로 명확히 하는 것이 진짜 해법. "AI가 다 판단해준다"는 환상을 팔지 않는다.

---

## F. 실행 순서 제안 (승인 시)

1. **P0(가치 최대·저비용)**: D-4 원문↔결과 diff 뷰 + D-1 증강 모드 기본화 → "비교 불가·양 감소" 즉시 해소.
2. **P1**: C-1 보존율 + D-5 생략 경고 + D-3 품질 배지 → "생략 여부" 자동 신호.
3. **P2**: D-2 모드 자동분기 + C-3 충실도 + C-6 골든셋 → 입력유형별 최적화·회귀방지.

> 각 단계는 독립 배포 가능. P0만으로도 사용자 핵심 우려(비교·양)는 풀린다.

## 검증 계획(이 기획이 맞는지) — 구현 착수 전 확인법
- 대표 문서 3종(희소 목록 / 고밀도 정본 / 혼합)으로 현행 vs 제안 모드 결과를 **보존율·밀도 수치로 대조** → 증강 모드가 실제로 양·보존을 지키는지 실측.
- diff 뷰 프로토타입으로 사용자가 "나아졌다"를 5초 안에 판단 가능한지 사용성 확인.
