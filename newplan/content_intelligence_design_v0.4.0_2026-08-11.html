v0.2.0에 대한 지적 4건을 그대로 받아들이고, 실제 제품 조사를 근거로 다시 설계한 버전

2.2 조사에서 도출한 결론 5가지

  1. 지표 언어는 배수다 시장 전체가 채널 평균 대비 몇 배를 공용어로 쓰고, 국내 커뮤니티는 이것을 떡상이라 부름 (평균 대비 2배 이상을 떡상 영상으로 정의하는 용례가 일반적)
  2. 메뉴는 동사형 그룹 4에서 5개 Create, Publish, Analyze처럼 하는 일 중심으로 묶고, 그 안에서 흐름이 이어짐
  3. 리서치와 제작은 끊기면 안 됨 발견한 것을 보드에 저장하고 바로 아이디어로 전개하는 연결이 제품의 몸통
  4. 매일 올 이유가 구독을 지킴 맞춤 피드, 알림, 브라우저 확장이 리텐션 3종 세트인데 v0.2.0에는 전부 없었음
  5. 국내 용어는 이미 존재함 관심 채널, 모니터링, 요즘 뜨는, 리포트처럼 검증된 한국어가 있으므로 새로 만들 필요가 없음

3.1 v0.2.0의 결함

결함내용과 영향
용어 원칙의 자기모순음차 금지를 원칙으로 세우고도 워치리스트, 아웃라이어, 니치, 킷 같은 음차 라벨을 그대로 채택함. 원칙과 결과가 어긋난 상태였음
IA가 도메인 나열백엔드 도메인 구분(UC-100대 단위)을 그대로 메뉴로 옮김. 사용자의 일 순서가 아니라 시스템 구조를 노출한 설계였음
화면 정의가 목록 수준화면 이름과 한 줄 설명만 있고 영역 구성, 표시 필드, 상태가 없어 구현자가 처음부터 다시 설계해야 하는 상태
디자인 근거 부재표준 스택에 shadcn과 Tailwind가 이미 있는데 디자인 토큰과 컴포넌트 매핑을 정의하지 않음
콜드 스타트 미정의데이터가 없는 첫 사용자가 무엇을 보는지 정의가 없었음. 첫 실패의 재현 조건
과금 축 미정의구독 SaaS가 목표인데 무엇을 제한하고 무엇에 과금하는지 설계가 없었음

4용어 v3

새로 만들지 않고, 국내 시장에서 이미 검증된 한국어를 채택. 통계 용어는 화면에서 문장으로 풀어씀

4.1 명명 원칙

  1. 실측 우선 블링, 뷰트랩 등 국내 제품과 크리에이터 커뮤니티가 이미 쓰는 말을 채택 (관심 채널, 모니터링, 요즘 뜨는, 떡상)
  2. 음차 금지 워치리스트, 아웃라이어, 니치 같은 영어 소리 옮김 라벨 사용 금지. 코드와 API는 영문 캐노니컬 유지 (다국어 대비)
  3. 통계는 문장으로 지표명 대신 의미를 그대로 노출: 평소 대비 8.4배, 같은 주제 상위 3%, 근거 32개

6.1 방향 3가지

  1. 데이터 밀도형 라이트 UI Linear, Vercel 계열의 밀도 높은 대시보드 문법. 보더 중심, 그림자 최소, 카드 라운드 12px. 다크 모드는 토큰 반전으로 지원하되 기본은 라이트
  2. 숫자가 주인공 표와 지표에 tabular-nums 고정폭 숫자, 문장형 지표 표기(4.3절)를 컴포넌트 수준에서 강제
  3. 토큰 외 색 금지 아래 정의된 CSS 변수 외의 임의 색상 사용 금지, 플랫폼 브랜드 색은 아이콘에만 허용하고 차트는 중립 팔레트 사용

8.6 콜드 스타트

10설정 체계

v0.3.0까지 설정이 메뉴 한 줄로만 존재했던 결함을 인정하고, 시장조사 기반 전체 인벤토리로 정의

10.1 원칙

  1. 설정은 DB, 관리는 UI 모든 운영 설정은 DB에 저장하고 화면에서 변경. 코드 하드코딩과 env 파일 토글 금지. 재배포 없이 즉시 반영, 누가 언제 바꿨는지 감사 기록
  2. env의 정직한 경계 DB 접속 정보와 설정 암호화 마스터 키, 이 두 부트스트랩 값만은 env 또는 시크릿 매니저에 남음 (DB의 위치를 DB에 저장할 수 없는 물리적 한계). 그 외 전부, 플랫폼 API 키까지 DB에 암호화 저장하고 UI에서 등록과 회전. 이 분리는 업계 표준과도 일치: env는 배포 시점 인프라 값, 런타임에 바뀌는 값은 DB 기반이 정석이며 env 토글은 안티패턴
  3. 3계층 스코프 시스템(운영자) 위에 워크스페이스, 그 위에 개인. 하위 스코프가 상위를 덮어쓰고 해석 순서는 개인, 워크스페이스, 시스템, 코드 기본값
  4. 성능 매 요청 DB 조회 금지. 캐시(Upstash)에 룰셋을 올려 로컬 평가하고 변경 시 무효화
  5. 안전한 기본값 설정을 하나도 건드리지 않아도 제품이 완전히 동작. 설정은 조정 수단이지 필수 입력이 아님. 설정 항목이 많다고 온보딩에 노출하지 않음

10.2 설정 데이터 모델

Setting { scope: system | workspace | user, scope_id, key, value: jsonb, encrypted: bool, version, updated_by, updated_at }
SettingAudit { key, scope, scope_id, old_value, new_value, actor, at }
feature flag는 Setting의 한 종류 (key 접두사 flag.), 킬 스위치 포함
  • 키별 Zod 스키마 레지스트리로 타입과 범위 검증, 설정 UI 폼은 스키마에서 자동 생성 (신규 설정 추가 시 화면 코드 수정 없음)

11자료정리 백엔드 (AI 큐레이션 파이프라인)

1차 구현에서 분류와 정리가 동작하지 않고 전부 수동이 되었던 실패의 원인을 지목하고, 자동이 기본이 되는 구조로 재정의

11.1 1차 실패 진단

겪은 증상추정 원인본 설계의 차단 장치
분류 백엔드가 제대로 동작 안 함요청 경로에서 동기 처리, 실패하면 그대로 방치, 재시도와 상태 추적 부재모든 정리 작업을 비동기 잡으로 분리, 재시도와 실패 큐, 잡 상태를 화면에 노출 (침묵 실패 금지)
전부 수동으로 하게 됨자동화가 보조 수단이고 수동 입력이 기본 흐름이었음자동 확정이 기본, 수동은 저확신 예외만. 검토 큐 유입률 자체를 관리 지표로 삼음 (11.6)
AI 정제 기능 없음분류를 1회 호출로 끝내고 불명확하면 포기불명확하면 AI가 추가 근거를 찾아 재판정하는 2차 검증 루프 (11.3)
사용자 정정이 소용없음정정 데이터를 버림정정 학습 루프로 축적과 반영 (11.4)

11.3 AI 검증 루프 (불명확하면 AI가 확인한다)

상황AI 행동결과
분류 확신도 미달같은 채널의 다른 게시물, 채널 소개, 필요 시 웹 검색으로 근거를 보강해 재판정임계 도달 시 자동 확정, 그래도 미달이면 근거 요약을 붙여 검토 큐로

11.4 정정 학습 루프

  • 주제 정정, 묶음 해제, 이상치 해제 등 모든 사용자 정정을 CorrectionLog에 축적
  • 주제별 정정 사례를 분류 프롬프트에 예시로 주입, 반복 정정은 포함 제외 규칙 승격 제안
  • 월간 표본 정확도 리포트(운영자 콘솔)로 임계값 재조정

11.5 비용 구조 (정직)

전량 LLM 분류는 비용상 불가. 1차는 규칙과 임베딩 유사도(저비용 대량), 2차 LLM 판정은 저확신 구간만, 3차 웹 검증은 그 중 일부만 진입하는 깔때기 구조. 단계별 통과율과 단가를 운영자 콘솔에서 계측하고 AI 예산 상한(10.3 그룹 13)과 연동

11.6 목표 지표 (초기 SLO, 측정 후 조정)
