# CLAUDE.md - dacrm CRM 모듈 (호스트 앱 내 /crm)

이 파일은 CRM 모듈 작업 시 에이전트가 따르는 규칙이다. 레포 루트의 기존 CLAUDE.md 가 있으면 그 아래 모듈 규칙으로 병합한다.

## 컨텍스트

- 데이터얼라이언스 내부 업무 시스템에 탑재되는 영업 CRM 모듈. 외부 판매 없음, 과금 없음
- 기준 문서: dacrm_통합기획서_v0.2.1.md(WHAT), dacrm_구현명세서_v0.1.0.md(HOW), dacrm_TASKS_v0.1.0.md(순서)
- **호스트 규칙이 상위다.** 레포 루트 `CLAUDE.md`가 SSOT이고 이 파일은 그 아래 모듈 규칙이다.
  두 문서가 충돌하면 **루트 CLAUDE.md가 이긴다.** 이 파일이 호스트와 어긋나면 이 파일을 고친다.

### 스택 — 실측값 (v0.7.492 기준, 2026-08-16 확인)

> 이 절은 계획 초안의 추정치를 **실제 호스트로 정정한 것**이다. 초안대로 가면 T0-02부터 막힌다.

| 초안이 가정한 것 | 호스트 실제 |
|---|---|
| Next.js 15 | **Next.js 14.2.29** App Router |
| Prisma (`pnpm prisma migrate dev`) | **Prisma는 도입한다**(사용자 결정 2026-08-16). 단 **`migrate dev`·`db push`·`migrate reset`은 절대 금지** — 운영 DB의 비-Prisma 205테이블을 드리프트로 보고 리셋을 제안한다. 적용은 `prisma migrate diff`로 SQL만 뽑아 `supabase/migrations/NNN_name.sql` + `scripts/migrate.sh` |
| `pnpm typecheck` | 그런 스크립트 없음 → `cd apps/web && pnpm exec tsc --noEmit` |
| Tailwind | Tailwind + **`globals.css` 디자인 토큰(SSOT)**. 토큰이 실질 체계다 |
| 워크스페이스 | pnpm 모노레포, 실제 패키지는 `apps/web` 하나. 경로 별칭 `@/*` → `apps/web/*` |

- 마이그레이션은 **운영 DB 공유**다. 적용은 사용자 승인 후 단독 창구로만 (루트 CLAUDE.md M-2).
  **2026-08-16 승인됨** — 조건은 *"당연히 호환 고려해서 장애 없게 반영해서 적용해야지"*. 즉 승인의
  범위는 **기존 205테이블에 장애가 없는 순수 추가**까지다. 파괴적 변경은 그때 다시 승인받는다.
- 번호는 파일 생성으로 **즉시 선점**한다. 같은 번호를 다른 내용으로 쓰면 `migrate.sh`가 조용히 스킵한다.

> **⚠️ 데이터 계층이 둘이 됐다** — 기존 205테이블 = Supabase JS + `supabase/migrations/NNN.sql`,
> `crm_` 24테이블 = Prisma. **경계를 넘지 않는다**: `crm_` 테이블을 Supabase 클라이언트로 만지거나
> 기존 테이블을 Prisma 스키마에 끌어들이면 양쪽이 깨진다.

### 삭제·권한 (사용자 결정 2026-08-16 — CRM에도 그대로 적용된다)

> 원문: *"삭제는 본연에 가지고 있는 목적이 진짜 삭제야, 권한은 이걸 사용하는 사용자인거지,
> 콘텐츠인텔리전스 권한이 있는 사용자 이렇게 해놔야 나중에 확장이 되지"*

- **CRM은 소프트 삭제(휴지통) + 영구 삭제 선택**이다 — 사용자 결정 2026-08-16, `lib/crm/domain/soft-delete.ts`.
  기본은 휴지통(30일 보관, 통합기획서 473·616행), 화면에서 '영구 삭제'를 고르면 그때 진짜 지운다.
  **CI의 "진짜 삭제" 지시(#3)를 CRM에 그대로 옮기지 않는다** — CI는 소프트삭제를 *대체안으로* 낸 것이
  반려된 맥락이고, CRM의 휴지통은 기획서가 명시한 **제품 기능**이다. (이 절의 이전 판이 "물리 삭제"라고
  단정했던 것은 그 맥락을 잘못 옮긴 것이다.)
- **권한은 앱 전역 `admin`이 아니라 모듈(워크스페이스) 멤버십 기준**이다. CRM은 `CrmWorkspaceMember`
  기준으로 게이트한다 — `role === 'admin'`으로 막으면 확장이 안 된다.

**확인창은 자작하지 않는다** — `components/ui/ConfirmDeleteDialog` + `lib/ci/use-delete.ts` 패턴
(ci-crud 세션 v0.7.494 신설, INVENTORY 등재, 사용 5곳).

#### 확인창은 **두 벌**이다 — `DeletePlan.reversible`이 문구를 가른다

| 모드 | `reversible` | 확인창이 말해야 할 것 |
|---|---|---|
| `trash`(기본) | `true` | **"30일 안에 휴지통에서 복구할 수 있습니다"** — 겁주지 않는다. 되돌릴 수 있는 행위에 파괴적 경고를 붙이면 사용자가 정리를 안 한다 |
| `purge`(영구) | `false` | **되돌릴 수 없음을 명시** + 무엇이 **사라지고** 무엇이 **남는지 둘 다** |

> 영구 삭제에서 **남는 것을 안 밝히면 사용자는 전부 없어지는 줄 알고 못 지운다.**
> (실화면 근거: 채널 삭제 시 "게시물 311건은 남습니다")

**휴지통 화면이 있어야 영구 삭제가 성립한다** — 복구 경로가 없으면 `trash`는 그냥 숨김이다.
목록 표준(§2-6)을 그대로 쓰고, 빈 상태는 `EmptyState`로 처리한다.

**폴리모픽 연결 테이블은 삭제 순서가 있다.** `item_type`+`item_id`처럼 FK가 없는 구조는 CASCADE가
안 걸린다. **본체를 지우기 *전에* 코드가 먼저 치운다** — 지운 뒤에는 **어느 것이 고아인지 알 수 없다.**
(근거: `apps/web/lib/ci/queries/delete.ts` 주석)

## 완료 정의 (모든 커밋이 만족해야 함)

```bash
cd apps/web && pnpm exec tsc --noEmit    # typecheck (전용 스크립트 없음)
cd apps/web && pnpm lint
cd apps/web && pnpm test                 # node:test — 새 *.test.ts 는 package.json test 목록에 append 필수
pnpm design:check                        # ← 디자인 가드. 빠뜨리면 UI 규칙이 아무것도 안 걸린다
```

- `pnpm build`는 **dev 서버 가동 중 금지** (`.next` 충돌 — 루트 CLAUDE.md M-2). 커밋 게이트에서 뺀다.
- **`pnpm design:check`는 생략 불가.** CI(`.github/workflows/design-guard.yml`)가 PR에서 자동 차단하고,
  `.githooks/pre-commit`도 돌린다. 여기서 빠지면 위반이 커밋까지 흘러간 뒤에 발견된다.
- design:check는 **ratchet(개수 기준)**이다. 지금보다 늘면 차단된다 — 신규 모듈은 **0에서 시작**하므로
  자작 버튼·자작 카드·hex·raw input을 하나라도 넣으면 그 자리에서 빨간불이다.

## 커밋 규칙

- 형식: **`v{버전}: {변경 내용} claude`** — 제목줄 맨 끝에 소문자 `claude` (루트 CLAUDE.md 커밋 규칙)
- 버전은 **루트 `package.json` 단일 소스**다. 현재 **0.7.492**. TASKS의 `v0.5.x`는 **쓰지 않는다** —
  호스트 버전이 이미 0.7.x라 역행이고, `next.config.js`가 루트 버전을 사이드바에 주입하므로 화면이 깨진다.
  TASKS의 v0.5.x는 **태스크 식별자로만** 읽고, 커밋 버전은 그때의 루트 버전 +PATCH 1로 정한다.
- 커밋 **직전** `git log --oneline -5`로 최근 버전을 확인하고 번프한다 (동시 세션 번호 충돌 방지).
- **pathspec 커밋만 허용**: `git commit -m "..." -- <파일경로>`. `git add -A`·`git add .`·`git commit -a` 금지.
  인덱스는 세션 간 공유라 남의 스테이징이 딸려 온다 (루트 CLAUDE.md M-1).
- 태스크 하나당 커밋 하나를 원칙으로, 롤백 단위 유지

## 절대 규칙 (위반 코드는 작성 금지)

1. AI 출력은 코어 테이블(company, person, deal, task, meeting)에 직접 쓰지 않는다. 반드시 CrmAiSuggestion 을 생성하고 suggestion.service 의 반영 경로만 사용한다
2. verifiedFields 에 등록된 필드는 어떤 confidence 에서도 자동 반영하지 않는다
3. 금액, 스테이지 전이, won/lost 는 auto_apply 대상이 될 수 없다 (코드 하드코딩)
4. DB 접근은 getCrmDb(workspaceId) 로만 한다. 전역 prisma 로 crm_ 테이블을 만지는 코드 금지
5. 상태 전이는 state-machines.ts 의 canTransit 를 통해서만 판정한다. 서비스나 라우트에서 직접 status 를 대입하지 않는다
6. 쓰기 트랜잭션은 withCrmTx 를 사용하고 audit_log 를 같은 트랜잭션에서 기록한다
7. 외부 서비스(LLM, STT, Gmail)는 어댑터 인터페이스 뒤에 둔다. 키가 없는 환경에서는 mock 어댑터로 전 기능이 동작해야 한다
8. 모델명, 벤더명, 예산 수치를 코드에 하드코딩하지 않는다. CrmAppSetting 에서 읽는다. env 는 부트스트랩 시크릿만
9. 호스트 코드 수정은 구현명세서 1.2 의 3개 지점만 허용. 그 외 호스트 파일을 수정해야 할 것 같으면 멈추고 사람에게 보고한다
10. 스키마 변경은 반드시 마이그레이션 파일과 관련 정합성 테스트(DI-XX)를 같은 커밋에 포함한다

- 전사, LLM 응답 픽스처는 tests/fixtures/ 에 두고 mock 어댑터가 반환한다

### U-2. 딜 보드(T1-03)는 목록 표준의 예외가 아니다

칸반 보드는 `ListSurface`가 못 그리는 유일한 화면이다. 그래도:

- **어느 뷰인지는 URL이 기억한다** — 로컬 `useState` 금지. 링크를 공유하면 같은 뷰로 열려야 한다.
  딜은 `?mode=list`를 쓴다(`view`가 아니다 — `useListQuery`의 `view`는 표/카드 전환에 이미 쓰이므로
  보드/표를 같은 이름으로 두면 의미가 충돌한다).
- **뷰 전환은 `SegmentedTabs`** (탭 렌더러 SSOT). 탭 마크업을 자작하지 않는다.
- **기본 뷰는 그 화면의 본체가 정한다.** 딜은 파이프라인이 본체이므로 **보드가 기본**이다.
  목록 표준의 "표가 기본"을 기계적으로 적용하지 않는다.
- 검색·필터·스테이지 선택은 **`ListToolbar` 그대로** 쓴다. 보드라고 툴바를 새로 그리지 않는다.
- **데이터는 한 번만 불러 두 뷰가 나눠 쓴다** — 뷰마다 따로 부르면 전환마다 같은 요청이 다시 나간다.
- 카드 1장 = `className="card"` + `NbBadge`. 카드 안에 자작 스타일 박스를 넣지 않는다.
- **드래그만 두지 않는다** — 카드 안에 단계 선택 컨트롤을 함께 둔다.
  드래그뿐이면 키보드·터치·보조기술 사용자가 단계를 못 옮긴다.
- 보드 컴포넌트는 **처음엔 화면 폴더에 둔다.** 두 번째 사용처가 생기는 시점에 `components/ui/list/`로
  올리고 INVENTORY에 등재한다(§0-1 — 쓰는 곳이 하나면 공용으로 올릴 근거가 없다).

> 이 절은 v0.7.496 딜 화면 검증 결과로 고쳤다. 처음 판은 `?view=board`·"표가 기본"·"보드는 처음부터
> `components/ui/list/`"를 요구했는데, 셋 다 목록 표준의 관성이었지 근거가 없었다.
> **규칙이 현실과 어긋나면 현실이 아니라 규칙을 고친다.**

### U-3. 상호작용 표준 (루트 CLAUDE.md §2-3-1 — 모양보다 이게 먼저 티난다)

- **모듈 밖으로 나가는 길이 있어야 한다.** CRM은 사이드바를 **통째로** 자기 것으로 바꾼다.
  그래서 들어온 사람은 **호스트 업무 화면으로 돌아갈 방법이 사라진다.**
  호스트에서 CRM으로 오는 링크는 있는데 반대가 없으면 **그건 문이 아니라 함정이다.**
  자주 쓰는 곳만 셸에 둔다 — 사이드바를 복제하면 여기가 **두 번째 메뉴 정의**가 되고
  호스트 메뉴가 바뀔 때마다 두 곳을 고쳐야 한다. 나머지는 상단 전체 메뉴로 간다.
  > **검사 방법**: 모듈 화면을 열고 *"여기서 업무 화면으로 어떻게 가지?"*를 실제로 해 본다.
  > 안쪽 이동만 확인하면 이 결함은 안 보인다 — **감시 중 실제로 놓쳤고 사용자가 지적해 알았다.**
- **목록 행은 살아 있다.** 상세가 있으면 `rowHref`로 행 전체가 링크다. '상세' 버튼을 따로 두지 않는다
- 행 안의 액션(수락·거절·병합)은 `onClick={(e) => e.stopPropagation()}`로 감싼다
- **상세 화면엔 `back`이 항상 제목 왼쪽 위**에 있다. 자작 `ArrowLeft` 금지 — `interaction-standard.test.ts`가 차단
- 입력과 버튼은 같은 높이(`--control-h` 44px). 화면에서 `min-height: 44px`를 손으로 붙이지 않는다

### U-6. AI 결과 표시 (CRM의 제안 관문 T1-06과 직결)

호스트에 **고정된 두 패턴**이 있다. 새로 만들지 않는다:

- **추출/제안형** = `CrmAiSuggestion` 인박스가 여기 해당. "제목 + 신뢰도 + 근거(plain text) + 체크박스"
  리스트로 제시 → 사용자가 선택 → 일괄 반영. **자동 등록 금지** (이 파일 절대규칙 1~3과 같은 방향)
- **생성형** = AI 생성 → 미리보기/편집 → 저장
- 근거(source quote)가 HTML이면 **반드시 `lib/html-to-plain.ts`를 거친다.** 안 거치면 `<br/>`이 글자로 노출된다

#### 예외: 원터치 생성(붙여넣기)은 후보 체크리스트가 아니다

**AI가 스스로 찾아낸 것**(인박스)과 **사용자가 직접 붙여넣은 것**(원터치 생성)은 다른 패턴이다.
후자는 사용자가 이미 "이걸 등록해라"라고 지시한 것이라 후보로 되물을 필요가 없다.

대신 그 흐름은 **다섯 가지를 지켜야 한다** (v0.7.498 검증에서 전부 확인됨):

| | 왜 |
|---|---|
| **지어내지 않는다** | 못 채운 값은 빈칸으로 두고 묻는다("붙여넣은 글에서 찾지 못했어요"). 지어낸 값은 나중에 진짜처럼 읽힌다 |
| **무엇을 만들었는지 명시** | "새로 만든 것: 인물 · 감시" — 사용자가 무엇이 생겼는지 알아야 되돌릴 수 있다 |
| **되돌릴 수 있다** | 만든 것이 목록에 즉시 나타나고 휴지통 → 되살리기/영구삭제가 된다 |
| **미룰 수 있다** | 갭필을 강제하지 않는다(`나중에`). 강제하면 사용자는 아무거나 넣는다 |
| **부가 생성은 명시적 선택** | "딜도 함께 만들기"는 **기본 해제**. 사용자가 고른 것만 만든다 |

그리고 **실패해도 붙여넣은 글을 지우지 않는다** — 다시 찾아오게 만들면 두 번 다시 안 쓴다.

> 이 예외는 v0.7.498을 브라우저에서 실제로 밟아 확인한 뒤 추가했다. 처음 판의 U-6은 **형태**(체크리스트)만
> 요구했는데, U-6이 실제로 막으려던 것은 **자동 등록으로 인한 오염·지어낸 값·되돌릴 수 없음**이었다.
> 그 셋이 다른 방법으로 막혀 있으면 형태가 달라도 된다. **규칙이 형태만 보면 더 나은 구현을 막는다.**

### U-6-1. 성능 계약 (v0.7.492 퍼포먼스 작업 반영 — 2026-08-16 실측 확인)

> **왜**: 화면 하나 여는 비용은 **화면이 아니라 셸**이 정한다. 페이지 JS가 198 B인 빈 화면도
> DB 왕복 20회였다. CRM 화면을 아무리 가볍게 짜도 셸 비용은 그대로 붙는다 —
> 반대로 말하면 **셸 규약을 어기면 CRM 화면만 느려진다.**
> (근거: `docs/2026-08-16-performance-audit/PLAN.md`)

| 하지 말 것 | 대신 | 어기면 |
|---|---|---|
| `globals.css`에 `@import` (폰트 포함) | 폰트는 **자체 호스팅**. `public/fonts/fonts.css`를 `app/layout.tsx`가 `<link>`로 건다 | `lib/ui/font-loading.test.ts` **6종이 차단**. @import는 파싱 후에야 발견돼 첫 페인트 앞에 직렬로 매달린다 |
| CRM 레이아웃에서 프로필 직접 조회 | **`lib/auth/request-profile.ts`의 `getRequestProfile()`** (React `cache` — 요청당 1회) | 요청당 DB 왕복이 다시 늘어난다. 실제로 세 레이아웃이 같은 행을 3번 읽고 있었다 |
| 설정 직접 조회 | **`lib/settings.ts`의 `getShellSettings()`** (동일하게 `cache`) | 위와 같음 |
| 목록 개인설정을 화면마다 재조회 | `useListQuery(defaults, { persistKey })` — 탭 메모리 캐시가 붙어 있다 | 화면 이동마다 `/api/ui-preferences`를 다시 부른다 |
| `apps/web/vercel.json`의 `"regions": ["icn1"]` 제거 | 그대로 둔다 (Supabase가 서울) | `lib/ci/deploy-region.test.ts`가 잠근다 |

#### ⚠️ `getRequestProfile()`은 삭제된 계정을 **걸러주지 않는다** (필독)

이 함수는 **일부러 필터를 안 건다.** 기존 세 셸의 조건이 서로 달랐고(프로필 조회에
`.is('deleted_at', null)`을 건 것은 **`admin` 하나뿐**), 여기서 필터를 걸면 나머지 두 곳 동작이
조용히 바뀌기 때문이다. 그래서 **행을 그대로 돌려주고 `deleted_at`을 함께 실어 보낸다.**

```ts
const profile = await getRequestProfile()
if (!profile || profile.deleted_at) redirect('/login')   // ← CRM이 직접 해야 한다
```

**안 하면 소프트 삭제된 계정이 CRM에 그대로 들어온다.** CRM은 영업 데이터를 다루므로
`(ci)` 셸의 현재 코드를 그대로 베끼지 말 것 — `(ci)`는 `deleted_at`을 보지 않는다.

#### ⚠️ 컬럼이 부족하면 **새 쿼리를 만들지 말고 `COLUMNS`에 추가**한다

React `cache()`는 **인자로 키를 잡는다.** 컬럼을 다르게 넘기는 변형 함수를 만들면 캐시가 갈라져
왕복이 원래대로 늘어난다. `profiles`의 다른 컬럼이 필요하면 `request-profile.ts`의 `COLUMNS`
**합집합에 추가**한다 — 행 하나에 컬럼 몇 개 붙는 비용이 왕복 한 번보다 훨씬 싸다.
(이 파일이 합집합을 읽는 이유가 그것이다.)

#### 성능 판정 기준 — **숫자가 아니라 행위로 본다**

기준선 "하드 로드 DB 왕복 17회"는 **`(ci)` 셸 기준**이다. CRM이 자기 route group에 layout을 두면
그 layout이 하는 일만큼은 **정상적으로 늘어난다** — 그건 위반이 아니다. 판정은 이렇게 한다:

1. **CRM 셸이 프로필·설정을 직접 읽는가** → 읽으면 위반 (위 표대로 `getRequestProfile`/`getShellSettings`)
2. **앱 내 이동에서 `profiles` 조회가 0인가** → 0이 아니면 위반 (레이아웃은 앱 내 이동에서 다시 돌지 않아야 정상)
3. 숫자로 보려면 CRM 화면 **두 개를 연속으로 열어 화면당 증가분**을 본다 (절대값 비교 금지)

> 참고: `useListQuery`의 개인설정 캐시는 **탭 모듈 메모리**라 새로고침하면 비워진다. 정상이다 —
> 새로고침 후 첫 목록 화면에서 한 번만 조회가 나간다. 사라졌다고 캐시가 깨진 게 아니다.

### U-7. 완료 판정 — 정적 통과는 완료가 아니다

루트 CLAUDE.md의 E-1~E-5를 그대로 따른다. UI 태스크(T1-01~T1-08)는 **브라우저에서 직접**:

1. 기본 플래그 상태의 **실제 렌더 경로**로 연다
2. 폼에 사용자처럼 입력하고 버튼을 누른다
3. 결과가 **화면에 보이는지** 확인한다 (응답 200이 아니라)
4. 예외를 밟는다 — 빈 입력 · 잘못된 값 · 중복 · 0건 빈 상태 · 없는 id · 권한 없음 · 실패 메시지
5. **콘솔 오류 0**
6. 넣은 테스트 데이터는 **원상 복구**한다

#### ⚠️ 복구는 **필요조건이지 충분조건이 아니다** — 테스트는 운영 워크스페이스를 쓰지 않는다

> **실측 사고(2026-08-16 20:31~20:40)**: QA 세션이 UI로 등록한 회사·인물이 **10분 만에 사라졌다.**
> 소프트 삭제가 아니라 **행 자체가 없었고**, 생성 감사로그까지 지워졌다.
> 원인은 `tests/crm/integrity/_helpers.ts:31`의 `WS_A = 'ws_dataalliance'` —
> 주석이 *"시드가 만든 **실제** 워크스페이스"*라고 적고 있다. **테스트 공간 = 운영 공간**이었다.

- 각 테스트의 cleanup이 자기 id로 좁혀져 있어도 **정적으로는 안전해 보인다.**
  문제는 범위가 아니라 **같은 공간을 쓴다는 것**이다. 조건이 조금만 넓어지면
  (`name contains` · `action='lead.imported'` · `targetType='setting'` · `month=이번달`)
  사용자 데이터가 함께 걸린다.
- **테스트 전용 워크스페이스(`ws_test_*`)로 가른다.** 게이트 문서에 이미 "예산·리포트 테스트에
  전용 워크스페이스를 만들어 격리했다"고 적혀 있으니 그 방법을 전체로 넓히면 된다.
- **사람이 검증용으로 넣는 데이터도 같은 위험을 받는다.** 다른 세션이 같은 시각 테스트를 돌리면
  내가 넣은 것이 사라진다. **검증 중 데이터가 사라지면 내 실수가 아니라 이 구조를 먼저 의심한다.**
- 검증자가 지울 때는 **자기가 만든 id 단건으로만** 지운다. `deleteMany`·조건 삭제 금지.
