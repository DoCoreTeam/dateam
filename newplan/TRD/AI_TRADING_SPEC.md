## ⚠ 구현 범위 잠금 (Claude Code 필독)

**지금 구현할 범위는 §3.2의 Release 1-A(데이터 수집 + 판단 기록)뿐이다.**

- 만든다: 메뉴·소유자 접근·설정 골격, KIS 조회(**분봉 · 시세 · 호가 · 종목 정보만**, §20), 토큰 캐시, 확정 봉 저장, 세션 캘린더, 진입 조건 평가, `rule`·`jev` 판단 **기록**, 크론(선점·중복 방지), 버전·시각 기록. 데이터 모델은 §14.5.
- **만들지 않는다**: 백테스트·체결 재현·보정·기대값·관문(1-B), **계좌 조회(잔고·체결·미체결·증거금)**·알림 발송·신호 화면 버튼·체결 연결·손익(1-C), Gemini·AI 운영자(Release 2·3). 이 부분의 빈 함수·임시 코드도 만들지 않는다.
- 이 문서의 1-B·1-C 내용은 **1-A의 데이터 구조가 나중에 막히지 않게 하기 위한 참고**다.
- 기존 코드에서 필요한 것을 찾지 못하면 **§17.1의 기본 구현으로 진행하고 `docs/trading/ASSUMPTIONS.md`에 적는다.** 설정값이 필요하면 §19 기본값을 쓴다. 1-A를 위해 질문하며 멈추지 않는다.

## 0. 먼저 읽을 것 — 이 시스템의 컨셉

리뷰나 구현 중에 새 제안이 나오면 **아래 컨셉에 맞는지 먼저 본다.** 맞지 않으면 반영하지 않고 §18에 이유를 남긴다.

| # | 컨셉 | 뜻 |
|---|---|---|
| C1 | **시스템은 돈을 움직이지 않는다** | 주문은 사람이 원하는 수단(MTS·HTS 등)으로 한다. 시스템은 판단하고, 알리고, 기록하고, 배운다 |
| C2 | **기존 시스템 안에서, 새 서버 없이** | 기존 Next.js 앱(Vercel) + Supabase + 기존 설정·알림·권한·AI 호출 계층을 확장한다 |
| C3 | **사람 속도에 맞춘다** | 사람이 알림을 보고 주문하기까지 1~3분 걸린다. 판단은 1분 봉(기본)으로 하되, 보유 시간은 이 지연보다 충분히 길게 잡는다(기본 15분 이상). 초 단위 정밀도는 이 구조에서 가치가 낮다 |
| C4 | **검증이 먼저, 알림은 나중** | 비용과 지연을 뺀 뒤에도 기대값이 양수인지 확인하기 전에는 실제 알림을 켜지 않는다 |
| C5 | **단순하게** | 같은 결과를 내는 두 방법이 있으면 단순한 쪽. 필요해지면 그때 추가한다(각 결정에 "재검토 조건"을 적는다) |

**리뷰어에게**: 제안하기 전에 §18 설계 결정 기록을 봐 주세요. 이미 검토하고 이유를 적어 둔 항목이 많습니다. 특히 "상시 워커 / WebSocket / 틱 저장"은 C1·C3 때문에 의도적으로 뺐습니다(D-03~05).

**Claude Code에게**: 요구 수준은 **[필수]**(§1), **[권장]**(기존 시스템에 더 나은 방법이 있으면 그것을 쓰고 `docs/trading/ASSUMPTIONS.md`에 이유 기록), **[예시]**(경로·이름·숫자는 기존 관례에 맞게)로 나뉜다. 기존에 있는 기능은 새로 만들지 않고 확장한다.

## 1. 필수 규칙 [필수]

| # | 규칙 |
|---|---|
| M1 | 저장소에 **주문 API를 호출하는 코드가 없다.** KIS는 조회(시세·분봉·잔고·체결·미체결·증거금·종목 정보)만. 가드 테스트로 고정(Release 4 전까지) |
| M2 | 새 신호는 **안전 게이트(§10) → 진입 조건 → 판단 → 보정 → 신호 규칙**을 모두 통과해야 나간다. AI 응답이 알림을 직접 보내는 경로는 없다 |
| M3 | Jev 출력은 **원점수**다. 신호 판단은 보정 후 값(§7.4)으로만 한다. 보정이 없으면 신호를 내지 않는다(기록만) |
| M4 | 백테스트와 실시간은 **같은 함수, 같은 확정 봉**(§6.2)을 쓴다 |
| M5 | 미래 참조 금지: 모든 데이터는 `available_at ≤ 판단 시각`인 것만 쓴다. 최종 검증 구간(Lockbox)은 관문 직전에 한 번만 연다 |
| M6 | **리스크 산술(§9)이 맞지 않는 설정은 저장되지 않는다.** 금액은 데이터로 계산하고 코드·문서에 고정하지 않는다 |
| M7 | 매매에 쓰이는 값은 전부 설정 레지스트리에 있고 설정 화면에서 바꿀 수 있다. **전략 변경은 다음 거래일부터**, 즉시 적용은 신호를 막는 안전 조치뿐 |
| M8 | AI는 설정에 개입할 수 있지만 **금지 목록(§15.3)** 은 바꿀 수 없다. AI 변경은 사람과 같은 경로·같은 검증·같은 기록 |
| M9 | 같은 이벤트가 두 번 들어와도 한 번만 처리되게 **유일 키(§14.3)** 를 둔다 |
| M10 | 모든 판단·신호·거래에 **버전과 시각 기록(§14)** 을 남긴다 |
| M11 | 모듈 데이터는 **소유자만** 본다 |
| M12 | 기존 정책 준수: AI 호출은 기존 AI 계층(예산·마스킹·원장), 표는 같은 마이그레이션에서 RLS, 조용한 실패 금지(`reason` + `userMessage`) |

## 4. 구조 — 기존 앱 하나

```
[Vercel 크론, 1분마다]
   ├ KIS 조회: 확정 봉 · 호가 (1-A) / 잔고 · 체결 · 미체결 · 증거금 (1-C)
   ├ 1분 봉이 확정되면: 안전 게이트 → 진입 조건 → 판단(rule·ml·jev) → 보정 → 신호 규칙 → 알림
   └ 포지션이 있으면: 손절·목표·시간·당일 청산 확인 → 필요하면 알림 (1-C)
[Supabase]  모든 기록(봉·판단·신호·거래·시각·버전·설정)
[화면]      신호 · 포지션 · 기록 · 설정 (휴대폰 우선)
[백테스트]  같은 함수를 과거 데이터에 돌리는 개발 도구(CLI)
```

- **실행 시각 [권장]** (D-39): 판단 봉이 1분이라 실행 시각이 중요하다. Vercel Cron은 지정한 분 안의 아무 시점(최대 약 59초 지연)에 실행되고 재시도가 없다. 그래서 **이미 쓰고 있는 Supabase의 `pg_cron` + `pg_net`으로 매분 5초 무렵에 우리 API를 호출**하는 방식을 기본으로 한다(새 서버·외부 서비스 없음). 확정 봉이 아직 안 나왔으면 설정 시간 안에서 한두 번 다시 확인한다. pg_cron을 쓸 수 없는 환경이면 Vercel Cron으로 대체하고 지연을 측정한다.
- 어떤 방식이든 실행은 가끔 빠지거나 두 번 될 수 있다. 그래서 **매분 호출하고, 코드가 "지금 할 일"을 판단하며, 유일 키와 선점으로 중복을 막는다**(§14.3).
- 크론 지연(최대 약 1분)은 사람 지연(1~3분)보다 작다. 없애려 하지 않고 **측정해서 체결 재현의 지연에 포함**한다(D-03).
- Vercel Cron 표현식은 UTC다. 장 시간 판단은 코드에서 `Asia/Seoul` 기준.
- Jev 키는 시스템 설정의 AI 공급자 목록에 추가하고, 호출은 기존 AI 호출 계층에 판단 모델 호출 함수를 더해 예산·원장·실패 사유를 받는다.

## 5. 시간

| 시간 | 기본값 | 이유 |
|---|---|---|
| 확인 주기 | 1분(크론) | 봉 확정·계좌·청산 조건 확인 |
| 판단 봉 | **1분** | 사용자 결정. 잡음·사람 지연의 영향은 검증에서 5·15분과 같은 조건으로 비교해 확인한다 |
| 보유 시간 | 15분 이상 | 사람이 1~3분 늦게 들어가도 의미가 남는 길이 |

기본값은 1분이고, 1-B 검증에서 판단 봉 1·5·15분 × 보유 시간을 같은 비용·지연으로 비교한다. 다른 조합이 확실히 낫게 나오면(신뢰구간 하한 기준) 관리자에게 바꿀지 묻는다(설정 항목). 지수 수준(2026년 9월 약 1,050~1,130pt)에서는 1분 움직임이 왕복 비용보다 큰 경우가 많아, 1분 판단에서는 비용보다 잡음과 지연이 성과에 더 큰 영향을 줄 수 있어, 검증에서 이 부분을 중점적으로 본다.

## 6. 데이터

### 6.1 수집 [필수]

1-A부터 크론으로 1분·5분 확정 봉(시가·고가·저가·종가·거래량·미결제약정)과 최우선 호가를 저장한다. 야간장도 수집한다(신호는 정규장만). 과거 데이터는 KIS 분봉 조회로 가능한 범위까지 백필하고, 부족하면 CSV 가져오기(외부 데이터·증권사 프로그램 내보내기)로 채운다. 원본과 정리된 데이터를 따로 저장한다.

### 6.2 확정 봉 규칙 [필수]

- 판단 봉(예: 1분 봉 10:14:00~10:14:59)은 **KIS 조회에서 그 봉이 마감된 값으로 확인될 때** 확정으로 본다. 봉 끝 시각 이후 설정 시간(예: 20초) 안에 확인되지 않으면 **그 봉의 판단은 건너뛰고 기록**한다(늦게 온 데이터로 판단을 다시 하지 않는다).
- 비교용 5·15분 봉은 1분 봉으로 만들고, 구성 1분 봉이 모두 확정돼야 한다.
- 백테스트도 같은 규칙과 같은 출처의 봉을 쓴다.

판정 의사코드 [필수] (D-55):

```ts
// 매분 약 5초에 실행. now는 Asia/Seoul 기준으로 해석
const target = floorToMinute(now) - 1min;           // 확정할 1분 봉의 시작 시각
if (!calendar.isContinuousTrading(target)) return;  // 단일가·장외 시간 봉은 판단하지 않음(수집은 해도 됨)
const rows = await kis.minuteBars(contract, { to: now });   // 분봉 조회, 최신순
const bar = rows.find(r => r.startAt === target);
const newer = rows.some(r => r.startAt > target);   // 다음 분 봉이 이미 시작됨 = target 마감
if (bar && (newer || now >= target + 1min + graceSec)) {
  saveBar({ ...bar, confirmedAt: now, availableAt: now });   // 확정
} else if (now >= target + 1min + missingAfterSec) {
  markMissing(target);                               // SG-01 대상, 그 분의 판단은 건너뜀
} else {
  retryLater();                                      // 같은 실행 안에서 몇 초 뒤 1~2회 재조회
}
// graceSec 기본 10, missingAfterSec 기본 25 (설정)
// 거래량 0인 분도 정상 봉일 수 있으므로 거래량 유무로 확정을 판단하지 않는다
```

### 6.3 월물과 세션 캘린더 [필수]

- **종목 정보 동기화**: 매 거래일 장 시작 전에 KIS 종목 정보로 월물 목록·최종거래일을 갱신하고, 설정된 월물이 유효한지 확인한다.
- **교체**: 기본은 차월물 거래량이 근월물을 넘은 첫 거래일, 늦어도 최종거래일 N거래일 전(설정). 미니는 매달, 정규는 분기마다. 교체일에는 신호 월물·지표 연결이 같이 바뀐다.
- 지표용 연속 시리즈는 교체 시점의 가격 차이를 빼서 잇고(차이 조정), **손익·체결 재현은 실제 월물 가격만** 쓴다.
- 데이 트레이딩이라 포지션이 교체를 넘지 않는다. 교체일·최종거래일은 신규 신호 금지 구간(설정).
- **단일가 시간대를 구분한다** (D-40): 캘린더에 "접속매매 시작·종료"와 "단일가 시간대"(개장 전 단일가, 장 마감 단일가)를 따로 둔다. 단일가 시간대의 봉은 판단에 쓰지 않는다. 구체 시각(예: 개장 전 08:30~08:45, 장 마감 단일가 15:35~15:45)은 구현 시 거래소 기준으로 확인한다.
- **청산 시각은 고정값이 아니다**: `당일 청산 알림 = 그날 접속매매 종료 − N분`(기본 N = 15). 신규 금지 구간도 접속매매 종료 기준. 화면에 고정 시각을 두지 않는다.

| 날 | 거래 | 접속매매 종료 | 당일 청산 알림(N=15) |
|---|---|---|---|
| 평일 | 08:45~15:45(단일가 08:30~08:45 · 15:35~15:45) | 15:35 | **15:20** |
| **최종거래일(만기일)** — 정규는 3·6·9·12월, **미니는 매월** 두 번째 목요일(공휴일이면 앞당김) | 08:45~15:20 | 15:20(만기일 장 마감 단일가 여부는 구현 시 확인, 있으면 그 시작 시각) | **15:05** |
| 개장 시간 변경일(연초 첫 거래일·수능일 등) | 거래소 공지대로 | 공지대로 | 종료 − N |

미니는 만기가 매달이므로 **매달 한 번씩** 만기일 규칙이 적용된다. 만기일에 15:05 이후 남은 포지션은 SG-05 · 반복 알림 대상이다(D-50).
- KIS 점검 시간 등으로 조회가 안 되는 구간은 수집 공백으로 표시한다(SG-02).

### 6.4 거래일 [필수]

야간장이 어느 `trade_date`에 속하는지 거래소 기준을 확인해 정한다(설정). 일일 한도·설정 적용·성과 집계는 `trade_date` 기준.

### 6.5 as-of [필수]

모든 행에 `available_at`. 백테스트 시각 T에는 그 이전 데이터만. 데이터 조회 함수가 기준 시각을 인자로 받게 만든다. 수정은 덮어쓰지 않고 새 버전. (지식·뉴스는 Release 2부터 같은 규칙.)

### 6.6 이벤트 캘린더 [필수: Release 1은 수동]

금통위·FOMC·CPI·만기일 등 신호 금지 구간은 Release 1에서 **관리자가 설정 화면에 직접 등록**한다(기존 시스템 캘린더에 이 용도로 쓸 수 있는 것이 있으면 연결). 자동 수집은 Release 2.

## 7. 판단

### 7.1 진입 조건 [권장]

판단 봉(기본 1분)이 확정되면 진입 조건(지표 비교식)을 본다. 참일 때만 판단기를 부른다. Release 1은 전략 1개, 진입 조건 1~3개.

### 7.2 판단기 [필수: 교체 가능 · 특권 없음]

`rule`(진입 조건의 기본 방향), `ml`(지표로 학습한 가벼운 모델), `jev`를 같은 인터페이스로 둔다. 같은 시점·같은 보정·같은 평가로 비교한다. Jev는 1-A부터 원점수를 기록해 둔다(보정에 표본이 필요하므로).

### 7.3 Jev에게 묻는 것 (Release 1은 진입만)

```ts
const questions = {
  direction: { type: 'choice', criteria: { long: '<롱 기준>', short: '<숏 기준>', hold: '<관망 기준>' } },
  enter_now: { type: 'noul', instructions: '1~3분 늦게 들어가도 유효한가? 이미 추격 구간은 아닌가?' },
};
```

입력에는 절대 날짜·뉴스를 넣지 않는다(시각은 "세션 시작 후 N분", 가격은 ATR·전일 종가 대비). 응답은 입력 해시·모델·스펙 버전으로 저장한다. **Jev 대기 시간은 기본 10초**(설정) (D-41): 사람 지연이 수십 초~수 분이라 몇 초 더 기다려도 손해가 작고, 2.5초로 두면 변동이 큰 순간(응답이 느려지는 때)에 기권이 몰려 좋은 기회만 놓치는 편향이 생긴다. 기권률은 변동성 구간별로 기록한다. 대기 시간 초과·오류·예산 초과면 기권. **청산 판단(보유 중 계속 묻기)은 Release 2에서 섀도로 시작한다**(D-11).

### 7.4 보정 [필수]

- **실제로 하는 행동은 고른 방향 하나로 진입하는 것뿐**이다. 그래서 방향별로 따로 보정한다: 롱 신호에는 `p_long`, 숏 신호에는 `p_short`를 "청산 계획대로 했을 때 순이익 > 0이었는가"로 보정한다. `hold`가 가장 높으면 기권이다(D-09).
- 방법 (D-42): 기본은 **로지스틱 보정(Platt, 파라미터 2개)**. 표본이 적을 때 가장 안정적이다. 등위 회귀(isotonic)는 표본이 충분히 많을 때만(기본 1,000건 이상, 설정) 후보로 비교한다. 학습 구간으로 맞추고 검증 구간으로 평가.
- 측정: Brier score, 보정 곡선, 구간별 실제 승률·표본 수.

### 7.5 기대값 [필수]

`net_expected_value` = **보정 확률이 비슷한 과거 신호들의 실제 순손익 평균**(체결 재현 기준, 비용 포함). 이 평균표(보정 확률 구간 → 순손익)는 **학습 구간 데이터로만** 만들고 `ev_model_version`으로 관리한다. 검증 구간·Lockbox 데이터는 여기에 들어가지 않는다(D-35). 목표·손절·시간 청산·당일 청산이 섞인 결과를 그대로 평균하므로 공식이 청산 방식과 어긋나지 않는다(D-10). 신호 규칙(§7.6)은 이 기대값이 최소값 이상일 때만 통과시킨다. 비용은 이미 들어 있으므로 다시 빼지 않는다.

### 7.6 신호 규칙 [권장: 목록 · 필수: 순수 함수]

안전 게이트(§10) 통과 후 평가한다. 값은 모두 설정 항목이고, 규칙·설정 화면·대시보드는 같은 값 하나를 읽는다.

| ID | 규칙 | 기본값 [예시] |
|---|---|---|
| SR-01 | 순기대값(비용 포함) ≥ 최소값. `hold`가 가장 높으면 기권 | 설정 |
| SR-02 | `enter_now` 보정 확률 ≥ 기준 | 설정 |
| SR-04 | 개장 직후·마감 전·교체일·최종거래일 신규 금지 | 개장 후 5분, 마감 전 30분 |
| SR-05 | 이벤트 전후 신규 금지(수동 등록 캘린더) | 전 30분 / 후 15분 |
| SR-06 | 오늘 **실현** 손익(체결 기준) ≥ 목표 → 새 신호 종료 | 설정 |
| SR-07 | 1회 위험 > 남은 손실 여유 → 새 신호 없음 | §9 |
| SR-08 | 연속 손실 → 쿨다운 | 2연패 → 60분 |
| SR-09 | 거래일 최대 신호 수 | **6** |
| SR-10 | 같은 방향 재신호 최소 간격 | 10분 |
| SR-12 | 목표 거리(가격, 비용 미포함) ≥ 왕복 비용 × k | k = 3 |

SR-01은 비용을 포함한 기대값, SR-12는 비용을 뺀 가격 거리로 서로 다른 것을 본다(비용 이중 차감 없음, D-34).

## 8. 청산 계획 (Release 1은 규칙만)

| 항목 | 기본값 [예시] |
|---|---|
| 손절가 | 진입 기준가 ∓ 1.2 × ATR(판단 봉) → 호가 단위로 맞춤 |
| 목표가 | **1개**. 진입 기준가 ± 1.5 × ATR(판단 봉) |
| 시간 청산 | 진입 후 N분(설정) 지나면 청산 알림 |
| 당일 청산 | 세션 마감 − N분(캘린더로 계산, §6.3) |
| 진입 한계가 | 롱: 진입 기준가 + 0.3 × ATR / 숏: 진입 기준가 − 0.3 × ATR. 넘어서면 따라가지 않음 |
| 신호 유효 시간 | 10분. 지나서 체결되면 `late` |

1계약이므로 **분할 청산은 없다.** 분할 청산은 수량 2계약 이상을 허용하는 릴리스에서 다시 정한다(D-11).

**가격 관측과 체결은 다르다 [필수]**: 1분 조회에서 가격이 목표·손절에 닿으면 "목표가 도달 — 청산하세요" 같은 알림을 보낸다(`price_observed`). 포지션 상태·오늘 실현 손익·수익 목표 판정은 **KIS에서 청산 체결을 확인했을 때만** 바뀐다. 알림을 못 보고 가격이 되돌아가면 포지션은 계속 `holding`이고 감시도 계속된다(D-32).

## 9. 리스크 산술 [필수: M6]

### 9.1 계산

```
최악 진입가     = 진입 한계가 (롱: 위쪽 한계, 숏: 아래쪽 한계 — 사람이 늦게 들어가도 여기까지는 허용하므로)
가격 위험       = (|최악 진입가 − 손절가| + 손절 슬리피지 틱 × 호가 단위) × 승수 × 수량
1회 위험        = 가격 위험 + 왕복 비용(계좌 수수료)
남은 손실 여유  = 일일 손실 한도 − 오늘 실현 손실 − 열린 포지션의 남은 위험
신호 허용 조건  = 1회 위험 ≤ 남은 손실 여유
저장 불가 조건  = 일일 손실 한도 < (이 상품·손절 설정에서 예상되는 1회 위험)
```

- 방향을 반드시 넣는다: 롱은 `진입 한계가 = 기준가 + 거리`, 숏은 `기준가 − 거리`. 숏에서 "최대 진입가"를 쓰면 위험을 작게 계산하는 버그가 된다(D-31).
- 고정된 "하루 손절 N회" 대신 **남은 여유**로 판단한다. ATR이 신호마다 달라 1회 위험도 매번 달라지기 때문이다(D-12).
- 수익 목표 도달은 **새 신호만** 멈춘다. 열린 포지션의 손절·청산 감시는 계속한다(§10.2).

### 9.2 상품 규격

| 상품 | 승수 | 호가 단위 · 1틱 | 결제월 |
|---|---|---|---|
| KOSPI200 선물 | 250,000원 | 0.05pt · 12,500원 | 3·6·9·12월(최종거래일 둘째 목요일, 당일 15:20 마감) |
| 미니 KOSPI200 선물 | 50,000원 | 0.02pt · 1,000원 | 매월 |

### 9.3 2026년 9월 수준 예시 (추정, 실제 ATR은 데이터로)

지수 약 1,105pt, 1분 ATR 1.3pt로 가정: 손절 1.56pt, 진입 한계 0.40pt → 최악 진입 기준 손절 거리 1.96pt(롱: 한계가 1,105.60 − 손절 1,103.64 / 숏: 손절 1,106.76 − 한계가 1,104.80).

| | 미니 1계약 | 정규 1계약 |
|---|---|---|
| 손절 거리 × 승수 | 1.96 × 50,000 = 98,000원 | 1.96 × 250,000 = 490,000원 |
| 손절 슬리피지 2틱 | 2 × 0.02pt × 50,000 = 2,000원 | 2 × 0.05pt × 250,000 = 25,000원 |
| **가격 위험** | **100,000원** | **515,000원** |
| 왕복 비용(수수료) | 계좌 수수료로 계산(X원) | 계좌 수수료로 계산(Y원) |
| **1회 위험** | **100,000원 + X원** | **515,000원 + Y원** |

→ 일일 손실 한도가 약 10만원보다 작으면 미니 1계약도 저장되지 않는다. (손절폭이 판단 봉 ATR에 비례하므로 판단 봉을 바꾸면 이 금액도 바뀐다.) 정규·미니 선택은 이 계산과 1-B에서 측정한 스프레드·체결 결과로 정한다.

### 10.2 우선순위 [필수]

1 열린 포지션 위험 → 2 손절 보호 → 3 일일 손실 한도 → 4 당일 청산 → 5 수익 목표 → 6 새 신호. 수익 목표 도달(실현 손익 기준)은 6번만 멈춘다. 열린 포지션 감시는 어떤 경우에도 멈추지 않는다.

## 11. 상태 (1계약 기준으로 단순하게)

| 구분 | 상태 |
|---|---|

## 13. 검증

### 13.1 신호 백테스트

같은 함수로 과거 확정 봉에 진입 조건 → 판단 → 보정 → 신호 규칙을 돌리고, **신호 시점 가격**으로 청산 계획을 적용한 성과. 판단기 자체의 가치(보정 품질, 기준선 대비)를 본다.

### 13.2 체결 재현 (단순하게)

"사람이 따라 했다면"을 1분 봉으로 계산한다.

| 요소 | 방식 |
|---|---|
| 지연 | 신호 → 주문까지 지연(처음엔 가정값, 1-C부터 실제 기록으로 교체). 크론 지연도 여기에 포함 |
| 주문 방식 | 설정에서 고른 한 가지: **시장가**(지연 후 가격 + 슬리피지로 체결) 또는 **지정가**(지연 후 가격이 진입가대로 돌아와 거래된 경우만 체결, 아니면 미체결) |
| 진입 한계가 | 지연 후 가격이 넘어서면 거래 없음(롱은 위, 숏은 아래) |
| 손절 | 손절가 + 손절 슬리피지로 체결 |
| 슬리피지 | 고정값이 아니라 **수집한 최우선 호가 스프레드로 계산**(시간대·변동성별). 민감도는 1·2·4·8틱으로 함께 계산해 4틱 이상에서도 기대값이 버티는지 본다. 정규·미니를 따로 계산(D-43) |
| 한 1분 봉 안에서 손절·목표가 모두 닿음 | 불리한 쪽(손절)으로 계산. 이런 봉의 비율을 함께 보고, 비율이 기준(기본 5%)을 넘으면 결과에 경고를 붙인다 |

- **실제 기록이 가장 좋은 체결 모델이다.** 1-C부터 내 실제 거래(신호가 vs 체결가, 지연)를 모아 슬리피지·지연 가정을 교체한다(D-04).
- **놓친 신호도 본다**: 건너뛴 신호·늦게 따른 신호의 가상 성과를 따른 신호와 비교해, 좋은 신호를 놓치고 나쁜 신호만 따르는 경향(역선택)이 있는지 확인한다.

### 13.3 구간 나누기

개발 구간 안에서 학습/검증을 굴리며(워크포워드) 비교·수정을 하고, 그 뒤 **Lockbox는 관문 직전에 한 번만** 연다. 연 기록을 남기고 다시 쓰지 않는다. AI 모델이 과거를 알 수 있으므로 **실시간 섀도가 최종 확인**이다.

### 13.4 통계

- 신뢰구간은 **거래일 단위로 묶어서** 부트스트랩한다(같은 날 거래들은 서로 영향을 주므로).
- 표본 크기 감각: 거래당 손익의 표준편차가 약 1.5R이면 150건의 표준오차는 약 0.12R이라 평균이 +0.24R은 돼야 하한이 0을 넘는다. 그래서 관문 거래 수를 500건 이상으로 둔다. 1분 판단이면 신호가 많아 표본을 모으기 쉽다.
- 보정 모델과 기대값 평균표는 학습 구간으로만 만들고, 검증 구간·Lockbox에서는 만들어진 것을 그대로 적용해 평가한다.
- 판단기 비교는 차이의 신뢰구간으로: `Jev 기대값 − ML 기대값`의 하한이 0보다 커야 Jev가 낫다고 본다(기본 개선폭 +0.05R도 함께).

### 13.5 관문 (1-B → 1-C) [예시 값, 설정]

| 지표 | 기준(체결 재현, 불리한 쪽 계산) |
|---|---|
| 거래 수 | 개발 구간 검증 합계 **≥ 500**, Lockbox ≥ 100 (D-44) |
| 기대값 신뢰구간 하한 | > 0 (Lockbox는 부호 유지 + 검증 구간 추정 범위 안인지 확인) |
| 슬리피지 가혹 조건(미니 **4틱** · 정규 2틱) · 지연 길게 | 비용 차감 후 기대값 **> 0** (D-52) |
| Profit Factor | ≥ 1.25 |
| MDD | ≤ 일일 손실 한도 × 8 |
| 보정 | Brier가 기저율보다 나음, 구간 승률이 오름차순 |
| 판단기 | 선택한 판단기가 다른 판단기·무작위 진입보다 나음 |
| 리스크 산술 | 선택한 상품·손절·한도가 §9를 통과 |

## 14. 기록 · 재현 · 중복 방지

### 14.1 버전 [필수]

판단·신호·거래·실험마다: 데이터 · 지표 · 스펙(`decision_spec_version`) · Jev 모델(`jev_model_version`) · **Jev 입력 템플릿과 질문(`jev_prompt_version`, Release 1부터)** · 보정 · 기대값 평균표(`ev_model_version`) · 신호 규칙 · 설정 · 체결 모델 · 트레이딩 로직(`trading_logic_version`) 버전. Gemini 프롬프트 버전(`gemini_prompt_version`)은 Release 2부터.

### 14.2 시각 [필수]

`bar_close_at`(봉 마감) · `bar_confirmed_at`(확정 확인) · `decision_at` · `ai_request_at` / `ai_response_at` · `notify_sent_at` · `opened_at`(화면 열람) · `ack_at`(확인 버튼) · `order_at`(KIS 주문체결내역의 주문 시각) · `fill_at`.

이렇게 나누면 지연을 **서버(마감→발송) · 사람 보기(발송→열람) · 사람 판단(열람→주문) · 시장(주문→체결)** 으로 구분할 수 있다. 각 구간의 중앙값·90%·95% 값을 화면에서 본다.

### 14.3 유일 키 [필수]

| 대상 | 유일 키 [예시] |
|---|---|
| 봉 | 월물 + 봉 종류 + 봉 시작 시각 |
| 판단 | 월물 + 판단 봉 시각 + 스펙 버전 + 판단기 |
| 신호 | 판단 ID + 신호 규칙 버전 |
| 알림 | 신호 ID + 알림 종류 |
| 체결 | KIS 체결 번호(주문번호 + 체결 순번) |
| 크론 실행 | 작업 이름 + 예정 분 |

같은 것이 두 번 들어오면 DB가 거부하고, 처리는 트랜잭션 안에서 한다.

**외부 호출(Jev·알림)은 먼저 선점한 실행만 한다 [필수]** (D-33): 유일 키만으로는 두 크론이 동시에 Jev를 부르고 알림을 두 번 보낼 수 있다. 그래서 순서를 정한다.

1. 판단 행을 `pending`으로 먼저 넣는다(`INSERT … ON CONFLICT DO NOTHING`). 넣는 데 성공한 실행만 다음으로 간다.
2. 그 실행만 Jev를 부르고 결과를 저장한다(`completed` / `failed`). 오래 `pending`이면 다음 실행이 이어받는다(시간 기준).
3. 알림은 바로 보내지 않고 **알림 대기 표**에 유일 키(신호 ID + 알림 종류)로 넣은 뒤, 보낸 실행이 `sent`로 표시한다. 재시도는 `sent`가 아닌 것만.

새 서버 없이 기존 DB와 크론으로 된다.

선점 의사코드 [필수] (D-57):

```sql
-- 1) 선점: 성공한 실행만 id를 받는다
INSERT INTO trading_judgments (contract_code, decision_tf, bar_close_at, spec_version, judge, status, claimed_at)
VALUES ($1, $2, $3, $4, $5, 'pending', now())
ON CONFLICT (contract_code, decision_tf, bar_close_at, spec_version, judge) DO NOTHING
RETURNING id;
-- id가 없으면 여기서 끝(다른 실행이 처리 중이거나 완료)

-- 2) 오래 멈춘 선점 이어받기(선점 후 60초 넘게 pending)
UPDATE trading_judgments SET claimed_at = now()
WHERE contract_code = $1 AND decision_tf = $2 AND bar_close_at = $3 AND spec_version = $4 AND judge = $5
  AND status = 'pending' AND claimed_at < now() - interval '60 seconds'
RETURNING id;

-- 3) 판단기 호출 후 결과 저장: status = 'completed' | 'abstain' | 'failed'
```

크론 실행 자체도 `trading_job_runs (job_name, scheduled_minute)` 유일 키로 한 번만 돈다. 이 API 라우트는 한 번 실행이 1분 안에 끝나야 하므로 `export const maxDuration = 60`처럼 실행 한도를 명시하고(Jev 대기 10초 포함), 50초가 넘으면 남은 일을 다음 실행으로 넘긴다.

### 14.4 장중 로직 버전 고정 [필수] (D-36)

배포도 전략을 바꿀 수 있다. 트레이딩 판단에 쓰이는 코드(`lib/trading/**`)의 해시를 빌드 때 `trading_logic_version`으로 기록하고, **거래일 시작 시 값을 고정**한다. 장중에 이 값이 바뀌면(다른 모듈 배포는 해당 없음) SG-12로 새 신호를 막고 "로직 변경 감지 — 다음 거래일부터 적용"을 알린다. 관리자가 확인하면 그날은 "구성 변경일"로 따로 집계하고 재개할 수 있다. 종목 정보·설정도 거래일 시작 시 스냅샷을 고정한다.

## 15. 설정

### 15.1 설정 레지스트리 [필수]

모든 값을 한곳에 선언하고 설정 화면은 여기서 만든다. 저장 시 리스크 산술(§9) 등 검증을 통과해야 한다. 변경 이력과 되돌리기. 그룹 예: 기본 · 상품·세션 · 판단 · 보정 · 안전 게이트(기준값만) · 신호 규칙 · 청산 · 일일 한도 · 이벤트 · 알림 · 체결 재현 · 검증 · AI.

값은 하나로 관리한다. 예: 하루 최대 신호 **기본 6** — 규칙·설정·화면이 모두 이 값 하나를 읽는다.

### 15.2 변경 적용 [필수]

전략에 영향을 주는 변경은 **다음 거래일부터**. 즉시 적용은 신호를 막는 쪽(오늘 신호 끄기, 게이트 기준 강화, 진입 조건 끄기)만. 사람이 즉시 적용을 강제하면 그날은 성과 집계에서 따로 표시한다.

### 15.3 AI 개입 [필수 · Release 3부터 활성]

항목마다 자동 / 승인 / 끔. 적용은 다음 거래일. **AI가 절대 바꿀 수 없는 것**:

소유자·권한 · KIS/AI 자격증명 · 일일 손실 한도 **올리기** · 안전선 · 안전 게이트 · 실행 방식(주문 여부) · 손절 보호 정책 · 감사 기록 정책 · AI 개입 수준 자체 · Lockbox 열기와 관문 통과 선언.

### 17.2 그 밖의 규칙


- 소유자 전용: 기존 판정은 관리자를 먼저 통과시키므로 소유자 확인을 추가한다(방법은 기존 구조에 맞게).
- KIS 토큰 [필수] (D-51): 토큰과 만료 시각은 DB **한 행**에 암호화 저장한다. 모든 실행은 이 값만 쓴다. **만료 30분 전(설정)까지는 어떤 실행도 재발급 API를 부르지 않는다.** 그 이후에는 DB 잠금을 잡은 실행 **하나만** 재발급하고, 나머지는 잠금이 풀릴 때까지 기다렸다가 새 값을 읽는다. 재발급이 거부되면(1분 1회 제한, `EGW00133` 등) 다른 실행이 이어서 재발급을 시도하지 않고, 1분 뒤 잠금을 잡은 실행이 한 번만 다시 시도한다. 그동안 조회가 막히면 SG-02. 워커는 필요 없다.
- KIS 자격증명: 기존 암호화, 쓰기 전용, 이 시스템 전용 앱키. 호출 수는 KIS 한도보다 낮게(설정).
- 크론 인증: 크론에는 사용자 세션이 없으므로 화면 API(`requireAdminApi`·소유자 확인)와 **따로** 기존 크론 인증(서비스 토큰, Vercel의 `CRON_SECRET` 방식)을 재사용한다. 1분 크론은 **Vercel Pro 이상**이 전제다(기존 시스템이 이미 1·2분 크론을 쓰고 있음).
- AI로 계좌번호·실명을 보내지 않는다.
- **스케줄러 예외**: 기존 시스템의 배치 정책은 Vercel Cron이다. 이 모듈은 1분 판단의 정시성 때문에 **이미 쓰는 Supabase의 pg_cron을 기본 스케줄러로 예외 채택**하고, Vercel Cron은 대체 수단으로 둔다(D-39).
- 기존 정책: Next.js 앱 하나 · App Router · Tailwind + 토큰 + CSS Modules · Supabase JS · 같은 마이그레이션에서 RLS · 설정은 DB + 관리자 화면 · 기존 AI 계층 · 기존 알림·업무·감사 · PWA 캐시 제외(`/trading/**`) · 조용한 실패 금지.

- 호출은 **순차 큐 + 최소 간격**(기본 200ms, 설정)으로 보낸다. 실전 한도는 계좌당 초당 약 18~20건 수준이라 여유가 있고, 모의는 훨씬 낮다. 국내선물옵션 조회(현재가·분봉·호가·잔고·주문체결내역·증거금, 야간은 별도 조회 API). 주문 계열은 구현하지 않는다.

**증거금**: 증거금률은 KIS 조회 값을 쓴다. 지수 약 1,100pt에서는 정규 1계약 증거금이 수천만 원 수준일 수 있어(리뷰 추정 약 6,000만원, 미니 약 1,200만원 — 확인 필요) 예탁금에 따라 정규는 아예 불가능할 수 있다.

**KOSPI200 선물**: 정규 승수 250,000원·0.05pt(12,500원)·3·6·9·12월·최종거래일 둘째 목요일(당일 08:45~15:20)·정규장 08:45~15:45·야간장 18:00~06:00. 미니 승수 50,000원·0.02pt(1,000원)·매월물. 2026년 9월 KOSPI200 선물 약 1,050~1,130pt. 금액은 항상 데이터로 계산.
